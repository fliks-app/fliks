# Spec: provider plugins

Scope: metadata providers as plugins. The `provider` manifest block, the `metadata-provider` WIT interface and its host imports, id namespaces open to third parties, the Fliks defaults a plugin reads, the outbound limiter and the provider lane, bundled providers. The plugin lifecycle, the manifest keys, the install pipeline and the WIT package are in `plugins.md` (this file is its section J); the trait the host adapts a provider to, the registry, the limiter and the snapshots are in `metadata-orchestrator.md`; the record shapes a provider returns are in `metadata.md` (rules 24, 25, 31, 32, 34) and `book-metadata.md`; id storage is in `external-ids.md`.

The pluginApi stays 3: the `metadata-provider` interface and the `provider` world are part of `fliks:plugin@3.0.0` from its first release.

## Model

1. A provider is a `process` plugin (wasm) whose manifest carries a `provider` block and whose component exports `fliks:plugin/metadata-provider@3.0.0` (the world `provider`, which is the world `plugin` plus that export). There is no third tier: `PluginSummary.kind` stays `data` or `process`, the role is read from the manifest. A manifest with a `provider` block and a component without the export, or the export without the block, fails registration `invalid-component` (`plugins.md` rule 7, step 10).
2. A provider holds no database: `database.schema` is `false` (any other value is `PLUGIN_BAD_MANIFEST`), `scopes` may be empty (rule 3 of `plugins.md` otherwise asks for one), and `config-get` needs no scope (it reads only the caller's own keys, `plugins.md` rule 24; `config-set` still needs `config:rw`). The host calls a provider on its `provider` lane (rules 50-53) and keeps its `core` lane for `hello` and `health`.
3. Official ids follow `fliks.download` and `fliks.notify`: `fliks.tmdb`, `fliks.tvdb`, `fliks.openlibrary`, `fliks.googlebooks`, `fliks.bnf`, `fliks.audible`, `fliks.audnexus`, `fliks.thexem`, `fliks.musicbrainz`, `fliks.fanarttv`, `fliks.lrclib`. They live in `fliks-app/plugins`, each with its own version and tag.
4. The core keeps what touches data integrity and indexes it by namespace (uniqueness, collections, the request title lock, the merge and its field orders, `metadata_snapshots`, `media_field_sources`); a provider only talks to its upstream API and maps the answer to the record shapes. The host adapter (`PluginProvider`) implements `MetadataProvider`, so the orchestrator, the snapshots, the single-flight and the merge do not change.

## Manifest block

`provider` is an object with these keys and no other, at most one block per manifest. Its shape is checked with the rest of the manifest (`PLUGIN_BAD_MANIFEST`, the vector set `plugin-manifest`); the namespace rules of 19-33 run at registration.

| Key | Required | Shape |
|---|---|---|
| `namespaces` | yes | 1 to 8 entries, no name twice. A core namespace: `{name}` alone. A plugin namespace: `{name, label, idPattern, case?}`, `label` 1 to 64 characters, `idPattern` a string (rule 20), `case` `preserve` (default), `lower` or `upper`. |
| `kinds` | yes | Object, at least one key from `movie series book comic album`; each value a non-empty array of distinct capabilities from `search work children childStubs edition chapters person credits findBy lists scene lyrics artistSearch recordingSearch` (`lyrics`, `artistSearch` and `recordingSearch` under `album` only). |
| `findBy` | no | Distinct namespace names the `find-by` call accepts as input. |
| `sceneNamespaces` | with `scene` | Distinct core namespace names the `scene-mapped-ids` and `scene-mapping` calls accept as origin (`tvdb`). Required, and non-empty, when a kind lists the `scene` capability; absent otherwise. |
| `editionNamespaces` | no | Distinct namespace names `fetch-edition` accepts (ISBN, ASIN, OLID). |
| `chapterNamespaces` | no | Distinct namespace names `fetch-chapters` accepts (ASIN). |
| `limits` | yes | `{ratePerSec, burst, dailyQuota?, backgroundShare?, maxPauseSecs?}`: `ratePerSec` a number in (0, 1000], `burst` an integer 1 to 1000, `dailyQuota` null or an integer of at least 1, `backgroundShare` a number in (0, 1], default 0.75, `maxPauseSecs` an integer 300 to 86400, default 300: the longest a `rate-limited(retry)` of this plugin pauses the limiter (rule 57). |
| `requestTimeoutMs` | no | Integer 1000 to 60000, default 10000. |
| `snapshotTtlSecs` | no | Object over `work children edition person chapters credits` (`credits`: the discography of an artist, `person-credits` of a music provider); each value null (never expires) or an integer of seconds, at most 315360000 (ten years); a missing resource is 0. |
| `imageHosts` | no | At most 16 distinct lowercase host names, each with a dot and no scheme, port, path or wildcard. |
| `requires` | no | Distinct config keys (`^[A-Za-z][A-Za-z0-9_-]{0,63}$`, no `.`: a key with a dot is not one key of a plugin's own settings) that must resolve non-empty for the provider to be available (rule 41). |

Official block of a core namespace:

```json
"provider": {
  "namespaces": [{ "name": "tmdb" }],
  "kinds": {
    "movie":  ["search", "work", "person", "credits", "findBy", "lists"],
    "series": ["search", "work", "children", "childStubs", "person", "credits", "findBy", "lists"]
  },
  "findBy": ["imdb", "tvdb"],
  "limits": { "ratePerSec": 40, "burst": 40 },
  "requestTimeoutMs": 10000,
  "snapshotTtlSecs": { "work": 0, "children": 0 },
  "imageHosts": ["image.tmdb.org"],
  "requires": ["apiKey"]
}
```

A third-party provider with its own namespace (plugin id `org.example.anime`):

```json
"provider": {
  "namespaces": [
    { "name": "org.example.anime:aid", "label": "Example Anime DB", "idPattern": "^[1-9][0-9]{0,8}$", "case": "preserve" }
  ],
  "kinds": { "series": ["search", "work", "children", "findBy"] },
  "findBy": ["imdb", "tvdb"],
  "limits": { "ratePerSec": 1, "burst": 2 },
  "imageHosts": ["cdn.example.org"]
}
```

5. The first namespace is the provider's key in the registry: `preferredProvider`, the order per kind and `metadata_snapshots.provider` name it.
6. Capabilities of a kind map to the WIT functions: `search` to `search`, `work` to `fetch-work`, `children` to `fetch-children`, `childStubs` to `child-stubs`, `edition` to `fetch-edition`, `chapters` to `fetch-chapters`, `person` to `fetch-person`, `credits` to `person-credits`, `findBy` to `find-by`, `lists` to `list`, `scene` to `scene-mapped-ids` and `scene-mapping`. The host calls only what is declared: a call with a declared kind (`search`, `work`, `children`, `childStubs`, `lists`) needs the capability under that kind; `edition`, `chapters`, `person`, `credits`, `findBy` and `scene` carry no kind and need it under any kind. A provider whose only capability is `scene` serves no kind of work: `supports(kind)` is false, so it never enters the order of a kind and no `resolve` or `fallback` returns it. The host answers an undeclared call `Upstream` status 404 without entering the component. `supports(kind)` is a key of `kinds`; `has_persons()` is `person` under any kind. `artistSearch` and `recordingSearch` both map to `search` with `search-query.extra` holding `target` (`artist` or `recording`); a plain `search` carries no `target`, so the album search stays what it was. The host sends a target search only to a provider declaring that capability under `album`, and answers an undeclared one `Upstream` status 404.
7. `findBy`, `editionNamespaces` and `chapterNamespaces` only say what the plugin reads as input; any namespace known to the core (rule 19) may be listed.
8. `limits`, `requestTimeoutMs` and `snapshotTtlSecs` replace the host constants `LIMITS`, `TMDB_TIMEOUT`, `TVDB_TIMEOUT` and `snapshot_ttl()`.
9. `imageHosts` (at most 16 lowercase host names, the last label not numeric) is the only set of hosts, with their subdomains for a bundled plugin, from which the core downloads an image named by a record of this provider (rule 32).
10. Capabilities shown in the inspect report and the consent sheet (`plugins.md` rule 12): `namespace:<name>` per declared namespace, in order, then `provider:<first namespace>:<kind>` per kind, kinds sorted. They follow `network:internal`.
11. A new `namespace:` capability in an update holds it like a new scope (`plugins.md` rule 29).
12. `plugin.template.json` carries the same block; `fliks-plugin-sdk-provider` (`crates/plugin-sdk/provider`, next to the SDK because two `generate!` of one crate clash on their exported macros) holds the `MetadataProvider` guest trait and `export_provider!`, which export the world `provider`, `check_world` accepts the `metadata-provider` export when the manifest has the block and refuses it otherwise.
12a. The official scene provider is `fliks.thexem` (namespace `fliks.thexem:xem`, kind `series`, capability `scene`, origin `tvdb`): it answers `scene-mapped-ids` from TheXEM's `/map/havemap?origin=tvdb` and `scene-mapping` from `/map/all?origin=tvdb&id=<id>`, its base URL a plugin setting with the TheXEM default. It is bundled (rule 45).

## Calls

The interface is the one in the WIT package of `plugins.md` (`metadata-provider`). Every record is a `json` document, not a typed record: the trait already speaks JSON, the merge works on maps, and typing the fields would freeze each one in the ABI.

13. Arguments: `kind` is a documented kind string; `lang` carries the resolved metadata language (`language`, `region`, `locale` = `tmdb_locale`); `search-query` mirrors the `Search` of the trait (`kind`, `query`, `year`, and for books `title`, `author`, `author-id`, `isbn`, `language`) plus a 1-based `page`. An id argument is an `external-id` of one of the provider's namespaces (`fetch-work`, `fetch-children`, `child-stubs`, `fetch-person`, `person-credits`), of `editionNamespaces` (`fetch-edition`) or of `chapterNamespaces` (`fetch-chapters`). `search-query.extra` is the extension slot: further search parameters by name, ignored by a provider that knows none. `find-by` answers the `external-id` (in the provider's registry key, its first namespace, normalised by rule 28; any other is none) and kind it knows the work of `source` by, or none; `fetch-edition` and `fetch-chapters` answer none for an unknown edition; the host answers none, not 404, for `find-by`, `fetch-edition` and `fetch-chapters` when the plugin does not declare the capability. `list` takes a list name (`trending popular upcoming genres discover`), its string parameters and the kind.
14. Results: the host validates each record on receipt. It must parse as JSON, be at most 16 MiB, and be an object (an array of objects for `search`, `fetch-children`, `child-stubs` and `list` where the metadata specs say array). Keys outside the `Field` set are ignored by the merge. A malformed record is `Upstream` status 502 and counts as a failure for the provider's breaker: 3 in a row, with no valid record between, open it as 3 failed requests do (rule 56). A list answer has at most 10 000 elements. `ids` is an object of namespace to an id or an array of ids: at most 32 namespaces and 16 ids per namespace are read, a namespace the core does not know (or a third-party provider does not own, rule 26) is dropped, ids are normalised by rule 28, and a record whose `ids` is no object loses it; a third-party record also loses `tmdbId`. Dropped entries are warned by count. A person is an object `{name, biography, birthday, deathday, placeOfBirth, avatarUrl, knownForDepartment}` (each string or null, as `metadata.md` rule 34), credits are `{cast: [...], crew: [...]}` of the person credit items of that rule.
15. `provider-error` maps to `Upstream`: `not-found` to status 404, `unauthorized` to 401 (the provider stays registered; it is unavailable until a setting of the plugin changes; a 401 that answers a call begun before that change does not count), `rate-limited(retry)` to 429, and the host's limiter pauses for `retry` seconds when given (at most `limits.maxPauseSecs`, rule 57), else as for a `Retry-After` it did not read (rule 54); `unsupported` to 404 like an undeclared call; `upstream({status, message})` to that status (none when the upstream gave none) with the message as reason (the host logs it; a plugin never puts a URL or a secret in it).
16. The priority does not cross the boundary. The host knows the priority of the export in progress and applies it to every outbound request of that export (rule 54).
17. `provider-set-limits(rate-per-sec, burst, daily-quota)` replaces the plugin's limiter limits (an upstream's `x-ratelimit-*` headers, the contact-email tier of OpenLibrary); `provider-quota-spent` marks the day's quota spent until midnight UTC. Both are for a plugin with a `provider` block and answer `ERR_DENIED` to any other. Values are checked as the manifest's `limits`; a bad value is `ERR_VALIDATION`.
18. A plugin keeps no state the result depends on (`plugins.md` rule 40). A cached login token is a performance cache: a new instance logs in again, a 401 triggers it.
18a. Scene numbering (`scene-numbering.md`). The two calls are the functions of the optional interface `scene`, not of `metadata-provider`: a provider that declares the `scene` capability is built from the world `scene-provider` (the world `provider` plus the `scene` export) and the host reads that export only for a manifest that declares it, so a provider built before the interface existed stays valid. `scene-mapped-ids(origin)` answers the ids of `origin` (a namespace of `sceneNamespaces`) the provider has a scene mapping for, as strings; `scene-mapping(id)` answers the mapping of one id as a list of `scene-pair {scene-season, scene-episode, season, episode}` (the scene numbering of a release name and the aired numbering it maps to, all `u32`), or none when the provider has no mapping for it (an upstream answer that says so is none, never an error). A manifest that declares `scene` for a component without the export fails registration `invalid-component`. A host call to an origin outside `sceneNamespaces`, or without the capability, is `Upstream` 404 without entering the component. The host reads at most 200 000 ids and 100 000 pairs; a longer answer is a malformed record (rule 14). A list of ids is not validated further (the core keeps the ones that are positive integers), a pair list that is empty is none. The core calls the first available provider that declares `scene` for `tvdb`, in registration order, at background priority for the refresh and interactive for a mapping a release or import needs at once; the limits, timeout and breaker are the provider's own (rules 8, 50-54). With no such provider the core reads no scene numbers (`scene-numbering.md` rule 3).
18b. Lyrics (`music.md` rule 68). `fetch-lyrics(query)` is the one function of the optional interface `lyrics-provider`, built from the world `full-provider` (the world `scene-provider` plus that export); a provider declares it with the capability `lyrics` under `album` (under no other kind: `validate_block` refuses it) and the host reads the export only for a manifest that declares it. A hit with a `format` outside `lrc elrc ttml srt plain`, a document over 1 MiB or a document that does not parse (`fliks_domain::lyrics::parse`) is a malformed record (rule 14), counted by the breaker; a provider that declares `lyrics` serves no `album` metadata unless it declares another capability under `album` too.

## Namespaces

An id namespace names the system an external id belongs to (`external-ids.md`). The set is open to plugins, in two classes.

| | Core namespace | Plugin namespace |
|---|---|---|
| Form | bare name `^[a-z][a-z0-9]{1,31}$`: `tmdb tvdb imdb` and those `ExternalProvider` lists | `<pluginId>:<name>`, `<name>` = `^[a-z][a-z0-9-]{0,31}$`, e.g. `org.example.anime:aid` |
| Declared by | `ExternalProvider` (Rust); adding one is a core change | the manifest of the plugin whose id is the prefix |
| An id is valid | `ExternalProvider::normalize` | the manifest's `idPattern`, applied by the core |
| Unique | decided by the core (`is_unique`) | never |
| Served by | an `official` package only | the owning plugin |

19. A namespace name is classified by form (`fliks_domain::plugins::provider::classify`): a name with no `:` is core, one with a `:` is a plugin namespace whose prefix is a legal plugin id (`plugins.md` rule 1) and whose rest matches the form above; anything else is no namespace and fails the shape check. `:` appears in no core name, so a plugin namespace cannot imitate a core one, present or future.
20. Registration checks, in declaration order, the first failure ends the registration with that reason (`plugins.md` rule 7, after the permissions and routes of step 8): a plugin namespace whose prefix is not the plugin's own id is `namespace-not-owned`; a bare name `ExternalProvider` does not know is `unknown-provider-namespace`; a bare name it knows declared by a package that is not `official` is `core-namespace-not-official`; an `idPattern` that is not anchored (`^` first, an unescaped `$` last), is over 256 characters (counted in characters, not bytes) or does not compile is `invalid-namespace-pattern`. Patterns use the syntax of the Rust `regex` crate (linear time, no lookaround or backreference, so a pattern cannot be made to backtrack), built with a 1 MiB compiled-size limit and a nesting limit of 32, and applied as `^(?:<idPattern>)$` so a match is always a full match whatever alternation the author wrote. The core compiles it once per namespace (`IdRule`), not per id. Registration runs these checks (`check_namespaces`) for every provider block; `namespace-signer-changed` (rule 21) runs once the plugin has answered `hello`, after every check that can refuse it before then (permissions, `coreRefs`, the component, the database, the handshake), so a package that fails before it is alive freezes nothing; one that fails later (`ready` never comes) keeps its claim, which only the same signer can take again.
21. Ownership is frozen by signer. The table `provider_namespaces(name text PRIMARY KEY, "pluginId" text NOT NULL, "signerKeyId" text NULL, "idPattern" text NOT NULL, "case" text NOT NULL, label text NOT NULL, "createdAt", "updatedAt")` is written at the first registration that reaches the claim of rule 20 (later ones refresh `idPattern`, `case` and `label`). The rule is the one `may_adopt` applies to kept data: a row is taken by a package with the same signer, and a signed package takes over an unsigned row (the row then records the signer); any other change (another key, or an unsigned package over a signed row) is refused. Install refuses it first: `409 PLUGIN_NAMESPACE_SIGNER` before anything is committed, next to `PLUGIN_KEPT_DATA_SIGNER`; registration repeats the check as `namespace-signer-changed`, atomically for all the plugin's namespaces (one refused leaves none written). Core namespaces have no row.
22. The migration is `1789000000510_open-namespaces.sql`: `provider_namespaces`, and the closed `CHECK`s on `media_external_ids` (030), `requests` (040), `person_external_ids` (100), `collection_external_ids` (120) and `edition_external_ids` (200) become one form check, at most 84 bytes: `provider ~ '^[a-z][a-z0-9]{1,31}$' OR provider ~ '^[a-z][a-z0-9]*(\.[a-z0-9]+)*:[a-z][a-z0-9-]{0,31}$'`, plus a 1 to 128 character check on the id of a plugin namespace. `media."preferredProvider"` and `item_groups."preferredProvider"` widen to `text`. The database no longer knows which bare names are the core's: Rust checks it on every write. No data moves.
23. Rust: `fliks_domain::external_id::Namespace` is `Core(ExternalProvider)` or `Plugin(PluginNamespace)`. `ExternalProvider` stays the closed enum where the code reasons on one namespace (uniqueness, collections, the `tmdbId` of the request wire). Registry keys, `metadata_snapshots`, `media_field_sources`, the order per kind and `preferredProvider` use `Namespace`. `Namespace` is a plain `Copy` value: `Namespace::parse` is syntactic (a core name, or any name `classify` accepts as a plugin's) and holds no process state. What a plugin namespace is stored with lives in `Namespaces` (its `label` and `idPattern` rule), a value the server holds in `Plugins::namespaces` and fills from `provider_namespaces` when a row is claimed or loaded; `load` runs at boot before any task that reads ids, settings or requests. Inputs from a caller or a plugin (a route's `provider`, `preferredProvider`, a provider record's `ids`, `Metadata::require` and the admin provider order) parse through `Namespaces::parse`, which refuses a plugin namespace that is not declared; stored rows parse syntactically, and a media's plugin `externalIds` list only the namespaces `provider_namespaces` holds. `external_ids::link` re-checks a plugin namespace against `provider_namespaces` in its own statement (a key share lock, which `deleteData` waits on since it locks those rows first), so a snapshot taken before a deletion stores nothing. `Namespaces::normalize` and `Namespaces::label` answer a namespace that is not declared (deleted by `deleteData`) with no id and its name, so a request row that still names one decodes and lists.
24. The pure functions (`classify`, `check_namespaces`, `IdRule::new` and `IdRule::normalize`, `validate_block`) live in `fliks_domain::plugins::provider`; `sanitize_ids` and `answered_id` are in the same module; the vector sets `provider-namespace` (its `sanitize` cases pin rules 26 and 14's bounds) and `plugin-manifest` pin them.
25. A plugin namespace is never unique, with no admin opt-in: an opt-in needs a partial unique index driven by a flag over data that may already hold duplicates, and a 409 path for a namespace the core knows nothing about. Two media for one title are avoided by the title lock and the lowest-id lookup of rule 31.
26. Cross ids. A record often carries ids of other namespaces (TVDB answers `tmdbId`). The merge keeps, from an `official` provider, what it keeps today; from a third-party provider, its own namespaces only: it writes no core id at all (`sanitize_ids` drops the core namespaces of `ids` and the keys `tmdbId`, `tvdbId`, `imdbId`, `tmdbCollectionId` and `tmdbCollectionName`, in nested records too). A third-party plugin can neither link a media to a core id nor cause a 409 on one, and no cross-reference into a core namespace is made from its record (rule 31); the core ids a refresh falls back on (`external_id_for`, `Ids.fill`) are only those written by core providers or users. The TMDB collection is a core namespace's too, so a plugin cannot create, join or rename one; the merge (`merge`) skips those keys and the core ids for a record of a plugin namespace whatever reached it. Person ids written for the cast and crew of a record go under the namespace that served the record (never a field of the record), each normalised by it.
27. Uninstall or disable of a third-party provider keeps its ids (`media_external_ids`, `person_external_ids`, `requests`) and its `provider_namespaces` row: they are the media's data, like a kept schema (`plugins.md` rule 20). With no provider, the namespace is no longer refreshed and the merge skips it; a field it filled and nobody locked is taken at the next refresh by the next provider in the order: a `preferredProvider` of the media or a season naming such a namespace, one that cannot be read, is skipped like the library's (the media then resolves by its core ids, which a plugin record never wrote, rule 26: those of a core provider or a user, else `No provider ID available`), and `identify` without `preferredProvider` clears a pin to a plugin namespace. The client shows the raw id with the stored `label`. A reinstall by the same signer resumes everything.
28. Normalisation of a plugin id: trim, NFC, `case` applied (`lower`, `upper`), 1 to 128 characters, no control character, format character (Unicode `Cf`), whitespace (U+2028 included) or `:`, then a full match of `idPattern`. An id it refuses is dropped with a warn naming the namespace, never the value, and does not block the rest of the record. It applies to every id that enters: the `ids` of records and of the records nested in them (`cast`, `crew`, `seasons`, `episodes`), those of `fetch-edition` and `fetch-chapters` answers, the `find-by` result, the ids of the link routes (`media/external_ids.rs`), the `externalId` of `/api/metadata/:provider/...` for a plugin namespace and of `media-resolve-or-create`; the import and refresh reads of a plugin namespace take it in that form, the numeric check being a core namespace's. A `find-by` answer is an id of the plugin's own first namespace, normalised by that namespace (`answered_id`: an OpenLibrary key may come as `/works/OL1W` and is a work, an Audible or Audnexus id is an ASIN, for which the core has no namespace rule). A record's `ids` holds at most 32 namespaces and 16 values under each; the namespaces beyond are counted as dropped. An `idPattern` changed by an update governs later writes; stored ids are not revalidated, and the registration that changed it warns how many stored ids (`media_external_ids`, `edition_external_ids`, `person_external_ids`, `collection_external_ids`) no longer match.
29. `DELETE /api/plugins/:id?deleteData=true` deletes, in one transaction, for the namespaces of `provider_namespaces` whose `pluginId` is the plugin: their ids in `media_external_ids`, `edition_external_ids`, `person_external_ids` and `collection_external_ids`; their `metadata_snapshots`; their `media_field_sources` and `edition_field_sources` rows (a locked row is kept with `provider` NULL, so the lock survives); their `discovered_works` rows; `preferredProvider` on `libraries`, `media` and `item_groups` when it names one (set to NULL); and the `provider_namespaces` rows; once the transaction commits the process forgets them (`Namespaces::forget`), so process and database agree. A request that is not finished and has no media yet (`"mediaId" IS NULL`) becomes `failed` with reason `provider-removed`; every other request keeps its row with its `provider` and `externalId` (both are `NOT NULL`, the request is history): in-flight downloads are not cut. A claim of a namespace gets a `generation` (`provider_namespaces."generation"`, from a sequence, kept by later refreshes) and a request stores the one it was created under (`requests."namespaceGeneration"`, NULL for a core namespace); the title lookup of requests only matches the current generation, so another signer's re-claim after `deleteData` ignores the old rows (migration `1789000000554_namespace-generation.sql`).
30. Title lock: `requests:<kind>:<namespace>:<id>` holds as it is for a plugin namespace (the `:` of the namespace is not ambiguous: kind and id carry none, and rule 28 refuses an id with one).
31. `media-resolve-or-create` (`plugins.md` rule 57) keeps the entries whose namespace is served by a registered provider that supports the kind, a unique core namespace first (`tmdb` for video, `openlibrary` for books), then the others in the order given. An existing media is found by any of them whatever the provider's state, the first entry that holds one winning; creating one needs a provider available and uses the first entry whose provider is, so `[tmdb:603, org.x:7]` with TMDB unconfigured creates through the plugin (`unsupported-provider` when none is). An id that is not valid for the namespace of a served entry, with no valid entry, is `ERR_VALIDATION`. The title locks of all the entries are taken in the order of the `hashtext` value they lock (no deadlock between two calls), then it answers the lowest media id holding one (`external-ids.md` rule 6), else imports. An import by a plugin namespace links the id it was looked up by and sets the media's `preferredProvider` to that namespace when the plugin served the record, so the next call finds the media and a refresh reads the plugin again. A found media is changed by nothing. For `book` a creating entry that is not `openlibrary` makes the media from the plugin's work record alone (`plugins.md` rule 57). A create goes through the first available entry that is a core namespace or one of the caller's own namespaces (`<pluginId>:`), and links the caller's other own entries before `media.imported` is sent, so a later call by any one of them finds the media; a core id is never linked from a plugin call. A cross-reference into a core namespace happens only when a core namespace found the title: a plugin record never fills a `tmdbId` (`media-write.md` rule 17), and a library preference for a core provider does not re-read a plugin's record there. One entry per namespace counts (the first), and a namespace already linked by the import is not linked twice. A call whose entries name no core namespace and none of the caller's own is `namespace-not-owned` ("namespace not owned by the caller") when the media is not found. Two plugins naming one title by two namespaces create two media; manual merge is the remedy. `unsupported-provider` when no entry has a provider.
32. Images. The URL of an image comes from the plugin and is untrusted. `images/store.rs` downloads through the outbound connector (`net::guard`, the address classes of `fliks_domain::net`; `image-store.md` rule 26) and only from a host of `provider.imageHosts` of a registered provider plugin, or a subdomain of one when the plugin is bundled (`image-store.md` rule 29); it follows redirects only to a host of that list. The merged `Details` do not say which provider supplied an image, so the list is the union of the registered plugins' (a plugin's hosts leave it when the plugin is unregistered or revoked) and a host declared by one plugin serves the images of another.
33. Without TMDB (disabled): `movie` and `series` go through TVDB or a third-party provider; with no video provider a scan creates unidentified titles and the search routes answer `[]`; `media-resolve-or-create` falls to the next entry (rule 31).

## Defaults and overrides

34. Fliks ships its project keys in the source, not read from the environment: `plugins/defaults.rs` holds `DEFAULTS: &[(ExternalProvider, &str, &str)]` (`tmdb`, `tvdb` and `fanarttv`, key `apiKey`, as literals). Every build has them; a key typed in the plugin settings overrides it (rule 35). No route serves a default.
35. A form field of the plugin declares its default: `{"key": "apiKey", "type": "text", "labelKey": "tmdb.apiKey", "secret": true, "default": "fliks:apiKey"}`. The host resolves `plugin.<id>.apiKey` as the stored override when non-empty, else the Fliks default, in the `hello` config and in `config-get` (`plugins.md` rules 34, 41). `config-changed` is sent when the override changes or is cleared. The plugin cannot tell where a value comes from.
36. `fliks:<key>` resolves only for a plugin whose first namespace is the namespace of the `DEFAULTS` entry and whose package is `official` (`verifiedByKeyId` is a compiled key). Otherwise the field has no default (a warn at registration; the plugin works with a key the admin types). No plugin reads another namespace's key.
37. The override is the setting `plugin.<id>.apiKey` (secret through the field's `secret: true`, `settings.md` rule 17); no new table. `PUT /api/settings/plugin.<id>.apiKey` with `value: null` clears it (`settings.md` rule 16): the effective value is the default again. Writing or clearing needs `Manage Settings`.
38. Nobody reads a key back. `GET /api/settings` returns only `secretsSet`; a default appears in no response, no export (`GET /api/plugins/:id/export` knows only stored settings) and no log (the outbound guard never logs a URL).
39. `GET /plugins/ui` gives each field `hasDefault: bool` (rule 36) and `requiredByProvider: bool` (the key is in `requires`), and drops a `fliks:` `default`. For a secret field the client shows "Fliks default key" when `hasDefault` and not in `secretsSet`; "Custom key" and a **Reset** button when both; "Key required" when neither and `requiredByProvider`; typing an unsaved key hides "Fliks default key".
40. Environment keys: `TMDB_API_KEY` and `TVDB_API_KEY` are imported once into `plugin.fliks.tmdb.apiKey` and `plugin.fliks.tvdb.apiKey` when they differ from the default in the source, the setting `metadata.env_keys_imported = 'true'` marking it done; later boots ignore them with a warn. `FLIKS_TMDB_API_URL`, `FLIKS_TVDB_API_URL` and `FLIKS_TMDB_IMAGE_URL` are removed; tests redirect upstreams with `FLIKS_PLUGIN_UPSTREAM_OVERRIDE=<host>=<url>,...`, read at boot, logged at warn, applied by the outbound hook (host rewrite, the target exempt from the private class).

## Availability and choice

41. A provider is available when it is registered, `ready`, and every key of `requires` resolves non-empty (override or default). Providers enter the registry (`Metadata`, a `RwLock<HashMap<Namespace, Arc<dyn MetadataProvider>>>`) when they become `ready` and leave it when they fail, are disabled or uninstalled.
42. Order per kind: the setting `metadata.provider_order.<kind>` (a JSON array of namespaces). Default: `movie` and `series` to `[tmdb, tvdb]`; `book` to `[openlibrary, bnf, googlebooks, audible, audnexus]`; `album` to `[musicbrainz, fanarttv]`. An installed third-party provider is appended for its kinds; the admin moves it up. An absent or unavailable namespace is skipped.
43. `libraries."preferredProvider"` keeps its values and accepts a plugin namespace (it is validated as a namespace a provider serves, not `imdb`, `isbn`, `asin` or `file`, or a declared plugin namespace; a library form sends its stored value back unchanged and it is accepted even when its namespace failed to load: 400 `preferredProvider must be a provider namespace`; so are the `preferredProvider` of `PUT /media/:id`, `PATCH /media/seasons/:id` and `identify`); it goes first. `resolve(name)` is the named provider if available, else the first available of the kind's order, else none (no provider: rule 33). `fallback` and `person_fallback` are the next in the order. Per-field orders of books stay core constants indexed by namespace; a plugin namespace takes the place of its rank in the kind's order for each field, and the merge ignores a namespace with no provider.
44. The list routes (trending, popular, upcoming, genres, discover) call `list` on the first available provider of the kind's order (rule 42) that declares `lists` for it (`MetadataProvider::has_lists`). The route passes the list name and its parameters as the route reads them: `window` (`day`, else `week`) for `trending`; `genres`, `sort`, `voteGte`, `yearGte` and `yearLte` for `discover`, a key present only when the query has it, values verbatim (the provider parses them by `metadata.md` rule 14). Every other list takes none. The host validates the answer: a JSON array of objects, whatever the list (rule 14). The stale-while-error cache of `metadata.md` rule 17 is host state (`metadata/lists.rs`), keyed `(namespace, name, kind, params, locale, region)`, for `trending`, `popular`, `upcoming` and `genres`; `discover` is never stale-served (its key space is the caller's). With no provider for `lists` the answer is an empty list or page (PV.9).

## Bundled providers

45. The official providers are bundled: their signed archives are embedded in the server binary and installed at boot, so Fliks works offline on its first boot. At boot, before the plugins register, each embedded archive goes through the normal install pipeline (inspect, signature, promote) with `origin = 'bundled'` when no package of the id exists or the embedded version is newer than the installed one. A newer version installed from the catalog stays: no downgrade. An installed package of the id is marked `bundled` only when verified by an official key.
46. The daily auto-update (`plugins.md` rule 29) updates them between Fliks releases, with its gates. `plugins.auto_update = 'false'` does not stop a Fliks release from bringing its embedded version.
47. A bundled provider is disabled, not uninstalled: `DELETE` answers 409 `PLUGIN_BUNDLED` (the next boot would reinstall it). `FLIKS_PLUGINS_DISABLED=1` stops every plugin except the bundled ones (`plugins.md` rule 23): without providers Fliks has no metadata.
48. A bundled provider put `failed` by the plugin breaker (`plugins.md` rule 42) registers again by itself after 10 minutes (one try, then every 30 minutes). Meanwhile the core treats it as unavailable and `fallback` takes the next. A third-party provider keeps rule 42 as it is. The timer starts when the plugin's state turns `failed`; the attempt registers the package again under its lock, so an admin's restart in between is not undone. A restart that is still starting when its wait ends is retried at the next delay if it then fails.
49. A metadata call that arrives while its provider is `starting` (or handshaking) waits for `ready` at most 30 s, then fails `Upstream` 503 "provider starting"; any other state not `ready` fails 503 "provider <state>" at once. A lane that is full, a queue wait or a deadline that passes is 503 or 504 the same way, a trap `Upstream` with no status.

## Lane and outbound limits

50. A plugin with a `provider` block has a lane `provider` next to `core`: 0 to 8 shared instances, a queue of 64 calls. Background calls hold at most 7 instances at a time: one stays for an interactive call.
51. Queue wait at most 5 s for an interactive call and 60 s for a background one. Export deadline: 20 s interactive and 120 s background for `search`, `fetch-work`, `fetch-edition`, `fetch-person`, `person-credits`, `find-by`, `list`, `fetch-chapters`; 120 s and 600 s for `fetch-children`.
52. `fetch-children` takes an optional `season`: a provider answers that season alone, or every child when it cannot filter (the host picks by number). A `fetch-children` of a series issues its season requests in parallel inside one export (the SDK's `rt` waits on several responses with `wasi:io/poll`), bounded by the limiter and the 32 in-flight requests per plugin.
53. Memory per instance is the manifest's `memoryMb`; an instance idle for 10 minutes is removed (`plugins.md` rule 40).
54. The limiter stays in the host. The semantics of `Guarded::send` (breaker, token, `Retry-After` pause, backoff, quota, retries, interactive budget, slow-call log) are those of the outbound hook for a plugin with a `provider` block, using `fliks_domain::metadata::limiter` and `breaker` as they are, one pair per plugin **and per upstream host** (the host of each request URL, `Gates`), each built from `provider.limits`, so a host the plugin also calls (a popularity service beside the catalogue) has its own rate, pause and breaker, and an outage of it never pauses the other; the host is lower-cased without a trailing dot, at most 16 hosts get a gate of their own and the others share one more; a plugin's `rate-limited(retry)`, a spent quota and a checked record count against the host of the latest request of the export that gave them (concurrent exports never share it), a settings change ends every pause, and `provider-set-limits` sets every host: every outbound request of an export takes a token at the export's priority, the waiters of one priority in their order of arrival (a newcomer never takes the token an earlier waiter is waiting for); on 429 or 503 the host reads `Retry-After`, pauses the limiter and replays the request itself (body kept in memory up to 64 KiB, so GETs and small POSTs such as the TVDB login) with the current counters (3 retries, an interactive one only while its 5 s budget allows); the guest sees only the final response; one that reads a quota error in an upstream's body answers `rate-limited(retry)` and the host pauses the limiter for `retry` seconds. `requestTimeoutMs` bounds each request within the export's deadline.
55. A plugin, a third-party one included, cannot bypass politeness toward the upstream: there is one tested implementation instead of one per plugin, and the priority never leaves the host.
56. The hook decides on each answer. A 2xx resets the backoff; a 429 or 503 pauses the limiter (`Retry-After` as delta-seconds or an HTTP date, else the backoff step) and is replayed within rule 54's counts when the request body was sent whole and is at most 64 KiB, an interactive replay only if the pause fits the 5 s budget; any other status resets the backoff. The breaker (3 consecutive failures, open 30 s) sees one outcome per export request: the final status, or a transport failure; a final 429, or a 503 with `Retry-After`, is the upstream throttling (MusicBrainz answers its global limit so) and counts for nothing. A replay that cannot go (no token within the budget, spent quota) leaves the guest the last 429 or 503 it received.
57. The host answers in place of the upstream, with no request made: `429` with `Retry-After` in seconds when the daily quota is spent or a request would wait for a token or a pause past the time left to its export's deadline (an interactive request: past 5 s if that is sooner), so a pause never turns the export into a timeout the plugin breaker counts as a crash, `503` while the breaker is open. The body is `{"message": "<plugin id> <reason>"}`. A `rate-limited(retry)` the plugin answers after such a host answer is its echo and pauses nothing. A request whose retry hint the plugin read in the body returns `rate-limited(retry)`; the host then pauses the limiter for `retry` seconds, at most `limits.maxPauseSecs` (default 300, so a plugin that does not opt in is held to 5 minutes whatever it echoes; a provider with a daily window such as Metron declares up to 86400). A pause over 5 minutes is warned, and a change of the plugin's settings ends it. A `Retry-After` header and the backoff stay capped at 5 minutes (rule 56), and a pause longer than the time left to an export is answered `429` with the pause as `Retry-After`, never waited out.
58. The priority of an export is held in the Store the call runs in and applied to each of its requests. A plugin route call (`http`, pre-roll included) is interactive: someone waits for its answer, so it gets the whole rate and the 5 s budget of rule 54, and work that may wait for the rate goes to a job or a scheduled task. Any other request outside an export (`hello`, `health`, events, jobs, scheduled tasks) is background. `requestTimeoutMs` (default 10000) bounds the connection and the response headers of each attempt; the body is bounded by the between-bytes timeout.
59. `FLIKS_PLUGIN_UPSTREAM_OVERRIDE` is compiled only with the `parity` cargo feature (rule 40, `config.md`). The hook rewrites the scheme, host and port of a request whose host is listed to the target's, prefixing the target's path, and vets the target as an internal address; the `Host` header is the guest's.

## Music records

The `album` kind declares `search`, `work`, `children`, `edition`, `person`, `credits` and `findBy`. `person-credits` takes no kind, so a provider that declares `credits` under `album` declares it under no other kind: the manifest check refuses the pair (`PLUGIN_BAD_MANIFEST`) until the call takes a kind. Its records, their checks and the bounds of every key are `music.md` rules 18-24 (`fliks_domain::music::provider`); `musicbrainz`, `isrc`, `spotify`, `deezer` and `fanarttv` are core namespaces (`music.md` rule 15), declared by official plugins like `openlibrary`.

## Comic records

The `comic` kind declares `search`, `work` and `children` (`comics.md` rules 38-45 use them). A comic provider is a plugin like any other: none is bundled, none has a default key, and the credentials are the admin's own settings (`requires`). Record keys outside the lists below are ignored. The host checks them when it receives them, on top of rule 14.

60. A `search` hit and the `work` record share the book keys (`ids`, `externalId`, `title`, `overview`, `year`, `posterUrl`, `publisher`) and add `volume` (the number printed on the cover, an integer from 0 to 9999 or null), `issueCount` (an integer of at least 0 or null), `mediaType` (`"comic"` when present) and `sourceUrl` (the volume's page at the provider, an `https` URL). `externalId` (1 to 128 characters, normalised by rule 28) and `title` (1 to 500 characters after trim, no control character) are required; `posterUrl` must be an `https` URL (the image store downloads it, rule 32, and only its local copy is ever stored), and a `publisher` or `overview` with a control character (line breaks and tabs are allowed in an `overview`) is dropped like one out of range; `year` outside 1 to 9999, a `publisher` over 255 characters, an `overview` over 10 000 characters, a `volume` or `issueCount` out of range or a `sourceUrl` that is not an `https` URL of at most 2048 characters is dropped from the record, not the record. A `work` record that fails a requirement is a malformed record (rule 14: `Upstream` 502, counted by the breaker).
61. A `children` answer is the issues of the volume, one object each: `number` (the printed label, 1 to 255 characters after trim, no control character), `sortNumber` (a finite number with `|x| < 10000`, rounded to 2 decimals and so inside the grammar of `fliks_domain::comics::name::number` (`comics.md` rule 31), the keys ingest writes: the range from 100000 is the one ingest gives to unnumbered files), `kind` (`issue`, `annual` or `special`; absent is `issue`), `title` (at most 500 characters, longer is cut), `releaseDate` (the store date, `YYYY-MM-DD` and a real date, or null). `coverDate`, `storeDate`, `externalId` and `posterUrl` of an issue are read by nobody: the model has no column for them. A child that breaks a rule above (an unknown `kind`, a `sortNumber` that is missing, not a number, not finite or out of range, a label that is empty or too long, a `releaseDate` that is not a real date) is dropped and the host warns once per answer with the number of children dropped and the first reason, never a value. Children that share `(kind, sortNumber)` (`1.1` and `1.10` sort alike) keep the first, in the order the provider listed them, and the host logs the number of repeats. A list answer of more than 10 000 children is refused whole (rule 14).
62. The checks run in `fliks_domain::comics::provider` (`work`, `issues`), pure functions over the JSON; `PluginProvider` runs them on every `comic` answer and hands the rest of the host the surviving, normalised children (`number`, `sortNumber`, `kind`, `title`, `releaseDate`), and the metadata routes and the import run the same functions again on what they read from a snapshot, so a record that does not come from a plugin is held to the same rules.
