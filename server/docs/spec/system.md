# Spec: system

Auth, CASL and error-body rules are in `auth.md` (cited as "auth rule N"); jobs and the `commands` table are in `scheduler.md`.

Scope: the 11 routes of the system controller: health, restart, version, update, stats, backup create/list/restore/download/delete, logs. Specified elsewhere and not repeated: `/api/system/liveness`, `/api/system/events` and `/api/system/activity` (`events-hub.md`), `/api/system/streams*` and `/api/system/transcode-cache*` (`playback-info.md`), `/api/system/qoe/*` (`qoe.md`). The routers own disjoint paths, so no 405 can arise.

## Routes

Every route needs authentication (JWT or API key). The backup routes need `manage:all`; every other route except `version` is satisfied by `settings.access` or `manage:all` (auth rule 25: `Create`, `Read`, `Manage` on `Settings` all come from `settings.access`). Success statuses: 201 for `POST`, 200 otherwise.

| Method path | Auth (extractor + policy) | Request (fields, constraints) | Response (fields, types, nesting) | Errors (status, message/code) | Side effects |
|---|---|---|---|---|---|

Client use: status page, restart, backups page, download link (an `<a href target=_blank>`, so cookie auth only), logs, dashboard, desktop updater. The error interceptor treats `/api/system/health` failures as "server down". Clients show `error.message` of a failed backup/restore, so the tool's last stderr line is part of the contract. The backups page is admin-only: other `settings.access` callers get 403.

## Rules

### A. Auth and shape

1. The restart policy is `settings.access` in effect; the five backup routes (create, list, download, restore, delete) need `manage:all`, because a dump holds every password hash, refresh-token hash and secret setting in clear (settings redaction would be bypassed by anyone with `settings.access`, and a restore can overwrite `users`). `GET /version` needs no permission but is still authenticated, and `scope:'stream'` tokens are refused (401).
2. Every handler's first line is its permission check (auth rule 27). 403 body is `{"message":"Forbidden resource","error":"Forbidden","statusCode":403}`. Error bodies of the 400/404/500 rows are `{statusCode, message, error}` (bootstrap rule 5): 500 `error` = `Internal Server Error`.

### B. Health and restart

3. `health` = `{version, uptimeSeconds: floor(uptime), database, installedPlugins, runningPlugins, restartSupervisor, confPersistent, dataPersistent, dbSuperuser, dbLimited, dbGaps}`. `version` = the product version (rule 9). `uptimeSeconds` = seconds since the `fliks-server` process started.
4. `database`: `SELECT 1`; ok → `{name:'PostgreSQL', ok:true}`, failure → `{name:'PostgreSQL', ok:false, message:<driver error message>}` (`message` absent when ok). With the database down `health` still answers 200, with `ok:false` and both counts `0`.
5. `installedPlugins` = `SELECT count(*) FROM plugin_packages`; `runningPlugins` = same with `WHERE enabled = true` ("enabled", not necessarily reachable; capability health belongs to the plugin).
5b. `confPersistent` is false once a secret file was placed in the temp dir or kept in memory (`auth.md` rule 2); `dataPersistent` is false when the data dir fell back to the temp dir. Both are true in a normal install.
5c. `dbSuperuser` is true when the connected role is a PostgreSQL superuser (rule 41). `dbGaps` lists what a non-superuser role lacks, from `create_role`, `create_database`, `public_owner`, `foreign_objects`, `advisory_locks`, `plugin_roles`; `dbLimited` is true for a non-superuser role on PostgreSQL older than 16, where `CREATEROLE` can still reach the host. Never an error: a gap that breaks a migration fails there.
6. `restartSupervisor` (health) and `supervisor` (restart) come from one detector, first match wins: env `FLIKS_SUPERVISED` non-empty (the string `0` counts) → `'supervisor'`; env `pm_id` non-empty → `'pm2'`; env `INVOCATION_ID` non-empty → `'systemd'`; `/.dockerenv` exists → `'docker'`; none → `null`. Rust appends a fifth rung, env `FLIKS_ENGINE_TOKEN` non-empty (set only by `fliks_engine::supervise`) → `'supervisor'`, so a bare-metal install run under the engine can restart.
7. `POST /restart`: no supervisor → 400 `No process supervisor detected`, no side effect. Else warn `Restart requested (supervisor: <name>)` and answer 201 `{ok:true, supervisor}` before exiting.
8. Exit mechanics: 300 ms after the response (so it flushes), begin the normal graceful shutdown (drain), then exit with code 1 from `fliks-server` itself; the parent `fliks-engine --supervise` respawns it with its backoff (base 1 s). Never signal PID 1 (it is the engine, which must stay up to serve the 502 window and the resolver). The exit code is non-zero so a bare systemd `Restart=on-failure` also restarts.

### C. Version and update

9. `version` is `env!("CARGO_PKG_VERSION")` of the workspace; `.github/release-please-config.json` bumps `server/Cargo.toml` and `Cargo.lock`.
10. `UpdateStatus` = `{currentVersion: string, latestVersion: string|null, updateAvailable: bool, releaseUrl: string|null, releaseNotes: string|null, publishedAt: string|null}`, all keys always present. (a) Env `FLIKS_DISABLE_UPDATE_CHECK` trimmed + lower-cased in `1|true|yes` (read on every call): `latestVersion` and the other nullables `null`, `updateAvailable:false`, no outbound request. (b) A cached success younger than 6 h is returned as is. (c) Else `GET https://api.github.com/repos/<FLIKS_GITHUB_REPO, read once at start; unset → fliks-app/fliks, set-but-empty kept as is>/releases/latest` with `Accept: application/vnd.github+json`, `User-Agent: fliks-server`, 15 s timeout; non-2xx → warn `GitHub release lookup failed: HTTP <status>` and the all-null fallback; transport error or bad JSON → warn `GitHub release lookup error: <message>` and the fallback; `draft:true` → fallback. (d) Success: `latestVersion = tag_name ?? name ?? null` (raw, `v` prefix kept), `releaseUrl = html_url ?? null`, `releaseNotes = body ?? null`, `publishedAt = published_at ?? null`, `updateAvailable = isNewer(latestVersion, currentVersion)`. Only a result with a non-null `latestVersion` is cached (a failure retries on the next call); no single-flight. The fallback is still 200.
11. `isNewer`: parse each side as `v?` prefix stripped, cut at the first `-` or `+`, split on `.`, each part `parseInt(.,10)` (digit prefix: `3rc1` → 3); the side is trimmed and the `v` match is case-insensitive (`V1.2`); any part NaN or an empty side → not newer. Compare part by part, missing parts = 0; only a strictly greater part decides. Equal parts: newer only when `latest` has no `-` suffix and `current` has one (`5.1.0` vs `5.1.0-beta.1`); `+` build metadata is not a suffix. `1.2.x` is unparsable (false).

### D. Stats

12. `movies` and `series` = `SELECT type, count(*) FROM media GROUP BY type` folded through the kind registry, zero-filled (`media-details.md` rule 10), `pendingRequests` = `SELECT count(*) FROM requests WHERE status = 'pending'`.
13. `diskSpace`: libraries `ORDER BY name ASC` (+ `id ASC`) with a folder; per folder (`position`, `id` order) `{path: the folder path as stored, label: the library name, `<name> (<last segment of the path>)` for a folder after the first (`label` of the library is always null), freeSpace: f_bfree * f_bsize, totalSpace: f_blocks * f_bsize}`; on a `statfs` error `freeSpace` and `totalSpace` are `-1` (JSON numbers; same semantics as `libraries.md` rule 6, run on the blocking pool). Absolute paths are exposed here by design: the route needs `settings.access`, the audience allowed to see server paths.

### E. Backups

14. Backup dir = `<data_dir>/backups` (`paths::data_dir()`, `FLIKS_DATA_DIR` with the writable-or-tmp fallback of `config.md`), created on first backup only. `GET /backups` lists regular entries ending `.dump` or `.sql` (case-sensitive), `{filename, size, date: mtime ISO}`, newest first by `date` string then `filename DESC`; a missing dir → `[]`.
15. Name validation (create-by-name routes: download, delete, restore): must match `^[A-Za-z0-9_.-]+\.(sql|dump)$` (ASCII `\w`, so use the explicit class, not Rust's Unicode `\w`; `$` is end of input only) else 400 `Invalid backup name "<name>"`; then the file must exist in the backup dir else 404 `Backup "<name>" not found`. The check runs before any path join, so no separator or `..` segment can pass (`..sql` is a legal, harmless name).
16. Download: 200, `Content-Disposition: attachment; filename="<name>"`, `Content-Type: application/octet-stream` (`application/sql` for a `.sql`), `Content-Length`, weak `ETag`, `Last-Modified`, `Accept-Ranges: bytes` and `Cache-Control: private, no-store`, `Range` supported; streamed, never buffered. The headers are pinned in the parity scenario.
17. Create: `filename = fliks-backup-<ISO-8601 UTC timestamp with milliseconds, every ':' and '.' replaced by '-'>.dump` (e.g. `fliks-backup-2026-10-16T02-00-00-123Z.dump`); mkdir -p the dir; run `pg_dump <connection args> -Fc -B` (the custom archive: the restore picks what it replays, rule 36; `-B` leaves the large objects out, which no schema filter reaches and which the core pass would replay under any role's own) with stdout = `<filename>.partial`, created mode `0600`, renamed to `<filename>` once `pg_dump` exits 0 (so no listing or prune sees a cut file) in a `0700` directory; on any failure close and delete the partial file and rethrow; answer `{filename, size: bytes of the file}`. Log `Creating backup: <filename>` then `Backup created: <filename> (<size> bytes)`. A plugin schema the core login cannot read is left out with `--exclude-schema` and named in `pluginsSkipped` (a warn log too): on a core that is neither superuser nor `BYPASSRLS`, a schema with a `FORCE ROW LEVEL SECURITY` table, found by a catalog query before the dump; and, once, a schema whose name the failed `pg_dump` printed (a plugin set FORCE between the query and the dump), after which the dump runs again. One plugin never stops every core backup; its data is not in the archive, so a restore leaves that plugin with an empty schema. The nightly `.sql` files of earlier builds stay listed, downloadable, pruned and restorable (rule 23).
18. Tool runner (`pg_dump`, `psql`): spawned without a shell, arguments as a vector, stdout to the file or discarded, stderr captured. `ENOENT` → 500 `<cmd> is not available on this server`; another spawn error → 500 `<cmd> failed: <message>`; exit code ≠ 0 → log `<cmd> exited with <code>: <full stderr>` and 500 with the last non-empty stderr line (else `<cmd> exited with code <n>`). No timeout applies (a dump of a large library takes minutes); the child is killed and the partial file removed when the server shuts down. The shipped tools are PostgreSQL 18's: creating a backup works against servers 15 to 18, restoring a `.dump` is supported on 17 and 18 only (rule 36); the restore tests run on both in CI.
19. Connection args and secret: `-h <DB_HOST>`, `-p <DB_PORT>`, `-U <DB_USERNAME>`, `-d <DB_NAME>` (defaults `localhost`, 5432, `fliks`, `fliks`); the password travels in `PGPASSWORD`, never in argv; the child inherits the rest of the environment. All five values come from the one parsed `Config` the pool uses (default password `fliks`).
20. Retention (`Backup` job only, `scheduler.md` rule 22): keep the newest 7 of `list_backups()`, delete the rest, return the removed names; the direct `POST /backup` never prunes. The prune is shared with rule 33, whose `v<version>` dumps get one exception; for `fliks-backup-*` files nothing changes.
21. Delete: rule 15 validation (so a missing file is 404), `rm -f`, log `Backup deleted: <filename>`, answer `{ok:true}`.
22. Restore body: no DTO, the handler reads `body.filename` of a plain object. `{}` → 400 `Invalid backup name "undefined"`; any non-string `filename` (including a one-element string array) → 400 `Invalid backup name "<String(value)>"`; unknown extra keys are ignored. Flow: validate (rule 15), refuse what needs no database (rules 23, 24 screen, 39: nothing is stopped for a refused file), warn `Restoring backup: <filename>`, replay (rules 23-24 for a `.sql`, rules 36-38 for a `.dump`), log `Backup restored: <filename>`, answer 201 `{pluginsNotRestored, restarting}`. Rust also refuses a restore while the subtitle tick or a plugin job or scheduled call holds a `jobs::Running` claim (`subtitles.md` rule 55, `plugins.md` rules 50, 55), and stops every plugin before the replay and registers them again after it (`plugins.md` rule 44), unless the process restarts (rule 25); the restart is scheduled by the restore task itself, so a client that went away cannot leave the plugins stopped.
23. Plain `.sql` files (earlier builds): read the file line by line; a line `CREATE SCHEMA plugin_...` or one matching `^GRANT .+ TO (plugin_[a-z0-9_]{1,56}|fp_[0-9a-f]{8}_[a-z0-9_]{1,51});$` means the file holds plugin data, and the restore answers 409 `BACKUP_HAS_PLUGIN_DATA: ...` before anything runs: replaying it would run the plugins' CHECK constraints and functions as the core login. A plain file without plugin data restores as rule 24 says. No role is created.
24. Replay (a plain `.sql`, or the core script of rule 36): `psql <connection args> --single-transaction -v ON_ERROR_STOP=1 -f <abs path>`: one transaction, rolled back on the first error (without `ON_ERROR_STOP` psql would report success after skipping failed statements). The command runs with `-X` (no `~/.psqlrc`) after the file is screened: a line outside a `COPY ... FROM stdin;` block that starts with a backslash (except `\restrict <key>`, `\unrestrict <key>`, `\.`) is 400 `Backup contains psql meta-commands`. The screen is best effort, not a SQL lexer: a meta-command after `;` on the same line, or text inside a multi-line string literal, is not seen; it guards against a stray file in the directory, not a hostile one (no route uploads a file). Inside the replay's transaction, `public` and every `plugin_*` schema are dropped first and `public` is recreated, so the restore replaces the whole database content (also plugin schemas the dump lacks) and an older dump does not fail on objects a later migration added. The server keeps serving during the replay; `DROP TABLE` waits for in-flight queries and the pool's queries then wait on the lock.
25. Post-restore steps: refuse (409 `A command is running`) while any `commands` row is `queued`/`running` or this process runs a job, and hold a `Restore` claim in the in-process running set for the whole restore (no cron tick, manual trigger or second restore starts meanwhile); after a successful replay and the plugin passes run the 4.x ledger adoption and the pending sqlx migrations so an older dump gets the current schema, and mark every `queued`/`running` row failed (a scheduled backup dumps its own `running` row). A migration failure (a dump newer than this binary, rule 39 aside) answers 500 with that error; the plugin passes have run by then, so no plugin schema stays empty unreported. A success under a process supervisor (rule 6) answers `restarting: true` and restarts the process as `POST /restart` does (rule 8), so the settings, provider order and engine configuration the dump replaced are read again; without a supervisor `restarting` is false, the plugins register again in place, and the client asks the admin to restart the server.
36. Restoring a `.dump` (`restore.rs`) is supported on PostgreSQL 17 and 18: the shipped `pg_restore` is 18's and sends `SET transaction_timeout`, which servers before 17 reject. On an older server the restore answers 400 `Restoring a backup needs PostgreSQL 17 or later (this server runs <major>): ...` (key `system.restore_needs_pg17`, param `version`) before anything is stopped or replaced; the app itself runs on 15 and later, and a backup can still be created there. `pg_restore -l` lists the archive; the plugin schemas are the `SCHEMA` lines matching `^\d+; \d+ \d+ SCHEMA - (plugin_[a-z0-9_]{1,56}) ` (`pg_restore` puts a newline of an object name on the same line, so no name forges a second entry). The core pass is `pg_restore --no-owner --no-privileges --no-comments -N <each plugin schema> -L <list without the casts naming a plugin type> -f <private file>` (a cast has no schema, so no `-N` reaches it; core has no `COMMENT` and a plugin schema comment is plugin text), screened as rule 24, then replayed by rule 24 as the core login. The plugin schemas come back empty and core-owned, and a plugin cast is not restored.
37. Plugin passes, one per plugin schema of the archive, each under the per-id lock (`plugins.md` rule 44; none offline): `provision` (the `coreRefs` of the restored package, none without a package row), then `pg_restore -n <schema> --no-owner --no-privileges --single-transaction --exit-on-error -L <list without that schema's `FK CONSTRAINT` lines>` logged in as the plugin's role with its derived password, so every object the plugin made is created, owned, and its constraints and policies run, as that role. The held-back foreign keys are replayed one by one on the same login, after the data; one that references `public` (a dump from before `plugins.md` rule 35 forbade them) is skipped with a warn, since a plugin cannot create it. A schema without a package row gets `NOLOGIN` and its orphan comment back (`plugin_db::keep_orphaned`). The passes read only `plugin_packages.manifest` and write only `enabled` and the status columns, which every dump holding a plugin schema has, because they run before this build's migrations on the restored table (`fliks-server restore` never runs them). A registered plugin with `database.schema` whose archive holds no schema (rule 17 left it out) is disabled the same way and listed in `pluginsNotRestored`, since the replay dropped its live schema.
38. A plugin pass that fails (a CHECK the rows break, a policy, a missing right) leaves its schema empty (one transaction, or dropped and provisioned again when a later key fails), disables the package (`enabled = false`) with `statusReason = restore-failed: <last stderr line>`, and is listed as `{schema, message}` in `pluginsNotRestored`; the core restore stands and the other plugins restore. The client shows one translated message naming each schema and its text, as text.
39. Version guard: while screening, the rows of `COPY public._sqlx_migrations` are read (the column named `version`); a version this build has no migration for answers 400 `This backup comes from a newer Fliks (migration <n> is unknown to this version)` before anything is replayed. At boot, a database holding a migration this build does not know stops with a message saying it was migrated by a newer version and how to put back a backup, instead of sqlx's raw `VersionMissing` text.
40. `fliks-server restore <file>` runs rules 36-38 on any `.dump` or `.sql` path (the pre-migration dumps of rule 32 included) with the server stopped: it refuses while another session holds the instance lock (a session advisory lock on `hashtext('fliks:instance')` that the running server keeps on its probe connection for its life, so a restore started from another container is seen; the restore holds it too), takes no per-id lock, and never runs `db::migrate`, so an older image still boots after a rollback; the next boot of whichever image migrates, and sweeps the `running` command rows. It exits 1 when a plugin schema was not restored, after logging each. This replaces the manual `pg_restore --clean` of rule 32, which would replay the plugin constraints as the core login.
41. `fliks-server db-role [--print]` gives the application a non-superuser role (`DB_USERNAME`, shipped as `fliks_app`; `DB_PASSWORD` set, not `fliks`, not the admin's). The admin is `DB_ADMIN_USERNAME`/`DB_ADMIN_PASSWORD`, read by this command only. The role is `LOGIN NOSUPERUSER NOCREATEDB CREATEROLE NOREPLICATION NOBYPASSRLS` with `CONNECT`, `CREATE` and `TEMPORARY` on the database (`CREATE` is enough for the trusted extensions `pg_trgm` and `unaccent`; migrations use temporary tables, and `template1` withholds `TEMPORARY` from `PUBLIC`), owns `public` and every core object, administers the plugin roles of the database (`fp_<oid>_*`, and the 4.x `plugin_<id>` roles that have a schema of that name here), and alone may take the `pg_advisory_*lock` functions (revoked from `PUBLIC`). It first logs in as the role: when nothing is missing it exits 0 without the admin. Else, as the admin (a superuser; retried 60 s while Postgres starts): one transaction for the role, grants and lock functions, then one `ALTER ... OWNER` per object, each committed alone under `lock_timeout` 10 s (a busy table fails the run, a rerun finishes it); never `REASSIGN OWNED` (the bootstrap superuser is pinned). Objects owned by plugin roles and members of extensions stay. `--print` writes the same two statements with a SCRAM verifier, for a DBA to run one by one. Rollback is an environment change: a superuser ignores ownership. A migration may create only a trusted extension, with `IF NOT EXISTS`, and no other superuser-only statement.
42. The server's pool sets `lock_timeout` 60 s: a statement waiting on an advisory, row or table lock fails instead of stalling. Plugin pools do not carry it.

### F. Logs

26. Ring buffer: capacity 2 000 entries, split by level (error 500, warn 500, log 750, debug 250), so a flood of one level never evicts another `{timestamp: ISO-8601 ms Z at push, level, context, message}`, oldest of the same level dropped first; `level` in `log|warn|error|debug`; `error(message, trace, context)` stores `message + "\n" + trace` when a trace is given. Memory only, lost on restart.
27. `GET /logs`: copy the buffer, filter `level` (exact, case-sensitive; an unknown value → `[]`; empty string = no filter), filter `q` (lower-cased substring of `message` or `context`; empty = none), reverse (newest first), then cut to `limit`: absent or empty → 200; else `parseInt(limit, 10)` (leading whitespace and sign, digit prefix); a result that is NaN, 0 or negative means no cut (up to 2 000). A `limit` that is not a canonical integer → 400 (shared with `scheduler.md` rule 20); `0` and negative integers keep "no cut".
28. Feed, `tracing`: a subscriber layer of `fliks-server` pushes every event at ERROR/WARN/INFO/DEBUG (`error`/`warn`/`log`/`debug`; TRACE is dropped) with `context` = the event target without the `fliks_server::` prefix and `message` = the `message` field followed by ` key=value` for each other field. Debug events exist only when `RUST_LOG` enables them (default INFO). The layer is installed beside the stderr writer of `main.rs`, which keeps printing (ANSI colours only on a terminal). A panic hook logs every panic at ERROR (`panic: <text>`, thread and location), and a panic in a handler answers 500 `{statusCode: 500, message: "Internal server error"}`; `AppError::internal` logs its message at ERROR.
29. Output of child processes (plugins) is not in the ring; it goes to the container's stdout/stderr, inherited through `fliks_engine::supervise`.
30. Hygiene: the ring is readable with `settings.access` and mirrored on stderr, so no entry may carry a credential. HTTP trace events log the method and path only, never the query string (stream tokens and API keys travel there); an error from `reqwest` is logged with its URL removed (`reqwest::Error::without_url`); the `Authorization`, cookie and `PGPASSWORD` values are never fields.

31. A `pg_dump` newer than the server major, or a server newer than the client tools, makes `pg_dump` abort; the Dockerfile installs PGDG `postgresql-client` and the tool's message surfaces as the 500 text.

### G. Pre-migration backup

31. At boot (`serve` and the `migrate` subcommand), before any migration runs, the server checks for pending migrations: some embedded sqlx migration is absent from `_sqlx_migrations` (or, on a 4.x database not yet adopted, from the TypeORM ledger). With none pending, or on an empty database (no table in `public`), nothing is dumped. Tests and `restore` call `db::migrate` directly and never dump.
32. A pending set triggers a dump (rule 17's tool runner and modes, but the same `pg_dump -Fc` as rule 17, restored with `fliks-server restore <file>`, rule 40) into `<data_dir>/backups/pre-migration/` as `fliks-pre-migration-v<version>-<ISO timestamp as rule 17>.dump`, `<version>` being the newest applied migration version (the newest TypeORM ledger timestamp before adoption, `0` when none). The folder is separate, so the rule 14 listing, the download and restore routes and the rule 20 prune never see these files. Log `Creating backup: <filename>` and `Backup created: <filename> (<size> bytes)`, with the folder path.
33. Retention: after a successful dump keep the newest 3 files of the folder and delete the rest (rule 20 logic), except the oldest file carrying the same `v<version>` as the newest file, which is never deleted: a migration that keeps failing writes a dump per restart, and the oldest of them is the only one holding the database as it was before the pending chain began (later ones may hold a half-migrated state). The folder therefore holds up to 4 files; dumps of older versions are pruned as usual, and the exception moves on once a later version is dumped.
34. A failed dump (rule 18 errors, including a missing `pg_dump`) aborts the boot with `pre-migration backup failed, migrations not applied: <message> (set FLIKS_SKIP_PRE_MIGRATION_BACKUP=1 to skip it)`; no migration runs and the partial file is removed. Each boot deletes the `*.partial` files a killed process left in the backup folder and in its pre-migration folder, before the skip flag is read.
35. Escape hatch: env `FLIKS_SKIP_PRE_MIGRATION_BACKUP` in `1|true|yes` (trimmed, case-insensitive) skips the step with a warning. It is an env var, not a setting, because it is read before the database is migrated, so the `settings` table may not exist or be readable. The parity runner sets it (no `pg_dump` guaranteed on the runner).

## SQL

- `SELECT 1` (health).
- `SELECT count(*) FROM plugin_packages` and `... WHERE enabled = true`.
- `SELECT count(*)::int FROM media WHERE type = 'movie'` (and `'series'`); `SELECT count(*)::int FROM requests WHERE status = 'pending'`.
- `SELECT l.id, l.name, df.path FROM libraries l JOIN library_default_folders df ON df."libraryId" = l.id ORDER BY l.name ASC, l.id ASC`.

## Open questions

- Does `restart` stay at `settings.access` (rule 8) or move to `manage:all` with the backups? Nothing in the specs argues for a change, so it stays until answered.
- Restart under the engine (rules 6, 8): the fifth detector rung reports `'supervisor'` instead of `null` on bare-metal engine installs, and Docker keeps `'docker'` because `/.dockerenv` is checked first. Confirm exiting `fliks-server` (not PID 1) is the intended restart in Docker, and that macOS (no `FLIKS_SUPERVISED`) should also report `'supervisor'`.
- `uptimeSeconds` is the `fliks-server` process uptime. Acceptable?
- After a restore, in-memory state (cached ACL / settings reads, engine config revision, SSE connections of deleted users) is stale: restart the process after a restore (`exit(1)` as in rule 8) instead of keeping the server running? It would change the restore UX (a 60 s outage) but remove a class of stale-cache bugs.

## Boot and shutdown

The listener is bound before the database probe, the pre-migration dump and the migrations. Until the app router is published, `GET /api/system/liveness` answers 200 and every other route answers 503 `{"message":"errors.starting"}` (`Retry-After: 5`; the client treats it as an unreachable server, no toast on a GET), so a healthcheck or an orchestrator never sees a long dump as a dead process; readiness keeps its meaning: a host app waits for `/api/system/health` to stop answering 503. Liveness stays 200 for the whole of every boot attempt, a failing one included (the process exits when an attempt fails, and the supervisor restarts it), so a healthcheck restarts a hung process only once the app is published. A stop signal during boot ends the process. After the signal the open connections get 15 s to drain (the engine waits 25 s for the server and Docker 30 s for the container); the buffered QoE samples, the pending pushes and the plugins are then flushed whatever is still open.
