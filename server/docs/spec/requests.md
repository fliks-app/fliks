# Spec: requests (+ auto-approval rules, request lifecycle)

Scope: the 16 requests and auto-approval-rules routes, the auto-approval matcher and the request lifecycle hooks. Notification sending is in `notifications.md` (cited "notif rule N"); auth, CASL, error bodies in `auth.md` ("auth rule N"); the bus in `events-hub.md` ("hub rule N"). Library access (`getAccessibleLibraryIds`, `resolveSoleLibrary`) is the `libraries` spec; TMDB, the image store, `importFromTmdb`, `remove` and `applyMonitoredForRequestScope` are called in-process.

The media-side services (TMDB facts and art, `resolveImportTarget`, `importFromTmdb`, media removal, notifications) are free functions in `requests::services` (`server/crates/server/src/requests/`); the media write side calls the hooks of `requests::Lifecycle` (rule 42).

## Routes

23 routes in total: 11 requests + 5 auto-approval rules here, 7 notifications in `notifications.md`. Every route is authenticated and policy-checked. `scope:'stream'` tokens are rejected by the extractor (auth rule 12). Guards run before validation (auth rule 17). POST = 201, DELETE = 200 (empty body). Declaration order matters: `title-state` is declared before `:id` and `comments/:commentId` is a 3-segment path.

Shapes used below. `PublicIdentity` = `{id: number, username: string, avatar: string|null}` (rule 6). `RequestRow` = `FliksRequest` JSON (rule 5). `RuleRow` = `{id, createdAt, updatedAt, name: string, enabled: boolean, criteria: object}`.

## Rules

### A. Policies and visibility

1. CASL for requests: `requests.create` grants `create` on `FliksRequest`, `read` and `update`/`delete` conditioned (`{userId: self}`, update/delete also `{status:'pending'}`); `requests.manage` grants `manage` (every action incl. `approve`, `decline`). Guards use class-level checks, so conditions never bite at the guard: every `requests.create` holder passes `Read`/`Update`/`Delete`/`Create`; only managers pass `Approve`/`Decline`. Per-instance authorisation is done in the service (rules 2-4).
2. "Manager" in the service = `ability.can(Action.Manage, FliksRequest)` on the caller's ability (`requests.manage` or `manage:all`). "Super-admin" = `isAdmin` or `permissions` contains `manage:all`.
3. Owner-or-manager gate (`findOne`, `addComment`, `getComments`, `removeComment`, `update`, `remove`): a non-manager who does not own the request gets a bare `ForbiddenException()` (body `{"message":"Forbidden","statusCode":403}`, auth rule 15). Comments: `removeComment` compares `comment.userId` (the comment's author), not the request owner.
4. Library gate `assertCanAccessRequestLibrary(user, request.libraryId, request.userId)`: `libraryId == null` passes; super-admin passes; the request's owner passes; otherwise `libraryId` must be in `getAccessibleLibraryIds(user)` else 403 `You do not have access to this request's target library`. Runs in `findOne` (after the owner gate), `approve`, `decline`, `addComment`, `getComments`, `removeComment` (only when the comment's request still loads). Order in `approve`/`decline`: manager check (bare 403) → row lookup (404) → library gate → status check (409).
5. `RequestRow` columns (table `requests`): `id`, `createdAt`/`updatedAt` (ISO), `mediaType`, `kind` (`'add'` default), `tmdbId`, `title`, `status`, `declinedReason` `string|null`, `seasons` `number[]|null` (jsonb; `[]` and `null` both mean "whole title"), `posterUrl`/`fanartUrl` `string|null`. Enums: status `pending|approved|declined|processing|available|failed|removed` (`failed` is only written by the Seerr importer; `removed` = was `available`, then its media left the library or was unmonitored), kind `add|delete`, mediaType `movie|series`. Relation ids (`userId`, `approvedById`, `qualityProfileId`, `languageProfileId`, `libraryId`, `mediaId`: `number|null`) are present on rows loaded from the DB and also present on the rows `POST`, `PATCH` and decline return; only a comment's embedded `request` has none (rule 27). The table names the title by `provider` and `"externalId"` (text), next to `"mediaType"`, under the `CHECK`s of `media_external_ids` (`external-ids.md` rules 2, 3); the wire's `tmdbId` is `"externalId"` as an integer when `provider = 'tmdb'`, which is every row the API writes.
6. Embedded users are always projected to `PublicIdentity` (`user`, `approvedBy`, each `comments[].user`): `approvedBy` null when unset. Nothing else of the account (email, permissions, quotas) leaves the server. Every route returning a request goes through `projectEmbeddedUsers` (or builds the projection in the query).
7. `GET /api/requests/:id` loads `relations: ['user','approvedBy','media','comments','comments.user']` via the FK: `media` is the full `Media` JSON of the linked row including its eager relations (`library`, `qualityProfile`, `languageProfile`, `metadata`; no files or seasons) and the `path` getter (`@Expose`, `library.path` joined with `folderName`, or null), `searchVector` excluded (`select:false`); `comments` have no ORDER BY (physical order). The list and `approve` use rule 8 instead, so the same title has two different `media` shapes. `media.path` and `media.library.path` are present only for callers who can manage libraries (`paths_visible`), omitted otherwise.
8. List and `approve` join the library media holding the request's `(mediaType, provider, externalId)` in `media_external_ids` (lowest media id first, `external-ids.md` rule 6), not by the request's FK, so partial-library titles surface a `media` object; the FK `mediaId` stays as stored. Media is mapped from the QueryBuilder join: the entity's own columns only (no eager relations, so no `library`/`qualityProfile`/`metadata` keys and `path` serialises as `null`); `media.type = r."mediaType"`, both `text`. A request only names a title by a provider whose ids are unique per kind (`ExternalProvider::is_unique`, TMDB for `movie` and `series`), so there is at most one match.

### B. List and title state

9. `GET /api/requests` scoping: non-manager → `r."userId" = caller` and the `userId` query filter is ignored; manager → no user scope, `userId` filter applies; a manager that is not a super-admin additionally sees only `(r."libraryId" IS NULL OR r."libraryId" IN (accessible ids))`, with `[0]` substituted when the accessible set is empty. Filters are AND-ed; `tmdbId`/`userId` are applied only when truthy (`0` is ignored). `tmdbId` filters `provider = 'tmdb'` and `"externalId"`. Pagination `OFFSET (page-1)*limit LIMIT limit`; `total` is the unpaginated count. Order `createdAt DESC, id ASC`.
10. `title-state` aggregates ADD requests in `pending|approved|processing|available` for the title (`mediaType`, `tmdb`, the query's `tmdbId`) across all users, `ORDER BY createdAt ASC`, never exposing requesters: `wholeSeriesRequested` = series with any active request whose `seasons` is null/empty; `requestedSeasons` = sorted union of all active `seasons`; `requested` = (series: `wholeSeriesRequested`; movie: any active). Profiles: for series only, `existingSeriesProfiles` (rule 12); `profilesLocked = locked !== null`; movie always `profilesLocked:false`, both ids null. Delete-kind rows are ignored.

### C. Create

11. Order of checks in `create` (ADD kind): (1) `checkQuota` (rule 13) → (2) duplicate guard (rule 12a) → (3) explicit `libraryId` access (non-super-admin: must be in accessible ids, else 403 `You do not have access to the selected library`) → (4) library resolution: `libraryId ?? resolveSoleLibrary(mediaType, user).id` (exactly one accessible library accepting the type, else 400 `Several libraries accept <type> — pass libraryId to choose one` / `No library accepts <type>`); persisted on the row so approval never guesses → (5) series profile lock (12b) → (6) auto-approval (rules 28-29) → (7) media ensure if auto-approved (rule 14) → (8) INSERT → (9) events, notification → (10) art wait (rule 16). `kind: 'delete'` short-circuits to rule 19 before step 1.
12. (a) Duplicate guard (from the guard to the INSERT, one transaction holds a per-`(mediaType, provider, externalId)` advisory lock (`pg_advisory_xact_lock(hashtext('requests:<mediaType>:<provider>:<externalId>'))`), so two concurrent creates of a title cannot both pass; the scope rules below are unchanged and the loser answers the 409 it would have answered a moment later): ADD rows for the title `(mediaType, provider, externalId)` in `pending|approved|processing|available`, any user; the request body names `('tmdb', tmdbId)`. None → ok. Not a series-with-non-empty-`seasons` → 409 `This title has already been requested`. Series with seasons: any existing row with null/empty `seasons` → 409 `The whole series has already been requested`; else overlap = `dto.seasons.filter(taken)` (request order, duplicates kept) non-empty → 409 `Season(s) <overlap joined ", "> have already been requested`. (b) Profile lock (series only): profiles of the earliest (`createdAt ASC`) active ADD request for the title, else the library media row's `qualityProfileId`/`languageProfileId`; when found they REPLACE the body's profile ids (even if the client sent others; null → undefined).
13. Quota (the user's `user_quotas` row of the request's kind, exposed as `<kind>QuotaLimit`, and `quotaPeriodDays`, see `users.md`, writable only with `users.manage`): `limit` = that row's limit; no row (0 on the wire) = unlimited (a negative limit always blocks); `periodDays = quotaPeriodDays || 7`; window start `since` = `periodDays × 24 h` before the current time (UTC days, so a DST change does not move the window; a negative stored period puts `since` in the future; `PATCH /users/:id` refuses `quotaPeriodDays < 1`, `users.md` rule 20, so a negative period can only come from a row stored before that check); count = ADD requests of this user and mediaType with status in (`pending`,`approved`) and `createdAt >= since` (processing/available/declined do NOT count; delete requests never count); `count >= limit` → 403 `Quota exceeded: <count>/<limit> <mediaType> requests in last <periodDays> days`. The check runs before the duplicate guard. Quota applies to managers too.
14. Auto-approved create ensures the media exists BEFORE inserting the request (rule 24). A failure aborts the create (nothing inserted); a media imported before a later failure is not rolled back. The inserted row is `status:'approved'`, `approvedBy = requester`, `media` = the ensured Media (or null when `ensure` returned null).
15. Row inserted: `user` = requester, `kind:'add'`, `mediaType`, `provider: 'tmdb'`, `externalId: String(tmdbId)`, `title`, `seasons: dto.seasons ?? null` (an empty array is stored as `[]`), `qualityProfile`/`languageProfile` = `{id}` or null (a falsy id, incl. 0, is null), `library: {id: resolved}`, status per auto-approval. A non-existent quality profile, language profile or library id is 400 `Quality profile #<id> not found` / `Language profile #<id> not found` / `Library #<id> not found` (create and `PATCH`); a `tmdbId` above 999999999 (nine digits, `external-ids.md` rule 3) is 400 with the standard validation body (`tmdbId must not be greater than 999999999`).
16. Art: after notification, `create` awaits `Promise.race([populateRequestArt(saved), sleep(5000)])`. `populateRequestArt` keys art `request/<mediaType>-<provider>-<externalId>/{poster,fanart}` (`image-store.md` rule 22): an existing file yields `getApiPath` (no `?v=` suffix), a missing one needs TMDB `getMovieDetails`/`getTvShowDetails(externalId)` (a provider other than `tmdb` has no metadata source: the lookup fails closed, so no art) then `downloadAndStore(url, 'request', key, variant)` (returns the path WITH `?v=<hash>`); if both end null nothing is written; otherwise `UPDATE requests SET posterUrl, fanartUrl` (both columns) and the in-memory row (and so the response) carries them only if the race finished in time. Every failure is swallowed (WARN `Request #<id>: art prefetch failed: <message>`).
17. Create response: the row of rule 5 (all relation ids, `declinedReason: null`, `user` and `approvedBy` as public identities) plus `qualityProfile` and `languageProfile` (`{id}` or `null`), `library: {id}` and `media`: the ensured Media (as in rule 7) or `null`. `posterUrl`/`fanartUrl` carry the art only when it landed within the wait, else `null`. A delete-kind create returns the row without `qualityProfileId`/`languageProfileId`, with `library: {id}|null` and `media: {id, path: null}`.
18. Events and notification of create (their `tmdbId` is the row's `externalId` as an integer; after INSERT, before the art wait): domain `request.created {requestId, mediaType, tmdbId, userId, kind:'add', seasons: dto.seasons ?? null}`; when auto-approved also domain `request.approved {requestId, mediaId: media?.id ?? null, mediaType, tmdbId, seasons: dto.seasons ?? null, approvedByUserId: requester}`; notification `request.approved` if auto-approved else `request.created`, payload `{title: dto.title, mediaType}` (fire-and-forget). No `media.acquisition.requested` here (only `onMediaImported`, rule 36, announces for the auto path).
19. Delete-kind create: the target media must exist for the title `(mediaType, provider, externalId)` else 400 `This title is not in the library and cannot be deleted`; dedup only against a `pending` DELETE row for the same title (409 `A deletion request for this title is already pending`); no quota, no auto-approval, no duplicate check against add requests, no library check, no art download. Row: `kind:'delete'`, `status:'pending'`, `seasons:null`, `approvedBy:null`, `media:{id}`, `library` = media's library (or null), `posterUrl`/`fanartUrl` copied from the media. Notification `request.delete.created {title: dto.title, mediaType}`; NO domain event.

### D. Update, delete, approve, decline

20. `PATCH`: runs `findOne` first (404/403/library gate), then `status !== 'pending'` → 403 `Only pending requests can be updated`, then owner-or-manager again (redundant). Per field: `undefined` = untouched; falsy non-undefined (`null`, `0`) clears the profile; `libraryId` non-null → library access check (rule 11 step 3) then set, falsy clears.
21. `PATCH` response: the shape of rule 7 (FK `media`, `comments`) with relation ids of the saved row, and `qualityProfile`/`languageProfile`/`library` (`{id}` or `null`) only for the fields the body touched.
22. `DELETE`: manager deletes any request in any status (including linked/processing ones; the media is untouched); non-manager: after `findOne` (owner gate), status must be `pending` else 403 `Only pending requests can be cancelled`. No notification, no domain event.
23. `approve` (ADD kind) steps: (1) manager else bare 403; (2) row by id else 404 `Request #<id> not found`; (3) library gate; (4) `status != pending` → 409 `Request is not pending`; (5) when no media holds the request's title, `assertImportTarget(mediaType, request.libraryId)` throws 400 if no resolvable library (request stays pending); (6) one conditional `UPDATE requests ... WHERE id = $1 AND status = 'pending'` sets status `approved`, `approvedBy` = caller, `declinedReason = null` (the loser of two concurrent approvals gets 409 `Request is not pending` and nothing imports or notifies twice); (7) `ensureMediaForApprovedRequest` SYNCHRONOUSLY (rule 24); on any error: status back to `pending`, `approvedBy = null`, error rethrown (two writes, not a transaction; a concurrent reader sees `approved` meanwhile); (8) if media: re-read the row, and when still `approved` and `mediaId` null (existing-media path) set `media = media`; domain `media.acquisition.requested {mediaIds:[media.id], reason:'request-approved'}`; (9) domain `request.approved {requestId, mediaId: media?.id ?? null, mediaType, tmdbId, seasons: seasons ?? null, approvedByUserId: caller}`; (10) notification `request.approved {title}` (NO `mediaType` key here, unlike the create path); (11) response = row re-read with joins (rule 8).
24. `ensureMediaForApprovedRequest(spec{mediaType, tmdbId, qualityProfileId, languageProfileId, libraryId, seasons}, addedByUserId)` (also used by auto-approve with `addedByUserId = requester`, approve passes the REQUESTER's `userId` as importer, not the admin): (a) `importFromTmdb({type, tmdbId, qualityProfileId?, languageProfileId?, libraryId?}, addedByUserId, seasons)` (the quality profile lands in the created media's video want, `items.md` rule 32; `envelopeCovers` reads the existing media's from its want); (b) on error with `status === 409` (title already in the library): load media by `(tmdbId, type)` — missing → return null; `envelopeCovers(existing profiles, requested profiles)` false → 409 with the long message of the Routes table; true → reuse the existing media; any other error → rethrown; (c) `applyMonitoredForRequestScope(media, seasons)` on the resulting media (rule 33).
25. `decline`: manager/404/library/409 as rule 4; then `status='declined'`, `approvedBy = caller` (the decliner is stored in `approvedBy`), `declinedReason = reason ?? null` (empty string kept as `''`); response = the row of rule 5 without `media`, `approvedBy` the decliner; notification event `request.delete.declined` if `kind==='delete'` else `request.declined`, payload `{title, reason: reason ?? ''}`; no domain event.
26. `approve` of a DELETE-kind row: UPDATE `status='approved'`, `approvedBy = caller`, `declinedReason = null`, `media = {id}` of the title's media if it exists; if the media exists, `MediaService.remove(media.id)` (runs `onMediaRemoved`, deletes the row) and, off the response path, `deleteMediaFolder(diskPath)` (failure logged ERROR `Media file deletion failed after delete request #<id> — title="<t>" path="<p>" error=<m>`); a failed `remove` rolls the request back to `pending`/`approvedBy null` and rethrows; media already gone → the request is simply approved. Notification `request.delete.approved {title, mediaType}`; NO `request.approved` domain event; response = row re-read with joins.
27. Comments: `addComment` loads the request WITHOUT relations (its eager `user` is the full account, projected before return), then owner-or-manager gate, library gate, INSERT; response = the saved comment `{id, createdAt, updatedAt, message, requestId, userId, user: PublicIdentity, request: {id, createdAt, updatedAt, user, mediaType, kind, tmdbId, title, status, approvedBy: null, declinedReason, seasons, posterUrl, fanartUrl}}` (`approvedBy` is `null` whatever the row says, no relation ids). `getComments` returns comments `ORDER BY createdAt ASC` with `requestId`, `userId`, `message`, `user: PublicIdentity` and no embedded `request`. No notification, no event.

### E. Auto-approval rules

28. Rule entity `auto_approval_rules`: `name`, `enabled` (default true), `criteria` jsonb. `criteria` keys (all optional, strict whitelist; unknown key = 400): `userIds` int[], `roleIds` int[], `mediaType` enum, `libraryIds` int[], `genreIds` int[] (TMDB genre ids), `maxSeasons` int >= 1, `yearFrom`/`yearTo` int 1900..2200.
29. Matching (`shouldAutoApprove`, only for ADD create): load `enabled = true` rules (no ORDER BY); none → false. Metadata (TMDB details: `genreIds`, `year`, `seasonCount`) is fetched only if some rule reads `genreIds`, `yearFrom`, `yearTo`, or `maxSeasons` while the body has no non-empty `seasons`; a failed lookup is logged (WARN) and leaves metadata null (fail closed: those criteria cannot match). Context: `userId`, `roleId = user.userRole?.id ?? null`, `mediaType`, `libraryId` = the RESOLVED library, `genreIds` (`[]` if none), `year`, `seasonCount` = the length of `dto.seasons` when non-empty, else `metadata?.seasonCount ?? null`. A rule matches when ALL set criteria hold: (a) `userIds`/`roleIds` (if either non-empty): requester id in `userIds` OR role id in `roleIds`; (b) `mediaType` equal; (c) `libraryIds` non-empty → library non-null and listed; (d) `genreIds` non-empty → intersects the title's genres; (e) `maxSeasons != null` and request is a series → `seasonCount` non-null and `<= maxSeasons` (ignored for movies); (f) `yearFrom`/`yearTo` → year non-null and within; `{}` matches everything. Rules OR together; the first match (in load order) wins and is logged `Auto-approving <type> <tmdbId> for user <id>: rule "<name>" (#<id>)`. An empty `seasons` is no scope: `seasonCount` falls back to the show's.
30. Rule DTO: `name` trimmed then `IsString` + `IsNotEmpty`; `enabled?` boolean; `criteria` required nested object (`{}` ok; `null`, absent or an array = 400). Controller bodies use the same DTO for POST and PUT.
31. `POST` stores `enabled ?? true`; `PUT` replaces `name`, `enabled` (omitted = reset to `true`), `criteria` wholesale; both return the saved entity; `GET` list `ORDER BY name ASC` (DB collation; parity compares order-insensitively like settings); a missing id on GET/PUT/DELETE = 404 `Rule #<id> not found`.

### F. Lifecycle (state machine)

32. Statuses and transitions (all other transitions do not exist; `declined` and `removed` are terminal, `available` only ends by removal or unmonitor, `approve` needs `pending`):

| From | To | Trigger | Rule |
|---|---|---|---|
| (new) | `pending` / `approved` | create, rule match → `approved` | 11, 29 |
| `pending` | `approved` | manager `approve`; or `onMediaImported` when the imported envelope covers the request | 23, 36 |
| `pending` | `declined` | manager `decline` | 25 |
| `pending`,`approved`,`processing` (ADD, linked to media) | `declined`, `media = null` | `onMediaMonitorChange` (monitored true→false) → reason `Media was unmonitored`; `onMediaRemoved` → reason `Media removed from library` | 38, 40 |
| `available` (ADD, linked to media) | `removed`, `media = null` | `onMediaMonitorChange` (monitored true→false); `onMediaRemoved`; also reached by the cleanup actions `delete` and `delete_files_unmonitor` | 38, 40 |
| season-scoped in-flight or `available` | `declined` (reason `Season <n> was unmonitored`, `media = null`; an `available` row becomes `removed` instead) or season trimmed | `onSeasonMonitorChange` | 39 |
| `approved` | `processing` | domain `acquisition.grabbed` / plugin host `requests.markInProgress` | 37 |
| `approved`,`processing` | `available` | SSE `import.complete` and scope covered | 41 |
| DELETE `pending` | `approved` (terminal done-state) | manager approve (removal executed) or `onMediaRemoved` for in-flight delete rows | 26, 40 |
| DELETE `pending` | `declined` | manager `decline` | 25 |

`ACTIVE_REQUEST_STATUSES` = pending, approved, processing, available (blocks a same-title re-request; `removed` does not); `IN_FLIGHT` = pending, approved, processing; `ACTIVE_DELETE` = pending; `SATISFIABLE` (approved, processing, available) is defined but unused. `seasonScopeOf`: null/empty `seasons` = covers everything, else the set.
33. `applyMonitoredForRequestScope(media, seasons)` (called from approve/auto-approve/`onMediaImported`): sets `media.monitored = true` if false; for a series with non-empty `seasons`, sets `seasons.monitored = true` for the listed season numbers that are false; never turns monitoring off; episodes untouched.
34. Subscriptions at boot: (a) SSE bus (audience-blind) `import.complete` → `onImportComplete(event.mediaId)`; (b) domain `acquisition.grabbed` → `markInProgress(event.mediaId, event.seasonNumber)`. Failures are caught and logged WARN `onImportComplete failed for media#<id>: <m>` / `markInProgress failed for media#<id>: <m>`; at-most-once, no replay: an event lost while the server is down leaves the request `approved`/`processing` until the next event for that media or the next reconcile (rule 44; hub rules 24, 37).
35. Who emits what these subscribe to: `import.complete` is emitted to the viewers of the media by the plugin host's `acquisition.imported` handler, and nowhere else; `acquisition.grabbed` is a domain event from the plugin host `events.publish`. Both reach the bus, which feeds the in-process lifecycle subscribers.
36. `onMediaImported(media, addedByUserId)` (called synchronously inside `importFromTmdb` / import-from-disk BEFORE the `media.imported` domain event and before the import returns): load the in-flight requests whose `(mediaType, provider, externalId)` the media holds in `media_external_ids` (a media with no external id matches none); for each, `envelopeCovers({media quality/language profile ids}, {request ids})` — false → untouched (never silently substitute a profile); true → `media = media`, `pending` → `approved` with `approvedBy = addedByUserId` (only if non-null; `approved`/`processing` rows keep theirs), then `applyMonitoredForRequestScope(media, request.seasons)`; save all touched; if any touched emit domain `media.acquisition.requested {mediaIds:[media.id], reason:'media-imported'}`. `envelopeCovers`: requested side null on an axis = satisfied; quality: same id or existing cutoff resolution >= requested cutoff resolution (existing null = not covered; missing profile = not covered; cutoff item missing = resolution 0); language: same id or every requested audio `isoCode` in the existing audio set.
37. `markInProgress(mediaId, seasonNumber?)`: requests linked by FK to `mediaId` with status `approved`; skip a row when `seasonNumber` is defined and the row has a non-empty `seasons` not containing it (movies/whole-series flip on any grab); set `processing`, save, then per touched row notification `request.processing {title, mediaType}`. Callers: the `acquisition.grabbed` subscription and the plugin host method `requests.markInProgress` (`idempotencyKey` ignored).
38. `onMediaMonitorChange(media, wasMonitored)`: acts only when `wasMonitored` and `media.monitored === false`: retires the linked ADD requests like rule 40 does (one `retireLinked` helper): in-flight are `declined` with reason `Media was unmonitored`, `available` ones `removed`, both `media = null`. Called by `setMediaMonitored` (`media-write.md` rule 27) for every real flip: `PUT`, bulk, cleanup `delete_files_unmonitor`, importer updates.
39. `onSeasonMonitorChange(media, seasonNumber, wasMonitored, isMonitored)`: only on true→false; candidates linked to the media in-flight or `available` (any kind); a series row whose `seasons` is null or empty is first expanded to the series' monitored season numbers plus this one, so a whole-series request does not survive the unmonitor (the season can be requested again); a row whose scope lacks the season is skipped; `remaining = seasons minus season`; empty → `declined`, reason `Season <n> was unmonitored`, `media = null` (`removed` instead for an `available` row); else `seasons = remaining`. No notification.
40. `onMediaRemoved(media)` (called BEFORE the media row is deleted, inside the media removal): first resolve every in-flight DELETE request linked to the media to `approved` with `declinedReason = null`, `media = null` (the approved one and concurrent duplicates); then `retireLinked` with reason `Media removed from library` (in-flight ADD rows `declined`, `available` ADD rows `removed`, `media = null`, no reason for `removed`: not a rejection). No notification.
41. `onImportComplete(mediaId)`: requests linked to `mediaId` with status `approved|processing`; load the media with `files`, `seasons`, `seasons.episodes` (missing → no-op); a request is covered when: movie → `media_files` count >= 1; series → over the media's seasons filtered by the request scope (`seasons` null/empty = all), skipping unmonitored seasons and seasons without monitored episodes, EVERY monitored episode must have an item part (`items.md` rule 21: a multi-episode file gives a part to every existing episode of its range); `false` if any is missing; the result is `anyChecked` (at least one season examined): a scope with no monitored episodes to check (scope past the library, everything unmonitored) is NOT covered (the request stays open). Covered rows → `available`, saved, then per row notification `request.available {title, mediaType}`.
42. Re-entrancy during `approve`/auto-approve: the import calls `onMediaImported` (rule 36), which must see the request row already `approved` (rule 23 step 6 commits before step 7) and link it; so no transaction or row lock on the request is held across the import call (the approval claims the row with one conditional `UPDATE ... WHERE status = 'pending'`). The hooks (`requests::Lifecycle::{on_media_imported, on_media_removed, on_media_monitor_change, on_season_monitor_change}`) are in-process calls from the media write side; `on_media_removed` runs inside the delete's transaction and `on_media_imported` once the media row is committed.
43. The module has no settings keys or SSE events of its own, and one timer, the reconcile (rule 44). `GET /api/system/stats` and `GET /api/counts` read `requests` rows directly (`pendingRequests`), `users-stats` counts by status, the SSE audience resolver (`recipientsForMedia`) reads `requests."mediaId"`; all read the same table.
44. Reconcile: at startup, then every hour (`0 * * * *`, server time zone, a housekeeping timer like the commands prune: not listed, not triggerable, no `commands` row), run `onImportComplete(mediaId)` (rule 41) for every media that has an ADD request linked in `approved|processing`. It reuses rule 41 whole: coverage test, conditional `approved|processing` → `available` transition, `request.available` notification once per row moved, no write for a row another event already moved. A failure is logged WARN `request reconcile failed for media#<id>: <m>` and does not stop the pass. Requests without a linked media are not touched.

## SQL

All tables/columns are camelCase quoted identifiers . `requests."mediaType"` is `text` under a `CHECK` (`movie|series`); the other enum columns are Postgres enums (`requests_status_enum`, request kind enum): compare to text literals or cast.

1. List (rule 9), equivalent to:
```sql
SELECT r.*, u.id, u.username, u.avatar, ab.id, ab.username, ab.avatar, m.* -- m: media columns only
FROM requests r
LEFT JOIN users u ON u.id = r."userId"
LEFT JOIN users ab ON ab.id = r."approvedById"
LEFT JOIN media m ON m.id = (SELECT e."mediaId" FROM media_external_ids e WHERE e.kind = r."mediaType" AND e.provider = r.provider AND e.value = r."externalId" ORDER BY e."mediaId" LIMIT 1)
WHERE <scope> [AND r.status = $st] [AND r.kind = $k] [AND r.provider = 'tmdb' AND r."externalId" = $t] [AND r."mediaType" = $mt]
ORDER BY r."createdAt" DESC
LIMIT $limit OFFSET ($page - 1) * $limit; -- plus a COUNT over the same WHERE
```
`<scope>`: `r."userId" = $uid` (non-manager) | `(r."libraryId" IS NULL OR r."libraryId" IN (<ids or 0>))` [+ `AND r."userId" = $q`] (manager, non-super-admin) | none / `r."userId" = $q` (super-admin).
2. Quota (rule 13):
```sql
SELECT count(*) FROM requests r WHERE r."userId" = $1 AND r."mediaType" = $2 AND r.kind = 'add'
  AND r.status IN ('pending','approved') AND r."createdAt" >= $since;
```
3. Duplicate guard / title-state / series profile lock (rules 10, 12): `SELECT * FROM requests WHERE "mediaType" = $1 AND provider = $2 AND "externalId" = $3 AND kind = 'add' AND status IN ('pending','approved','processing','available') [ORDER BY "createdAt" ASC]` (guard: no ORDER BY; profile lock: same filter `LIMIT 1 ORDER BY "createdAt" ASC`, fallback `SELECT "qualityProfileId","languageProfileId"` of the series holding the title in `media_external_ids` (external-ids rule 6)).
4. Delete-kind dedup: `SELECT * FROM requests WHERE "mediaType" = $1 AND provider = $2 AND "externalId" = $3 AND kind = 'delete' AND status = 'pending' LIMIT 1`.
5. Detail (rule 7): `requests` by id + `LEFT JOIN`s `users` (eager `user`, `approvedBy`), `media` (FK) with its eager relations, `request_comments` + `users` for each comment.
6. Comments list: `SELECT c.*, u.* FROM request_comments c JOIN users u ON u.id = c."userId" WHERE c."requestId" = $1 ORDER BY c."createdAt" ASC`. Insert/delete by id.
7. Approve/decline/update/remove: `UPDATE requests SET status, "approvedById", "declinedReason", "mediaId", "qualityProfileId", "languageProfileId", "libraryId", "updatedAt" = now() WHERE id = $1` (only changed columns are written); `DELETE FROM requests WHERE id = $1`. After approve: `SELECT * FROM requests WHERE id = $1` (relink check, rule 23 step 8), then the rule-1 join with `WHERE r.id = $1` (`findResolvedRow`).
8. Lifecycle finds (rules 36-41), each `status IN (...)` over the in-flight/approved sets: `SELECT * FROM requests r WHERE status IN ('pending','approved','processing') AND EXISTS (SELECT 1 FROM media_external_ids e WHERE e."mediaId" = $1 AND e.kind = r."mediaType" AND e.provider = r.provider AND e.value = r."externalId")` (`onMediaImported`), `... WHERE "mediaId" = $1 AND status = 'approved'` (`markInProgress`), `... WHERE "mediaId" = $1 AND status IN ('approved','processing')` (`onImportComplete`), `... WHERE "mediaId" = $1 AND kind = 'add'|'delete' AND status IN ('pending','approved','processing')` (decline / delete resolution), `... WHERE "mediaId" = $1 AND status IN (in-flight)` (`onSeasonMonitorChange`, no kind filter). Writes: one `UPDATE requests` per touched row. `onImportComplete` coverage: `SELECT * FROM media_files WHERE "mediaId" = $1`, `seasons` of the media, `episodes` of those seasons (`seasonNumber`, `monitored`, `episodeNumber`, `endEpisodeNumber`, `hasFile`).
9. Rules: `SELECT * FROM auto_approval_rules WHERE enabled = true` (matching, no ORDER BY), `... ORDER BY name ASC` (list), by id (get/put/delete), INSERT/UPDATE/DELETE.

## Events

Request routes and the lifecycle emit NO SSE events (`GET /api/system/events` carries nothing request-specific); the UI polls.

| Event | Kind / audience | Payload | Emitter | Consumer |
|---|---|---|---|---|
| `request.created` | domain (hub bus; plugin webhooks read it) | `{requestId: number, mediaType: string, tmdbId: number, userId: number\|null, kind: string, seasons: number[]\|null}` | `POST /api/requests` ADD only (rule 18) | plugin webhook/process dispatchers |
| `request.approved` | domain | `{requestId, mediaId: number\|null, mediaType, tmdbId, seasons: number[]\|null, approvedByUserId: number\|null}` | auto-approved create; ADD `approve`. Not for DELETE-kind approve, not for `onMediaImported` promotions | plugin dispatchers |
| `media.acquisition.requested` | domain | `{mediaIds: number[], reason: string}` | `approve` ADD (`'request-approved'`, only when media non-null); `onMediaImported` (`'media-imported'`, only when a request was touched) | acquisition owner (plugin dispatchers) |
| `import.complete` | consumed, SSE bus, audience-blind (hub rule 24) | `{mediaId, title, seasonNumber?, episodeNumber?}` (lifecycle uses `mediaId` only) | plugin host (rule 35) | `onImportComplete` |
| `acquisition.grabbed` | consumed, domain | `{mediaId, seasonNumber?, episodeNumber?}` (lifecycle uses `mediaId`, `seasonNumber`) | plugin host (rule 35) | `markInProgress` |

Notifications sent (event: payload; see `notifications.md`): `request.created`/`request.approved` `{title, mediaType}` (create), `request.approved` `{title}` (approve), `request.declined`/`request.delete.declined` `{title, reason}`, `request.delete.created`/`request.delete.approved` `{title, mediaType}`, `request.processing`/`request.available` `{title, mediaType}`.
