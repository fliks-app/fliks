## Rules

### A. Policies and visibility

1. CASL for requests: `requests.create` grants `create` on `FliksRequest`, `read` and `update`/`delete` conditioned (`{userId: self}`, update/delete also `{status:'pending'}`); `requests.manage` grants `manage` (every action incl. `approve`, `decline`). Guards use class-level checks, so conditions never bite at the guard: every `requests.create` holder passes `Read`/`Update`/`Delete`/`Create`; only managers pass `Approve`/`Decline`. Per-instance authorisation is done in the service (rules 2-4). `[ts:src/modules/auth/casl/casl-ability.factory.ts:107]`–`[ts:src/modules/auth/casl/casl-ability.factory.ts:122]`
2. "Manager" in the service = `ability.can(Action.Manage, FliksRequest)` on the caller's ability (`requests.manage` or `manage:all`). "Super-admin" = `isAdmin` or `permissions` contains `manage:all`. `[ts:src/modules/requests/requests.service.ts:76]`–`[ts:src/modules/requests/requests.service.ts:85]`
3. Owner-or-manager gate (`findOne`, `addComment`, `getComments`, `removeComment`, `update`, `remove`): a non-manager who does not own the request gets a bare `ForbiddenException()` (body `{"message":"Forbidden","statusCode":403}`, auth rule 15). Comments: `removeComment` compares `comment.userId` (the comment's author), not the request owner. `[ts:src/modules/requests/requests.service.ts:704]`–`[ts:src/modules/requests/requests.service.ts:707]`, `[ts:src/modules/requests/requests.service.ts:1076]`–`[ts:src/modules/requests/requests.service.ts:1078]`, `[ts:src/modules/requests/requests.service.ts:1127]`–`[ts:src/modules/requests/requests.service.ts:1129]`
4. Library gate `assertCanAccessRequestLibrary(user, request.libraryId, request.userId)`: `libraryId == null` passes; super-admin passes; the request's owner passes; otherwise `libraryId` must be in `getAccessibleLibraryIds(user)` else 403 `You do not have access to this request's target library`. Runs in `findOne` (after the owner gate), `approve`, `decline`, `addComment`, `getComments`, `removeComment` (only when the comment's request still loads). Order in `approve`/`decline`: manager check (bare 403) → row lookup (404) → library gate → status check (409). `[ts:src/modules/requests/requests.service.ts:112]`–`[ts:src/modules/requests/requests.service.ts:126]`, `[ts:src/modules/requests/requests.service.ts:787]`–`[ts:src/modules/requests/requests.service.ts:794]`, `[ts:src/modules/requests/requests.service.ts:1034]`–`[ts:src/modules/requests/requests.service.ts:1045]`
5. `RequestRow` columns (table `requests`): `id`, `createdAt`/`updatedAt` (ISO), `mediaType`, `kind` (`'add'` default), `tmdbId`, `title`, `status`, `declinedReason` `string|null`, `seasons` `number[]|null` (jsonb; `[]` and `null` both mean "whole title"), `posterUrl`/`fanartUrl` `string|null`. Enums: status `pending|approved|declined|processing|available|failed` (`failed` is only written by the Seerr importer, S5), kind `add|delete`, mediaType `movie|series`. Relation ids (`userId`, `approvedById`, `qualityProfileId`, `languageProfileId`, `libraryId`, `mediaId`: `number|null`) are present on rows loaded from the DB and also present on the rows `POST`, `PATCH` and decline return (recorded); only a comment's embedded `request` has none (rule 27). `[ts:src/modules/requests/entities/request.entity.ts:18]`–`[ts:src/modules/requests/entities/request.entity.ts:112]`, `[ts:src/common/enums/request-status.enum.ts:1]`
6. Embedded users are always projected to `PublicIdentity` (`user`, `approvedBy`, each `comments[].user`): `approvedBy` null when unset. Nothing else of the account (email, permissions, quotas) leaves the server. Every route returning a request goes through `projectEmbeddedUsers` (or builds the projection in the query). `[ts:src/modules/requests/requests.service.ts:712]`–`[ts:src/modules/requests/requests.service.ts:738]`
7. `GET /api/requests/:id` loads `relations: ['user','approvedBy','media','comments','comments.user']` via the FK: `media` is the full `Media` JSON of the linked row including its eager relations (`library`, `qualityProfile`, `languageProfile`, `metadata`; no files or seasons) and the `path` getter (`@Expose`, `library.path` joined with `folderName`, or null), `searchVector` excluded (`select:false`); `comments` have no ORDER BY (physical order). The list and `approve` use rule 8 instead, so the same title has two different `media` shapes. `F70`: `media.path` and `media.library.path` only for callers who can manage libraries (`paths_visible`, F22), omitted otherwise. `[ts:src/modules/requests/requests.service.ts:698]`–`[ts:src/modules/requests/requests.service.ts:710]`, `[ts:src/modules/media/entities/media.entity.ts:107]`–`[ts:src/modules/media/entities/media.entity.ts:114]`, `[ts:src/modules/media/entities/media.entity.ts:166]`–`[ts:src/modules/media/entities/media.entity.ts:171]`
8. List and `approve` join the library media by `(tmdbId, type)`, not by the request's FK, so partial-library titles surface a `media` object; the FK `mediaId` stays as stored. Media is mapped from the QueryBuilder join: the entity's own columns only (no eager relations, so no `library`/`qualityProfile`/`metadata` keys and `path` serialises as `null`); `media.type::text = r."mediaType"::text` because the two enums are distinct Postgres types. `UQ(type, tmdbId)` on `media` guarantees at most one match. `[ts:src/modules/requests/requests.service.ts:644]`–`[ts:src/modules/requests/requests.service.ts:657]`, `[ts:src/modules/media/entities/media.entity.ts:32]`. Exact key set of the joined `media` (RelationId fields) is `[assumed]` TypeORM behaviour: record parity on the seed before porting.

### B. List and title state

9. `GET /api/requests` scoping: non-manager → `r."userId" = caller` and the `userId` query filter is ignored; manager → no user scope, `userId` filter applies; a manager that is not a super-admin additionally sees only `(r."libraryId" IS NULL OR r."libraryId" IN (accessible ids))`, with `[0]` substituted when the accessible set is empty. Filters are AND-ed; `tmdbId`/`userId` are applied only when truthy (`0` is ignored). Pagination `OFFSET (page-1)*limit LIMIT limit`; `total` is the unpaginated count. Order `createdAt DESC` only: ties follow Postgres in Nest; Rust orders `createdAt DESC, id ASC` (C12). `title-state` also answers 400 for a `mediaType` outside the enum (`C111`). `[ts:src/modules/requests/requests.service.ts:629]`–`[ts:src/modules/requests/requests.service.ts:696]`
10. `title-state` aggregates ADD requests in `pending|approved|processing|available` for `(tmdbId, mediaType)` across all users, `ORDER BY createdAt ASC`, never exposing requesters: `wholeSeriesRequested` = series with any active request whose `seasons` is null/empty; `requestedSeasons` = sorted union of all active `seasons`; `requested` = (series: `wholeSeriesRequested`; movie: any active). Profiles: for series only, `existingSeriesProfiles` (rule 12); `profilesLocked = locked !== null`; movie always `profilesLocked:false`, both ids null. Delete-kind rows are ignored. `[ts:src/modules/requests/requests.service.ts:594]`–`[ts:src/modules/requests/requests.service.ts:627]`, `[ts:src/modules/requests/request-status.constants.ts:7]`–`[ts:src/modules/requests/request-status.constants.ts:12]`

### C. Create

11. Order of checks in `create` (ADD kind): (1) `checkQuota` (rule 13) → (2) duplicate guard (rule 12a) → (3) explicit `libraryId` access (non-super-admin: must be in accessible ids, else 403 `You do not have access to the selected library`) → (4) library resolution: `libraryId ?? resolveSoleLibrary(mediaType, user).id` (exactly one accessible library accepting the type, else 400 `Several libraries accept <type> — pass libraryId to choose one` / `No library accepts <type>`); persisted on the row so approval never guesses → (5) series profile lock (12b) → (6) auto-approval (rules 28-29) → (7) media ensure if auto-approved (rule 14) → (8) INSERT → (9) events, notification → (10) art wait (rule 16). `kind: 'delete'` short-circuits to rule 19 before step 1. `[ts:src/modules/requests/requests.service.ts:270]`–`[ts:src/modules/requests/requests.service.ts:376]`
12. (a) Duplicate guard: ADD rows for `(tmdbId, mediaType)` in `pending|approved|processing|available`, any user. None → ok. Not a series-with-non-empty-`seasons` → 409 `This title has already been requested`. Series with seasons: any existing row with null/empty `seasons` → 409 `The whole series has already been requested`; else overlap = `dto.seasons.filter(taken)` (request order, duplicates kept) non-empty → 409 `Season(s) <overlap joined ", "> have already been requested`. (b) Profile lock (series only): profiles of the earliest (`createdAt ASC`) active ADD request for the tmdbId, else the library media row's `qualityProfileId`/`languageProfileId`; when found they REPLACE the body's profile ids (even if the client sent others; null → undefined). `[ts:src/modules/requests/requests.service.ts:512]`–`[ts:src/modules/requests/requests.service.ts:547]`, `[ts:src/modules/requests/requests.service.ts:557]`–`[ts:src/modules/requests/requests.service.ts:587]`, `[ts:src/modules/requests/requests.service.ts:288]`–`[ts:src/modules/requests/requests.service.ts:294]`
13. Quota (users fields `movieQuotaLimit`, `seriesQuotaLimit`, `quotaPeriodDays`, see `users.md`, writable only with `users.manage` per F11): `limit = movie ? movieQuotaLimit : seriesQuotaLimit`; `!limit` (0/null) = unlimited (a negative limit is truthy and always blocks); `periodDays = quotaPeriodDays || 7`; window start `since = now` with `setDate(getDate() - periodDays)` (server-local calendar days, DST-sensitive); count = ADD requests of this user and mediaType with status in (`pending`,`approved`) and `createdAt >= since` (processing/available/declined do NOT count; delete requests never count); `count >= limit` → 403 `Quota exceeded: <count>/<limit> <mediaType> requests in last <periodDays> days`. The check runs before the duplicate guard. Quota applies to managers too. `[ts:src/modules/requests/requests.service.ts:236]`–`[ts:src/modules/requests/requests.service.ts:264]`, `[ts:src/modules/users/entities/user.entity.ts:62]`–`[ts:src/modules/users/entities/user.entity.ts:69]`
14. Auto-approved create ensures the media exists BEFORE inserting the request (rule 24 call chain, Nest-side). A failure aborts the create (nothing inserted); a media imported before a later failure is not rolled back. The inserted row is `status:'approved'`, `approvedBy = requester`, `media` = the ensured Media (or null when `ensure` returned null). `[ts:src/modules/requests/requests.service.ts:296]`–`[ts:src/modules/requests/requests.service.ts:334]`
15. Row inserted: `user` = requester, `kind:'add'`, `mediaType`, `tmdbId`, `title`, `seasons: dto.seasons ?? null` (an empty array is stored as `[]`), `qualityProfile`/`languageProfile` = `{id}` or null (a falsy id, incl. 0, is null), `library: {id: resolved}`, status per auto-approval. Ids are not checked for existence: a non-existent profile id or (super-admin) library id is an FK violation, 500 in Nest (Q2). `[ts:src/modules/requests/requests.service.ts:316]`–`[ts:src/modules/requests/requests.service.ts:336]`
16. Art: after notification, `create` awaits `Promise.race([populateRequestArt(saved), sleep(5000)])`. `populateRequestArt` keys art `request/<mediaType>-<tmdbId>/{poster,fanart}`: an existing file yields `getApiPath` (no `?v=` suffix), a missing one needs TMDB `getMovieDetails`/`getTvShowDetails(String(tmdbId))` then `downloadAndStore(url, 'request', key, variant)` (returns the path WITH `?v=<hash>`, `[ts:src/modules/images/image.service.ts:376]`); if both end null nothing is written; otherwise `UPDATE requests SET posterUrl, fanartUrl` (both columns) and the in-memory row (and so the response) carries them only if the race finished in time. Every failure is swallowed (WARN `Request #<id>: art prefetch failed: <message>`). `[ts:src/modules/requests/requests.service.ts:365]`–`[ts:src/modules/requests/requests.service.ts:373]`, `[ts:src/modules/requests/requests.service.ts:452]`–`[ts:src/modules/requests/requests.service.ts:499]`
17. Create response (recorded): the row of rule 5 (all relation ids, `declinedReason: null`, `user` and `approvedBy` as public identities) plus `qualityProfile` and `languageProfile` (`{id}` or `null`), `library: {id}` and `media`: the ensured Media (as in rule 7) or `null`. `posterUrl`/`fanartUrl` carry the art only when it landed within the wait, else `null`. A delete-kind create returns the row without `qualityProfileId`/`languageProfileId`, with `library: {id}|null` and `media: {id, path: null}`. `[ts:src/modules/requests/requests.service.ts:338]`
18. Events and notification of create (after INSERT, before the art wait): domain `request.created {requestId, mediaType, tmdbId, userId, kind:'add', seasons: dto.seasons ?? null}`; when auto-approved also domain `request.approved {requestId, mediaId: media?.id ?? null, mediaType, tmdbId, seasons: dto.seasons ?? null, approvedByUserId: requester}`; notification `request.approved` if auto-approved else `request.created`, payload `{title: dto.title, mediaType}` (fire-and-forget). No `media.acquisition.requested` here (only `onMediaImported`, rule 36, announces for the auto path). `[ts:src/modules/requests/requests.service.ts:338]`–`[ts:src/modules/requests/requests.service.ts:363]`
19. Delete-kind create: the target media must exist by `(tmdbId, mediaType)` else 400 `This title is not in the library and cannot be deleted`; dedup only against a `pending` DELETE row for the same title (409 `A deletion request for this title is already pending`); no quota, no auto-approval, no duplicate check against add requests, no library check, no art download. Row: `kind:'delete'`, `status:'pending'`, `seasons:null`, `approvedBy:null`, `media:{id}`, `library` = media's library (or null), `posterUrl`/`fanartUrl` copied from the media. ### D. Update, delete, approve, decline

20. `PATCH`: runs `findOne` first (404/403/library gate), then `status !== 'pending'` → 403 `Only pending requests can be updated`, then owner-or-manager again (redundant). Per field: `undefined` = untouched; falsy non-undefined (`null`, `0`) clears the profile; `libraryId` non-null → library access check (rule 11 step 3) then set, falsy clears. `[ts:src/modules/requests/requests.service.ts:740]`–`[ts:src/modules/requests/requests.service.ts:769]`
21. `PATCH` response (recorded): the shape of rule 7 (FK `media`, `comments`) with relation ids of the saved row, and `qualityProfile`/`languageProfile`/`library` (`{id}` or `null`) only for the fields the body touched.
22. `DELETE`: manager deletes any request in any status (including linked/processing ones; the media is untouched); non-manager: after `findOne` (owner gate), status must be `pending` else 403 `Only pending requests can be cancelled`.
