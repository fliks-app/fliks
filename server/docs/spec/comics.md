# Spec: comics in the catalogue

Scope: what the `comic` kind adds to the data model and to the media payloads: the kind and its family, a volume and its issues, `comic_details`, `comic_issues`, the wire shapes of the detail and the list. Archive ingest and the page routes are the last two sections. Local metadata (`ComicInfo.xml`, file names, manual edits) and metadata providers (Metron, Comic Vine) are the last two sections; acquisition is the Acquisition section and the reader is later work (`plans/books-audiobooks.plan.md`, phase 7). The wire contract shared with the client is `plans/comics-contract.md`; the migration is `1789000000700_comics.sql`.

## Kind and families

1. `MediaKind::Comic`: wire name `comic` (`media.type`, `requests."mediaType"`, `user_quotas.kind`, the `comic` level of `cleanup_rules.levels`), `has_seasons` false, `families` `[Image]`, `count_key` `comics`, `completed_stat_key` `comicsFinished`. Every exhaustive `match` on `MediaKind` has a `comic` arm. The kind CHECKs list `MediaKind::ALL`; the family CHECKs (`editions.family`, `wants.family`, the quality families) gain `image`, the family `Family::Image` was reserved for (`items.md` rule 39).
2. A comic is one `media` row of type `comic`: one series volume (a run, e.g. the one that started in 2016), with the work-level title, overview, year and poster on `media`. A library accepts the type like any kind: `"comic"` in `libraries."mediaTypes"`.
3. `create_shell` for a comic inserts one `image` want (`language` NULL, with the quality profile the creation resolved, like any kind) and no edition and no item, like a book. Ingest creates the volume's one `image` edition and one item per issue. The format of a file is not the edition's: a volume can mix `cbz` and `pdf` files (rule 10).
4. A media cannot become a comic or stop being one: `PUT /api/media/:id` answers `400 A comic cannot change type`. A comic is not requestable (`POST /api/requests` answers `400 mediaType must be one of the following values: movie, series, book`) and the TMDB and TVDB imports refuse a kind that is not video.

## Volume and issues

5. `comic_details("mediaId", kind = 'comic', publisher, "startYear", volume, "originalLanguage")` is the volume-level detail row, one per comic, `kind` pinned by a composite foreign key (`media-details.md` rule 12). `"startYear"` is 1 to 9999, `volume` the number printed on the cover (`>= 0`), NULL when unknown. `media_details_json` has a fourth arm for it (every video-only key NULL). The row is created by ingest; a payload of a comic without one reads `null` for each field.
6. An issue is an ungrouped item of the volume's edition (`items.md` rule 4: a comic has no group) and its `items."number"` stays NULL. A comic therefore never appears in an episode list, count or lookup (`items.md` rule 12), and `item_of(comic, NULL)` answers `NULL` with several issues (`items.md` rule 36): an issue is addressed by its item id.
7. `comic_issues("itemId", "mediaId", kind, "sortNumber", label, "pageCount")` holds the facts of an issue item, one row per item, with `FOREIGN KEY ("itemId", "mediaId") REFERENCES items (id, "mediaId") ON DELETE CASCADE`. `kind` is `issue`, `annual` or `special`; `"sortNumber"` is the finite decimal sort key (`1`, `1.5`, `0`, `-1`); `label` the printed number (`"1"`, `"1.5"`, `"0"`), never empty; `"pageCount"` is positive or NULL. `UNIQUE ("mediaId", kind, "sortNumber")` is the key ingest upserts on. **Decision:** `items."number"` stays an integer (every series path reads it), so the decimal key and the label live in this table, and annuals are a `kind`, not an item group: a group makes an item an episode for every query of `items.md` rule 12. `items.title` and `items."airDate"` carry the issue's title and release date.
8. A variant cover or a second scan of one issue is another version of the same item (`items.md` rule 35: another part with a higher `"version"`), never another issue: the unique key above refuses it. Story arcs and collected editions (TPB, omnibus) as collections of comics are later work: `collection_entries` can hold them (`items.md` rule 38) but no collection route reads comic entries yet.

## Wire

Keys absent for other kinds: a movie, series or book payload carries no `comic` key.

9. `GET /api/media/:id` of a comic carries `comic: ComicDetail` (`plans/comics-contract.md`): `publisher`, `startYear` and `volume` from `comic_details` (null when no row), `providers` (rule 44) and `issues` in the readable editions (`COALESCE(editions."libraryId", media."libraryId")` in the caller's libraries): the issues (`kind = 'issue'`) by `"sortNumber"` ascending, then the annuals and specials by `"sortNumber"`, then `kind`, then item id. An issue is `{itemId, mediaFileId, format, number (label), sort, annual (kind <> 'issue'), kind, title, overview (the summary or null), releaseDate (YYYY-MM-DD or null), pageCount, progression, finished}`.
10. The part of an issue is picked once, by the order of `items.md` rule 35 using the caller's `playback_states` row: the file the state names when it is still a part, else the first part of the state's version, else the first part of the highest version. `mediaFileId` is that file, `format` the lower-cased extension of the same file when it is `cbz`, `cb7`, `cbr` or `pdf`, else `null`; both are `null` for an issue without a file. `progression` is the caller's state: `1` when completed, else its `progression`, else position over duration, `null` when the caller never opened the issue. `finished` is the state's `completed`.
11. A list item of `GET /api/media?type=comic` and of the recently-added list carries `comic: {publisher, startYear, issueCount, readCount}`: the issues of the volume in the readable editions, and the ones the caller completed. Other lists (collections, playlists) carry none yet.
12. A comic counts in `GET /api/media/counts` and `GET /api/counts` under `comics`, in a user's `comicQuotaLimit` (read and written like `bookQuotaLimit`, `users.md` rule 19) and in the social stats as `comicsFinished`, the number of volumes finished (rule 13).
13. A comic is `watched` (and finished) when it has an issue with a part and every issue with a part is completed, the series rule (`media-query.md` rule 20) over its ungrouped items; its `progressPercent` is 100 then, else the progress of the most recently played unfinished issue (its `progression` when set, else position over duration, `books.md` rule 21).

## Ingest

15. A comic library (`"comic"` in `libraries."mediaTypes"`) owns the files whose extension is `cbz`, `cb7`, `cbr` or `pdf`. One file is one issue; the folder holding it is the volume (a file at the library root is a volume of its own). A library that also takes books keeps `.cbz` and `.pdf` as books (`book-ingest.md`): comic files are then `cb7` and `cbr` only. In a book library a `.cbz` stays a `text` file.
16. The orphan scan lists one group per volume, `media_type` `comic`, `group_key` `comic:<folder>`, the folder as `folder_name`, the title and year from `fliks_domain::comics::name::parse_path` (the folder name without its bracketed groups, a `(2016)` year). That function also reads the issue from the file name: the last standalone number (`001`, `#1.5`, `-1`, canonical decimal text, leading zeros dropped) is `label` and `sort`; a name with no number has the file stem as `label` and no `sort`; the word `annual` or `special` sets `kind`. Rule 31 extends it.
17. `register` writes the `media_files` row (`quality` = the format), then in one transaction, under the media's versions lock: the volume's empty `comic_details` row and `image` edition (created when missing), an ungrouped item and a `comic_issues` row per new file (`kind`, `sortNumber`, `label`, `pageCount`), and its `item_parts` row. A file already linked to an item is left alone.
18. An issue is addressed by `("mediaId", kind, "sortNumber")`: a file whose key matches an existing issue, a variant cover or a second scan of the number, becomes the next `version` of that issue's item, never another issue, and `"pageCount"` follows the file of the highest version. A file with no number is keyed by its `label` (its stem) instead and gets the next free `"sortNumber"` from 100000 up (a number in a name has at most four digits), so two unnumbered files are two issues and none is issue `0`. An issue whose file was removed keeps its item and takes the next file of its key.
19. `editions.format` is the format of every part file when they all share one, else NULL, recomputed at each registration; the format of an issue is that of its part file (its extension).
20. `pageCount` is the number of page entries of an archive, read from the entry list, NULL for a PDF (not paged by the server) and for an archive that cannot be read. The volume's poster, when it has none, is the first page (natural order) of the lowest issue, as a JPEG of at most 1000 px, stored like a book cover. A PDF has no cover.
21. A comic file enqueues no video or audio job: the post-import enrich, the subtitle scheduler, the sprite and marker settle all skip the `image` family. A comic rescan refreshes the rows and the page count of changed files and registers the new ones, as a book rescan does.

## Archives

22. The format is read from the magic bytes, never the extension: a zip (a `.cbr` that is really a zip too) is read in process with the `zip` crate; 7z and RAR with libarchive, built and linked on Linux only (the Docker image; other platforms answer `Unsupported`). libarchive runs in a child process (`comics/sandbox.rs`), because it allocates from a header's entry count before any entry is seen (a few KB of 7z can ask for gigabytes) and a memory-safety bug must stay out of the server. The parent opens the archive and passes it as the child's stdin (the child gets no path) and re-executes the server image as the hidden subcommand `comic-archive`, run before any async runtime exists. **Isolated:** allocation (`RLIMIT_AS` 1 GiB), CPU (`RLIMIT_CPU` 120 s and a 120 s wall-clock kill, race-free against pid reuse), crashes, privileges (as `nobody` when the server is root, `no_new_privs`, killed with its parent, an empty environment, descriptors beyond stdio close-on-exec) and file writes (`RLIMIT_FSIZE` 0). **Not isolated:** the network and whatever of the filesystem `nobody` can read; there is no seccomp filter yet. The answer comes back on stdout and the parent bounds what it reads (a reported page count over 5 000 is refused); a child that is killed, limited or cut short is an unreadable archive (422). Budgets, caches and the job slots stay in the parent. In the child `comics/ar.rs`, the one `unsafe` module, is a minimal reader over `libarchive2-sys`: formats limited to 7zip, rar and rar5, no filter and so no external program, a header warning is not an error, names are read as UTF-8 under a thread-local `C.UTF-8` locale made once (the image runs in the C locale; the parent logs once when the system has none), the handle is freed on every path. Nothing is extracted: entries are read into memory in archive order. libarchive is never let skip an entry (its own skip decodes a solid block outside any budget): every entry except an empty directory (rar5 refuses to read one) is read to its end through the operation's byte budget.
23. A page is a regular entry whose extension is `jpg`, `jpeg`, `png`, `webp` or `gif`. Directories, symlinks, hardlinks, devices, hidden entries (a segment starting with `.`), `__MACOSX`, names with a NUL, a leading `/`, a drive letter, an empty or `.` or `..` segment, and every other extension (nested archives included) are not pages. A backslash is a separator. Pages are in natural order (digit runs compare as numbers, case ignored); the entry name is only a key, and an entry is addressed by its position in the archive, so two entries with one name are two pages.
24. Limits, enforced while reading and not only from declared sizes: 20 000 entries, 5 000 pages, 64 MiB per entry, 2 GiB read per operation (every byte libarchive decodes, solid blocks and non-page entries included) and, for 7z and RAR, no more than 100 times the file (1 MiB floor) whatever the headers declare (a rar5 redirect declares 0 and still decodes), uncompressed over compressed at most 100 (1 MiB floor) per zip entry. The page list of a zip probes dimensions within 64 MiB of reads in all; pages past it list as `0 x 0`. Over a limit the archive is `TooLarge` (413). Encrypted entries, an unsupported zip method, an unreadable archive, no page, a PDF: 422.
25. Every decode goes through `image::Limits` and a 25 million pixel cap; a corrupt or oversized page is an error for that page only (the page list keeps its index with `0 x 0`), never a panic. A libarchive read error (a `read_data` warning included) refuses the whole 7z or RAR: the stream after it cannot be trusted. Decoding runs on the blocking pool, three at a time: the slot is held by the job itself until it returns. The ingest page count and cover have one slot of their own, so a library scan cannot starve the readers. One job holds at most the page bytes (64 MiB), the decoder's 200 MB allocation and its RGB copy (75 MB), so the peak is about 3 x 340 MB, 4 x with the ingest's slot, and a request waiting for another's cache fill (rule 28) holds its slot meanwhile; entry buffers are sized to the declared size and shrunk, and the page cache counts capacity.

## Pages

26. `GET /api/comics/:itemId/pages` answers `{ pages: [{ width, height }] }` and `GET /api/comics/:itemId/pages/:index?width=<px>` the page, 0-based. Both take `FileBoundAuthed` (cookie, bearer or the `?token=` credential) and `media.read`: a session token reads any readable issue, a stream token only when it is bound to the file the issue resolves to (an unbound stream token is 401, another file 404). The file is the one the detail payload names for the caller: both call the SQL function `comic_part(item, user)` (`items.md` rule 35: the state's file while it is a part, else the first part of the state's version, else of the highest version), so a token bound to that `mediaFileId` keeps working when a newer version appears. A missing or hidden issue is `404 Item #<id> not found`, a PDF part `404 Issue #<id> is a PDF`, an index out of range `404 Page not found`.
27. Without `width` the original bytes are served when the content sniffs as jpeg, png, webp or gif (the sniffed type, never the entry's name), else the page is re-encoded; with `width` (1 to 4096, else 400, then rounded up to the next multiple of 256) it is downscaled to it with `thumbnail_exact`, never upscaled, as JPEG; a JPEG no wider than the width is served as stored, not re-encoded. Answers carry `X-Content-Type-Options: nosniff`, a CSP of `default-src 'none'; sandbox` and `Cross-Origin-Resource-Policy: cross-origin`.
28. `ETag` = file row, size, mtime, inode, ctime, index and rounded width; `If-None-Match` answers 304 before any archive work; pages and list are `Cache-Control: private, no-cache` (revalidated, never `immutable`: the ACL can change). Small in-process caches serve the routes, keyed by the file's identity: the page list (64 archives), and for a solid archive (7z, RAR) the decoded pages (256 MiB of capacity in all, oldest evicted first), or, when they do not fit, the archive position of each page so that a page is one pass. They are filled by the first list or page request, one fill per archive at a time (concurrent first requests wait for it).
29. Progress is the existing playback state (`plans/comics-contract.md`, Progress); the server adds nothing. The OPDS-PSE stream URL (`opds.md` rule 19) serves these same pages under the OPDS credential.

## Acquisition

38. A comic is searched issue by issue, never as a volume: a trade paperback or a run of issues is never grabbed for one issue (`release.md` rules 68-70). The volume's `image` want has no language and the quality profile of its family (none: every `image` quality). Only issues that exist as items are wanted. Ingest makes an item per file (an unnumbered file included, rule 18), so a volume that came from ingest alone has no issue without a file and the server never invents a gap in its numbering. Issues without a file come from a metadata provider or from manual entry. An issue is wanted when it is monitored, has no part and has a release date not after today: an undated issue is not yet wanted, anywhere (wanted list, candidates, `releases.match`). Deleting the file of an issue (`DELETE` of a media file, the cleanup job) unmonitors that issue when it has no other part, so a file the user removed on purpose is not downloaded again; re-monitoring the issue wants it again.
39. `media.acquisitionContext` of a comic answers the volume (`scope` `[]`, `want` null, `year` the start year (`comic_details."startYear"`, else `media.year`), no creators or editions) or, with `itemId`, one issue: `scope` is one `Unit` (`itemId`, `title`, `airDate`, no group) whose `ref` is `{number, label}`, `number` being the canonical printed number (`sortNumber` for an issue or an annual, the label for a special, whose `sortNumber` is a rank) and `label` the printed number, led by `annual ` or `special ` for those kinds (`annual 2`); `want` is `missing` while the issue has no part, else `skip` (an issue is never upgraded), with the profile's allowed `image` qualities. A `groupId`, an `itemId` of another media, or an issue whose number is outside the number grammar of rule 31 (`abs < 10000`, at most two decimals: no release name can say it) is null; a language or a family but `image` is `ERR_VALIDATION`. Targets of `acquisition.candidates` and `releases.match` skip such an issue the same way.
40. `releases.score` of a comic is `score_and_sort_book_releases` of `image` (`release.md` rule 70) with the sizes of `quality_definitions` of the family. A `unit` is read as the issue wanted: `number` canonical, the kind from the lead word of the label (`annual`, `special`, any case); a group, end-number, absolute, a number outside the grammar or a label whose number is not `number` is `ERR_VALIDATION`. The other issues and the trades are rejected, and so is a release whose year is before the volume's start year or more than one year from the issue's release date (`YEAR_MISMATCH`); without a unit nothing is rejected on the number or the year. `releases.match` of a title that names comic volumes parses it (`parse_comic_release`) and picks the volume among those the title names: the one whose `comic_details.volume` is the release's volume number, else the one with the latest start year not after the release's year, else the first; a release older than every volume is `not-available`. A collected release or one without a number is `not-available`; else the issue of that kind and number of the volume (a special by its label's number), `not-available` when it does not exist or the volume has no `image` want, then `on-disk`, `not-monitored`, `too-fresh` (a release date in the future or none, or `minAgeMinutes`), else `grab` with the issue as `unit` (also on the skips of an existing issue).
41. `acquisition.candidates` lists one target per wanted issue: a monitored volume with an `image` want, a monitored issue item with no part and a release date not after `availableOn`, sorted by `(mediaId, 0, itemId)` (`kind` `comic` and family `image` filter as for books). The want of a volume is satisfied when none is left (`wants-follows.md` rule 2).
42. `library.ingest` of the family `image` takes comic files only (`cbz`, `cb7`, `cbr`, `pdf`) into a comic and runs the ingest of rules 15-21: one archive is one issue, keyed by `ComicInfo.xml` then the file name (rule 18; a special by its label), so a download named like its issue joins the wanted issue's item as its first version. A comic file keeps its own name in the volume folder (never the book file format, which would drop the issue number), and one whose name is taken there is `already present`. A comic file that names no issue becomes an unnumbered issue (rule 18), not the wanted one: a caller checks that `imported[].itemIds` holds the item it grabbed for and treats a miss as a failed grab (the download plugin blocklists the release). A `language` is `ERR_VALIDATION`, as for video. An `acquisition-event` of the family `image` may carry a unit, which the host ignores.

## Local metadata

31. `parse_path` also reads `volumeNo` (a `v2`, `Vol. 2` or `Volume 2` token in the folder, else the file name; the token is not part of the title or the number). An issue number is `name::number`: `-?` up to four ASCII digits and at most two decimals (`001.50` is `1.5`), anything else (`1.2.3`, `--1`, `.`, `12345`, full-width digits) is no number. It must stand alone in the name: after a separator, before a blank or the end, so `Series 2099 001` is issue 1 and `Series 1.2.3` has none. A dash before a zero-padded number is a separator: `-001` is 1, only `-1`, `-1.5` and `#-1` are negative. `of N` is ignored only right after a number (`001 of 012`, `001 (of 12)`: 1). The word `annual` or `special` sets `kind` and leaves the title only when it is the last word before the number (or the last word of a name without one): `Special Forces 001` is an issue of `Special Forces`. A `#`, `-` before the number is not part of the title; a volume folder holding only a token (`Volume 2`) gives the title of the file name. Golden vectors: `fixtures/comics-names/cases.json`.
32. `fliks_domain::comics::info::parse` reads a `ComicInfo.xml` (Anansi v2.0/2.1): the root must be `ComicInfo`, a DTD is refused, entities stay literal (only the predefined and numeric references are decoded), a malformed document is an error. It keeps `Series`, `Number`, `Volume` (0 to 9999), `Year`, `Month`, `Day`, `Title`, `Summary`, `Publisher` and `Format` (a text field is cut at 8000 characters, an out of range number is dropped). Credits, `Count`, `LanguageISO`, `Manga` and `GTIN` are not read: the comic model has no persons, reading direction, language or identifier column. Golden vectors: `fixtures/comics-info/cases.json`.
33. `info::resolve(name, info)` combines the two per field, `ComicInfo.xml` first: `Number` (an integer or decimal, optionally negative; else the file name's) gives the label and sort key; `Format` `Annual` gives kind `annual`, `Special`, `TPB`, `Omnibus` and `Hardcover` give `special`, else the file name's kind; a `Volume` of four digits is the year the run started (the Mylar convention), else the volume number; the title is `Series` else the folder or file name's; `Year`, `Month`, `Day` give the release date (`YYYY-MM-DD`, a missing or impossible month or day is `01`).
34. The `ComicInfo.xml` of an archive is the root entry of that name, any case, at most 1 MiB, read by `comics/archive.rs` like a page: a zip entry through the ratio cap and the operation budget, 7z and RAR in the sandboxed child (`info` operation, answer capped at 1 MiB) with a 256 MiB decode budget. Any failure (absent, too large, encrypted, unreadable, not valid) leaves the file name alone and logs a warning; a PDF has none. The orphan scan reads the first unlinked file of a volume (its `Series` is the group's title and its start year the group's year; the volume is still the folder) and `register` reads each new file again: a file is read once per scan and once per registration.
35. `register` applies `resolve` to each new file: the issue's label, sort and kind key (rule 18), `items.title`, `items.overview` (the summary) and `items."airDate"`; the volume's `comic_details` `publisher`, `startYear` and `volume` take a value only where they are NULL. A file that joins an existing issue as a version fills that issue's NULL title, summary and date. `media.title`, `overview` and `year` are never written by ingest. Nothing is refreshed for a file already linked.
36. Locks: a field edited by hand is locked and no scan fills it, even when its value was cleared. A volume's locks are `media_field_sources` rows with `provider` NULL and `locked` (`title`, `overview`, `year` for the start year, `publisher`, `details` for the volume number), the table of `metadata-orchestrator.md` rule 34. An issue's are `comic_issues."lockedFields"` (`label`, `sort`, `kind`, `title`, `overview`, `releaseDate`, a CHECK keeps the set closed), added by `1789000000720_comic-locks.sql`, which backfills nothing. A lock is removed by `unlock` (rule 37).
37. `PATCH /api/media/:id/comic` (`update:media`, the media readable by the caller, a comic else 400) takes `title` (not empty, at most 500 characters), `overview` (at most 10000), `publisher` (at most 255; `""` or `null` clears), `startYear` (1 to 9999, also written to `media.year`), `volume` (>= 0) and `unlock`; an unknown key is 400. `PATCH /api/comics/issues/:itemId` takes `number` (the label, not empty, at most 255), `sort` (a number between -9999 and 9999 with at most two decimals, the grammar of rule 31), `kind` (`null` is 400), `title`, `overview` (clearable, same caps), `releaseDate` (`YYYY-MM-DD`, `null` clears) and `unlock`; a `(kind, sort)` another issue of the volume holds is 409, an issue that is unknown or whose edition is outside the caller's libraries (`COALESCE(editions."libraryId", media."libraryId")`) is 404. `unlock` is a list of the body's field names (`startYear`, `volume` for a volume; `number` for the label) that removes their locks, the values staying as they are until the next scan fills them; a field set and unlocked by one body is 400. Both answer the `ComicDetail` of rule 9, lock the fields set by the body and run in one transaction under the media's versions lock (`items.md` rule 35), the lock `register` holds, so an edit and a registration never interleave. The poster has no upload route: `PUT /api/media/:id` `posterUrl` is the existing path.

## Providers

38. A comic provider is a plugin that declares the kind `comic` with `search work children` (record shapes: `provider-plugins.md` rules 60-62). None is bundled and no key is compiled in: the credentials are the admin's own plugin settings (`secretsSet`, `requires`) and the limits the manifest's `limits` and the provider's own signals (`provider-plugins.md` rules 17 and 57). With no provider available a comic library works on local metadata alone: `GET /api/metadata/search/comic` answers `[]`, the preview and the import through a provider that is not available answer 503, and nothing else changes. The order is `metadata.provider_order.comic`, else the plugins in registration order. `GET /api/metadata/providers` carries `serving.comic`: `[{provider, label, url}]` of the available comic providers in that order, `url` being the `homepage` of the plugin's manifest or null.
39. `GET /api/metadata/search/comic` is the comic case of the one search handler (`metadata.md` rules 6-12): `q`, `year`, `page`, `provider` and `mediaId`, an empty `q` is `[]`, `provider` a registered provider that supports comics. A hit with no `externalId` the namespace accepts or no `title` is dropped. A `ComicSearchResult` is the core of `metadata.md` rule 9 (`mediaType: 'comic'`, `posterUrl`) and `{publisher, volume, issueCount, overview, sourceUrl}`; `existingMediaId` is the lowest comic of a library the caller can read that holds the id (`media_external_ids`), else null.
40. `GET /api/metadata/{provider}/comic/{externalId}` (`Authed`) answers a `ComicPreview`: the hit fields of the work record plus `description` (the work's `overview`), `issues: [{number, sort, kind, title, releaseDate}]` (the children after the checks of `provider-plugins.md` rule 61, in the order of rule 9) and `attribution: {provider, name, url}`. An unknown or unsupporting `provider` is 400 `Unknown provider: <name>`, an id the namespace refuses 400 `Invalid id for provider: <name>`, an upstream 404 is 404 `not_found`, any other failure 503. Work and children go through their snapshots (`metadata-orchestrator.md` rule 29).
41. `POST /api/media/import` with `type: 'comic'` takes `provider`, `externalId`, `libraryId?` and `folderId?` (`wants`, `qualityProfileId`, `languageProfileId` and `monitoredSeasons` are refused as unknown properties) and needs `media.create`. The library is resolved like the book import (`book-metadata.md` rule 21); an id already linked to a comic, or a comic of the library that already has the volume's `folderName` whatever its origin (ingest or another provider), is 409 `This title is already in the library` (the second names the volume to identify instead). The work and the children are read before any row is written (an upstream failure leaves nothing). The media is then inserted (`type` `comic`, the title, the year, `folderName` from `naming_book_folder_format`, `preferredProvider` the provider, `create_shell`), the provider id linked, and rule 42 writes the rest; when it fails the media is deleted. `media.imported` follows; 201 is the `MD` of the comic with its `comic` object (rule 9).
42. The write shared by the import, identify and refresh runs in one transaction under the media's versions lock (rule 37). The volume: `media.title`, `overview`, `year` and `posterUrl`, `comic_details` `publisher`, `startYear` (the provider's `year`) and `volume`, each only from a value the provider gave and unless it is locked (the poster only when the download to the image store succeeded: a remote URL is never stored) (rule 36: `title`, `overview`, `year`, `publisher`, `details`, `posterUrl` rows of `media_field_sources`); the provenance of the fields written replaces the unlocked rows of those fields in `media_field_sources` and leaves the others, so a second provider keeps the entries of what the first wrote. The issues are merged, in a fixed number of statements whatever their count, with the issues the volume has, by the provider's key `(kind, sortNumber)` compared as exact numbers and, for a `special`, by `label` (a provider's special sort is a rank, not a number); the key is kept in `comic_issues."providerKind"`, `"providerSort"` and `"providerLabel"` (set when the issue is created or first edited, NULL: the live values), so an issue renumbered by hand still matches:  a match takes the provider's `label` (a special keeps its own, and a new special's label is stored as printed), `title` and `releaseDate` (`items.title`, `items."airDate"`) when the provider gave one and the field is not in the issue's `"lockedFields"`; an issue the volume lacks is created (a special whose rank another special holds takes the next free sort) as an item of the `image` edition (created when missing) with no part, `monitored` only when the volume is and the issue is undated or released after today (a monitored volume wants its coming issues, not the back catalogue, which the user can monitor; an issue already there keeps its flag) and its `comic_issues` row; an issue the provider no longer lists, a file, a `pageCount` and a field never written by the provider stay as they are. A later scan of the volume's folder joins a file to the issue of its number (rule 18).
43. Identify and refresh: `POST /api/media/:id/identify` with `provider` and `externalId` of a comic provider links the id and pins `preferredProvider` (`media-write.md` rules 47-50), `POST /api/media/:id/refresh` re-reads it; for a comic both end in rule 42 from the provider the media is pinned to, else the first comic provider whose id the media holds, and a comic with no such id is 400 for both (identify also needs a comic provider's `provider` and `externalId`; a `tmdbId` or `tvdbId` alone is 400). The work runs at background priority: nobody waits on it. The snapshot TTL of the plugin's manifest decides whether the provider is called (`metadata-orchestrator.md` rule 31). The scheduled `RefreshMetadata` does not refresh comics.
44. Attribution. The media detail's `providers` (`metadata-orchestrator.md` rule 42, not `comic.providers`) is `[{provider, name, url}]`, one entry per plugin namespace that holds an id of the volume in `media_external_ids` or a provenance row in `media_field_sources`, ordered by `provider`: `name` is the namespace's stored label, `url` the `homepage` of the package's manifest when it is an `https` URL, else null. An uninstall keeps the ids and field sources (`provider-plugins.md` rule 27), so the entry stays with a null `url` while the namespace row does; `deleteData` removes all three and the entry with them. Comic Vine requires a link back to it wherever its data shows and limits its use to non-commercial purposes: the client shows these links beside the volume and on a preview, and a volume whose data came from it carries its entry for as long as its id or a field source remains.

45. Volume fields come from the file record: the lowest issue's `ComicInfo.xml` resolved by rule 33 gives the volume's `title` (`Series`), `overview` (the issue's summary), `year` (the run's start year), `publisher` and `volume`. `register` never writes them; the settle of a comic and a refresh of a comic with no provider id merge that record alone (`metadata-orchestrator.md` rule 40), and rule 42's write merges `[provider, file]`, the provider first, through `media::write::fields::apply`. Rule 35's NULL-only rule for `comic_details` is replaced by the lock rows of rule 36. Rule 43's 400 for a comic with no provider id is gone: its refresh re-merges its files.
