## Rules

### A. HTTP client (`createEngineClient`)

1. Base URL has one trailing `/` stripped; every call sends `Authorization: Bearer <token>`; `Content-Type: application/json` only when a body is present (body `JSON.stringify`); no other headers. `[ts:src/modules/engine/engine-client.ts:60]–[ts:src/modules/engine/engine-client.ts:80]` Engine side: control plane is bearer `FLIKS_ENGINE_TOKEN`, loopback. `[engine:PROTOCOL.md:9]`
2. The reply is parsed as JSON only when `content-type` contains `json` (a parse failure yields `undefined`). A 2xx gives `{data, response}`; any other status gives `{error: <parsed JSON body, e.g. {code}>, response}`. A 2xx without a JSON body (204) has `data === undefined`. `[ts:src/modules/engine/engine-client.ts:81]–[ts:src/modules/engine/engine-client.ts:86]`
3. `{name}` placeholders in the path are replaced by `encodeURIComponent(String(v))`; query entries whose value is `undefined` are dropped, others `encodeURIComponent`-encoded as `k=v&k=v`. `[ts:src/modules/engine/engine-client.ts:47]–[ts:src/modules/engine/engine-client.ts:58]`
4. `stream('/v1/events', signal)` is a raw `GET` with `Accept: text/event-stream` and the bearer, aborted by the caller's signal; the `Response` is returned unread. `[ts:src/modules/engine/engine-client.ts:93]–[ts:src/modules/engine/engine-client.ts:100]`
5. There is no request timeout anywhere in the client; transport failures reject. Only the retry loops of rule 27 have deadlines. `[ts:src/modules/engine/engine-client.ts:72]` [new] Rust: control calls time out after 10 s; `GET /v1/events` has none (the 45 s idle watchdog of rule 49 ends a dead connection).

### B. Boot, hello poll, adopt

6. Configured engine = saved `engine_url` (trimmed, non-empty) else env `FLIKS_ENGINE_URL`; token = saved `engine_token` (trimmed, non-empty) else env `FLIKS_ENGINE_TOKEN`. Saved values are read from settings only at init and on `reconfigure()`. Url or token empty: error log `FLIKS_ENGINE_URL/FLIKS_ENGINE_TOKEN unset: playback is unavailable without the engine`, no client, no polling. `[ts:src/modules/engine/engine.service.ts:209]–[ts:src/modules/engine/engine.service.ts:243]`
7. Boot awaits the handshake (`onModuleInit` returns `whenReady()`, resolves whatever the outcome). `[ts:src/modules/engine/engine.service.ts:199]–[ts:src/modules/engine/engine.service.ts:207]` Consumers start themselves after it (`HostHardwareService`, `EngineEventsService`, live TV config). `[ts:src/modules/streaming/host-hardware.service.ts:32]–[ts:src/modules/streaming/host-hardware.service.ts:36]` `[ts:src/modules/streaming/services/engine-events.service.ts:75]–[ts:src/modules/streaming/services/engine-events.service.ts:78]`
8. `connect`: up to 20 attempts of `GET /v1/hello`, 500 ms apart (the sleep also follows the 20th failure). A hello that throws or is non-2xx counts as no answer. First answer: `adopt`; adopted: next poll in 10 000 ms. 20 failures: error log `engine did not answer /v1/hello: no playback until it does, retrying in the background`, next poll after `backoff()` = delay doubling from 500 (1000, 2000, 4000, 8000, then 10 000 cap `POLL_MS`); `delay` is reset to 500 by a successful adopt. `[ts:src/modules/engine/engine.service.ts:98]–[ts:src/modules/engine/engine.service.ts:102]` `[ts:src/modules/engine/engine.service.ts:312]–[ts:src/modules/engine/engine.service.ts:336]` `[ts:src/modules/engine/engine.service.ts:347]–[ts:src/modules/engine/engine.service.ts:354]` `[ts:src/modules/engine/engine.service.ts:391]–[ts:src/modules/engine/engine.service.ts:394]`
9. `adopt(hello)`: refused when `protocolVersion < 1` (log `engine protocol P < 1 (engine V): engine disabled`) or when `features` lacks `probe` or `capabilities` (log `engine lacks features a, b: engine disabled`). Refusal: `client = null`, returns false and **no poll is scheduled** (a refused engine is never retried until `reconfigure`). `[ts:src/modules/engine/engine.service.ts:85]` `[ts:src/modules/engine/engine.service.ts:95]` `[ts:src/modules/engine/engine.service.ts:357]–[ts:src/modules/engine/engine.service.ts:374]` Engine side: `hello` = `{engineVersion, protocolVersion, features[], instanceId}`. `[engine:PROTOCOL.md:3]` `[engine:crates/core/src/api.rs:41]` [new] Rust: a refusal never stops the poll; it retries with the hello backoff of rule 8 and the engine stays degraded (`status: down`) until it is adopted.
10. On acceptance: `GET /v1/config`; `revision = cfg?.revision ?? 0` (a non-2xx gives revision 0); `lastPushed = ''` (forces the next push); `instanceId`, `features` stored; client adopted; `reachable = true`; log `engine <v> hello OK (protocol P, features a,b)`; when `notify` is set the `onConnect` listeners run. A thrown `GET /v1/config` propagates (at boot it rejects `whenReady`; inside the poll it is caught). `[ts:src/modules/engine/engine.service.ts:375]–[ts:src/modules/engine/engine.service.ts:389]` [new] Rust: a failing `GET /v1/config` (transport) never aborts the boot or the poll, it counts as no adoption and retries like rule 9; a non-2xx still gives revision 0.
11. Derived state: `enabled` = client adopted; `runtime` = enabled and `features` contains `sessions`, `serve` and `events`; `status` = `'off'` if no URL is configured, else `'down'` if no client but a candidate exists, `'off'` if neither, else `'up'` when the last hello answered and `'down'` otherwise; `gatewayMismatch` = saved URL and `FLIKS_ENGINE_URL` both non-empty and different after trimming trailing slashes; `engineFeatures` = features of the adopted engine (empty without one). `[ts:src/modules/engine/engine.service.ts:97]` `[ts:src/modules/engine/engine.service.ts:169]–[ts:src/modules/engine/engine.service.ts:197]` `[ts:src/modules/engine/engine-remote-config.ts:35]–[ts:src/modules/engine/engine-remote-config.ts:44]`
12. Poll every 10 000 ms (`unref`'d timer): `hello`; `reachable = !!hello`. No answer: next in 10 s if connected, else `backoff()`. Same `instanceId` as adopted: next in 10 s. Otherwise (engine restarted, or never connected): if connected log `engine restarted: reloading config and capabilities`; `adopt(notify=true)`; accepted: next in 10 s; refused: polling stops; thrown: next in 10 s. `[ts:src/modules/engine/engine.service.ts:403]–[ts:src/modules/engine/engine.service.ts:426]`
13. `reconfigure()`: `epoch++`, timer cleared, client/candidate dropped, `reachable=false`, `ready = init(notify=true)`, awaited; if still the current epoch and a client was adopted, `await push()`. Every await in `init`/`connect`/`adopt`/`tick` checks the epoch, so a handshake begun before a reconfigure never adopts. `[ts:src/modules/engine/engine.service.ts:163]–[ts:src/modules/engine/engine.service.ts:164]` `[ts:src/modules/engine/engine.service.ts:230]–[ts:src/modules/engine/engine.service.ts:258]`
14. `testConnection(url, token, probePath?)`: url/token trimmed, empty ones fall back to the configured/effective ones; both still empty: `{ok:false, error:'Engine URL and token are required'}`. Own client, `GET /v1/hello`; no data or non-2xx or throw: `{ok:false, error:'The streaming engine at <url> did not answer'}`. Success: `{ok:true, engineVersion, protocolVersion}` without any protocol/feature check. With a non-blank `probePath` (trimmed): `POST /v1/probe {media:{mediaFileId:0, path}}`: non-2xx adds `probeOk:false, probeError:'probe -> <status>'`; `ok:false` body adds `probeOk:false, probeError: error ?? 'Probe failed'`; 2xx ok adds `probeOk:true`; a throw adds `probeOk:false, probeError:'Probe did not answer'`. Never adopts the engine. `[ts:src/modules/engine/engine.service.ts:261]–[ts:src/modules/engine/engine.service.ts:309]` `[engine:PROTOCOL.md:29]`

### C. Config owner (serialized, revisioned push)

15. Inputs held in memory: `streaming` (set by `pushStreaming`), `livetv` (set by `pushLivetv`, "goes out with the streaming ones, which the engine needs first"), `pathMappings` (settings, rule 28), `hostToken`. `push()` does nothing while no client or no `streaming` is known. `[ts:src/modules/engine/engine.service.ts:429]–[ts:src/modules/engine/engine.service.ts:445]`
16. Serialization: each push runs after the previous one settled (`pushing` promise chain; a failure rejects only its own caller, the chain continues). `[ts:src/modules/engine/engine.service.ts:440]–[ts:src/modules/engine/engine.service.ts:465]`
17. Dedupe: key = `JSON.stringify({streaming, livetv, pathMappings})` (key order of the objects as built: `toEngineStreaming` order, rule 21); equal to `lastPushed` returns without a request. `hostUrl`, `hostToken` and `lifetime` are not in the key (constant per process). `[ts:src/modules/engine/engine.service.ts:445]–[ts:src/modules/engine/engine.service.ts:446]`
18. Request: `PUT /v1/config` body `{revision: <revision+1>, hostUrl, hostToken, streaming, livetv?: <only when set>, pathMappings?: <only when non-empty>, lifetime}`. Non-2xx: `Error('PUT /v1/config -> <status>')` thrown and `revision`/`lastPushed` untouched (so the same revision is retried by the next push); 2xx: `revision++`, `lastPushed = key`, log `config pushed (revision N)`. Engine: 409 on a lower revision; the first push is needed before sessions/decide (400 before). `[ts:src/modules/engine/engine.service.ts:447]–[ts:src/modules/engine/engine.service.ts:461]` `[engine:PROTOCOL.md:26]` `[engine:PROTOCOL.md:31]` `[engine:PROTOCOL.md:32]` [new] Rust: a 409 refetches the revision from `GET /v1/config` and retries (5 attempts, 100 ms doubling); other statuses fail as above and the poll retries the push while `lastPushed` is unset.
19. `hostUrl()` = env `FLIKS_HOST_URL` when non-empty, else `http://127.0.0.1:` + (`Number(PORT) || 4848`). `hostToken` = 32 random bytes as 64 hex chars, regenerated at every process start, presented by the engine as the resolver bearer. `[ts:src/modules/engine/engine.service.ts:86]–[ts:src/modules/engine/engine.service.ts:93]` `[ts:src/modules/engine/engine.service.ts:148]–[ts:src/modules/engine/engine.service.ts:149]`
20. Push triggers (all through `pushStreaming`, deduped): (a) `HostHardwareService.load` at boot and on every `onConnect` (settings loaded first, then push, then GPU detection); (b) any `streaming_*` setting change while the engine is enabled; (c) every playback-info call through `hardware.apply`. `pushLivetv`: any of the 5 `livetv_*` keys changing, and once after `whenReady`; the in-memory `livetv` is re-sent with every later streaming push (an engine restart re-sends it too, with `lastPushed` cleared by adopt). `[ts:src/modules/streaming/host-hardware.service.ts:32]–[ts:src/modules/streaming/host-hardware.service.ts:61]` `[ts:src/modules/streaming/streaming-settings-cache.service.ts:119]–[ts:src/modules/streaming/streaming-settings-cache.service.ts:131]` `[ts:src/modules/streaming/services/engine-playback.service.ts:111]` `[ts:src/modules/livetv/services/livetv-session.service.ts:134]–[ts:src/modules/livetv/services/livetv-session.service.ts:141]`

## Decisions (plan §15.1)

1. Nest keeps a `/v1/events` follower limited to `BgJobDone` and the live events until S7 (the engine broadcasts to several hosts); both processes hello/adopt, only Rust pushes the config. Until step 4 deletes `EngineEventsService` it is that follower.
2. Rust writing `engine_url` / `engine_token` calls the `settings-changed` bridge with `origin: "own-module-write"`; Nest re-adopts on it.
3. Nest never pushes after S2; its live TV settings reach the config owner through bridge B2.
4. An adopt refusal and a failing `GET /v1/config` never stop the poll or the boot (rules 9, 10).
5. A 409 refetches the revision and retries with bounded backoff (rule 18).
6. `qsvPreset` / `ffmpegSlots` are validated in the settings PUT (rule 24).
7. F5 shape of `GET /api/engine/remote` (rule 45).
8. The parity runner's `engine` actor sends the per-boot host token (`PARITY_HOST_TOKEN`, read from the engine's `GET /v1/config`); B1's wire shape is in `docs/bridge.md`.
9. Control calls time out after 10 s, `/v1/events` never (rule 5).
