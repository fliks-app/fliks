# Spec: events hub (SSE) and activity registry

Sources: `backend/src/modules/scheduler/{events.service.ts,system.controller.ts,activity-registry.service.ts,download-progress-cache.service.ts,sse-audience.service.ts}`, Nest `SseStream` (`backend/node_modules/@nestjs/core/router/`). Milestone: S2 step 2 (`src/events/`). Tags use full paths.

Scope: the hub, its two routes, the event catalogue, the domain bus and the three bridges `POST /internal/events`, `GET /internal/events/stream`, `POST /internal/activity`. The remote routes (`/api/remote/*`, grants, `canControl`) and presence are spec'd in `remote.md`; here only the hub half of them (target registry, attribution, household hook) is stated.

## Rules

### `GET /api/system/events`: connection

1. Auth runs once at connect (JWT extractor order cookie `fliks_access`, then `Bearer`, then `?token=`; `EventSource` cannot send headers so web uses the cookie, native clients `?token=`). The user must exist and be `enabled` (loaded with its role), else 401. A token expiring or a user being disabled later does not close the stream by itself; only rules 28-30 do. `[ts:src/modules/auth/strategies/jwt.strategy.ts:44]–[ts:src/modules/auth/strategies/jwt.strategy.ts:48]` `[ts:src/modules/auth/strategies/jwt.strategy.ts:59]–[ts:src/modules/auth/strategies/jwt.strategy.ts:68]`
2. A token with any `scope` claim (only `'stream'` is minted, for both stream and Cast tokens) is rejected by `SessionTokenGuard`: 403 `{"statusCode":403,"message":"session_token_required","error":"Forbidden"}`. No cookie/Bearer/token or invalid: 401 from the JWT guard (Nest default body). `[ts:src/modules/auth/guards/session-token.guard.ts:22]–[ts:src/modules/auth/guards/session-token.guard.ts:31]`
3. Query params, all optional, copied into the connection identity: `device` -> `targetId`, `ff` -> `formFactor`, `tvPlatform`, `name` -> `deviceName`; `userAgent` = request `User-Agent` header. Absent is stored as `null` (`?? null`); an empty `device=` is stored as `""`, which is falsy, so it behaves like absent for the eviction/announce/listing branches. `[ts:src/modules/scheduler/system.controller.ts:245]–[ts:src/modules/scheduler/system.controller.ts:251]` `[ts:src/modules/scheduler/events.service.ts:714]–[ts:src/modules/scheduler/events.service.ts:722]`
4. `targetId` is `deviceId#tabNonce` (stable across reconnects, unique per screen). A client with no `device` never becomes a remote target (never listed, never announces). `[ts:src/modules/scheduler/events.service.ts:339]–[ts:src/modules/scheduler/events.service.ts:353]`
5. Response headers (Nest `SseStream`): `Content-Type: text/event-stream`, `Connection: keep-alive`, `Cache-Control: private, no-cache, no-store, must-revalidate, max-age=0, no-transform`, `Pragma: no-cache`, `Expire: 0` (sic, not `Expires`), `X-Accel-Buffering: no`; status 200; headers flushed immediately. The socket gets keep-alive and no-delay and the idle timeout is disabled. `[ts:backend/node_modules/@nestjs/core/router/sse-stream.js:31]–[ts:backend/node_modules/@nestjs/core/router/sse-stream.js:54]` (Nest 11.1.18, `package.json` of `@nestjs/core`)
6. First bytes on the wire are a single blank line `\n` (written when the stream is piped), before any event. `[ts:backend/node_modules/@nestjs/core/router/sse-stream.js:55]`
7. Wire format of every message (Nest `SseStream._transform`): `event: <type>\n` only when the message has a `type` (only `ping` does), then `id: <n>\n`, then one `data: <line>\n` per line of the payload, then a blank line. `<n>` is a per-connection counter starting at **1** and incremented for every message written, pings included (verified by running `SseStream`: `id: 1\ndata: {"a":1}\n\nevent: ping\nid: 2\ndata: 30000\n\n`). No `retry:` line. The Rust hub must emit the `id:` lines (frozen contract). `[ts:backend/node_modules/@nestjs/core/router/sse-stream.js:58]–[ts:backend/node_modules/@nestjs/core/router/sse-stream.js:66]`
8. All events except `ping` are unnamed messages (no `event:` line); `data:` is `JSON.stringify(event)`: `undefined` fields are omitted, `null` kept. Key order is the object-literal order at the emitter. `[ts:src/modules/scheduler/events.service.ts:739]–[ts:src/modules/scheduler/events.service.ts:744]`
9. On connect, in this order, synchronously (no event can interleave): (a) a fresh `connectionId` = `randomUUID()` (v4) is minted; (b) if `targetId` is set, every existing connection of the same user with the same `targetId` is evicted (rule 22); (c) the connection is registered; (d) if `targetId` is set, `remote.targets_changed` is `emitToUser(userId)` (so the new stream itself is not yet subscribed and does not receive it; the user's other streams and household viewers do); (e) first message to this client: `sse.connected`; (f) replay of the progress cache (rule 14); (g) subscription to the live bus. `[ts:src/modules/scheduler/events.service.ts:709]–[ts:src/modules/scheduler/events.service.ts:745]`
10. `sse.connected` payload: `{"type":"sse.connected","connectionId":"<uuid>"}`, delivered only to that connection, never through the bus. The client binds `connectionId` to its live playback sessions (`sseConnectionId`). `[ts:src/modules/scheduler/events.service.ts:134]–[ts:src/modules/scheduler/events.service.ts:138]` `[ts:src/modules/scheduler/events.service.ts:728]–[ts:src/modules/scheduler/events.service.ts:733]`
11. Ping: every 30 000 ms (`setInterval`, first one 30 s after connect, per connection, not aligned) the connection receives the named message `{type:'ping', data:'30000'}`; wire: `event: ping\nid: <n>\ndata: 30000\n\n`. `data` is the interval in ms as a string; the client uses any bytes to reset its idle timeout. The ping carries data on purpose (the spec drops an empty buffer). `[ts:src/modules/scheduler/events.service.ts:389]–[ts:src/modules/scheduler/events.service.ts:390]` `[ts:src/modules/scheduler/events.service.ts:747]–[ts:src/modules/scheduler/events.service.ts:751]`
12. Delivery filter per event (`shouldDeliver`): deliver if the envelope has no audience and no connection list (broadcast); or its `connectionIds` contains this connection id; or its `audience` contains this user id. Otherwise skip. `[ts:src/modules/scheduler/events.service.ts:766]–[ts:src/modules/scheduler/events.service.ts:775]`
13. A connection receives only events emitted after step (g) plus the replay of rule 14; there is no `Last-Event-ID` handling and no history. `[ts:src/modules/scheduler/events.service.ts:742]–[ts:src/modules/scheduler/events.service.ts:745]`
14. Replay on connect: `progressCache.snapshotFor(userId)` yields every cached `download.progress` snapshot whose recipients include this user, each written as an ordinary unnamed message, after `sse.connected` and before live events. `[ts:src/modules/scheduler/events.service.ts:735]–[ts:src/modules/scheduler/events.service.ts:740]`

### Teardown

15. When the client closes (`request.on('close')`) or the hub completes the observable: the ping interval is cleared, the bus subscription removed, the completer removed, the connection deleted; if the connection had a `targetId` (read before deleting; an evicted connection no longer has an entry so reads `undefined`), `remote.targets_changed` is `emitToUser(userId)`. `[ts:src/modules/scheduler/events.service.ts:753]–[ts:src/modules/scheduler/events.service.ts:762]` `[ts:backend/node_modules/@nestjs/core/router/router-response-controller.js:85]–[ts:backend/node_modules/@nestjs/core/router/router-response-controller.js:90]`
16. Completing the observable ends the HTTP response (`response.end()`), which is how a drop becomes visible to the client (it reconnects). `[ts:backend/node_modules/@nestjs/core/router/router-response-controller.js:81]–[ts:backend/node_modules/@nestjs/core/router/router-response-controller.js:83]`

### Audiences and emit API

17. `emit(event)`: broadcast to every open connection of every user, regardless of role. `[ts:src/modules/scheduler/events.service.ts:423]–[ts:src/modules/scheduler/events.service.ts:425]`
18. `emitToUser(userId, event)`: connections owned by that user. When the event type is `remote.state`, `remote.targets_changed` or `remote.stopped`, the registered household fan-out hook is also called with `(event, ownerId)`. `[ts:src/modules/scheduler/events.service.ts:428]–[ts:src/modules/scheduler/events.service.ts:437]`
19. `registerHouseholdFanOut(fn)` is registered once by `RemoteService`'s constructor; its behaviour (grantees of the device or owner plus all enabled admins, minus the owner, via `emitToUsers`; `GRANT_CACHE_MS` 30 s cache; `remote.state` and `remote.stopped` scoped to `deviceIdOf(targetId)` = `targetId.split('#')[0]`) belongs to `remote.md`. Because it calls `emitToUsers`, which never invokes the hook, it cannot loop. `[ts:src/modules/scheduler/events.service.ts:442]–[ts:src/modules/scheduler/events.service.ts:444]` `[ts:src/modules/remote/remote.service.ts:63]` `[ts:src/modules/remote/remote.service.ts:71]–[ts:src/modules/remote/remote.service.ts:100]` `[ts:src/modules/remote/remote.service.ts:39]`
20. `emitToUsers(userIds, event)`: connections of those users; an empty list delivers to nobody (an empty array is a non-null audience). No hook. `[ts:src/modules/scheduler/events.service.ts:446]–[ts:src/modules/scheduler/events.service.ts:449]`
21. `emitToConnection(connectionId, event)` returns a boolean. Polled target (key `polled:<targetId>`): pushed to its queue, `true`; if the queue already holds 20 (`POLLED_QUEUE_MAX`) the event is dropped with a warning and `false`. SSE connection unknown: warning, `false`. Otherwise delivered to exactly that connection only. A caller must not fall back to `emitToUser` for `remote.command` (it would command every device of the user). `[ts:src/modules/scheduler/events.service.ts:458]–[ts:src/modules/scheduler/events.service.ts:485]` `[ts:src/modules/scheduler/events.service.ts:373]` `[ts:src/modules/remote/remote.service.ts:192]–[ts:src/modules/remote/remote.service.ts:205]`
   - 21a. `emitRaw(type, payload, audience)` for plugin events: wire event is `{"type":"plugin.<id>.<type>","payload":<payload>}`; `audience: null` broadcasts, else a user-id list. `[ts:src/modules/scheduler/events.service.ts:451]–[ts:src/modules/scheduler/events.service.ts:456]` `[ts:src/modules/plugins/host/fliks-host.service.ts:1073]`
22. Superseded-connection eviction (C5): on connect with a `targetId`, every other connection of the same `userId` and same `targetId` is deleted from the registry and its stream is closed by the server (Nest left the socket open). It stops being a target, receives no teardown announce and is skipped by `dropConnectionsFor*`. Rationale: a killed webview or dropped mobile network sends no FIN. Two tabs of one device have different `targetId` and coexist; connections without `targetId` are never evicted; the same `targetId` under another user is not evicted. `[ts:src/modules/scheduler/events.service.ts:570]–[ts:src/modules/scheduler/events.service.ts:579]` `[ts:src/modules/scheduler/events.service.ts:711]–[ts:src/modules/scheduler/events.service.ts:713]`
23. Each `emit*` goes through one `dispatch`: when the audience is non-null, a `download.progress` event is recorded into the replay cache with the audience as recipients, and an `import.complete` clears the cache for `(mediaId, seasonNumber, episodeNumber)`. A `download.progress` sent through `emit` (null audience) is not cached. Then the envelope is published on the bus. `[ts:src/modules/scheduler/events.service.ts:490]–[ts:src/modules/scheduler/events.service.ts:503]`
24. Backend-internal `subscribe(handler)` receives every `SseEvent` envelope's event regardless of audience (including events addressed to one connection through the bus; not polled-queue events and not `sse.connected`/`ping`). `[ts:src/modules/scheduler/events.service.ts:777]–[ts:src/modules/scheduler/events.service.ts:780]`

### Progress replay cache (`download.progress`)

25. One entry per `mediaId`: `{event, recipients, recordedAt}`. `record(recipients, event)`: empty `downloads` deletes the entry (an empty snapshot retires the media); otherwise replaces the entry (a snapshot states the whole set; no merge). `[ts:src/modules/scheduler/download-progress-cache.service.ts:47]–[ts:src/modules/scheduler/download-progress-cache.service.ts:53]`
26. `clear(mediaId, seasonNumber?, episodeNumber?)`: no entry: no-op; `seasonNumber == null`: delete the media; else keep a download if its season differs, or if an episode is given and the download's episode differs (a download with no `episodeNumber` is a pack and survives a single-episode clear); no downloads left deletes the entry. `[ts:src/modules/scheduler/download-progress-cache.service.ts:57]–[ts:src/modules/scheduler/download-progress-cache.service.ts:72]`
27. `snapshotFor(userId)`: walks all entries; any entry older than 3 min (`STALE_AFTER_MS = 3 * 60_000`, against a clock that is injectable) is deleted regardless of which user connects; returns the events whose recipients include the user. Not persisted; restart empties it. `[ts:src/modules/scheduler/download-progress-cache.service.ts:18]` `[ts:src/modules/scheduler/download-progress-cache.service.ts:77]–[ts:src/modules/scheduler/download-progress-cache.service.ts:88]` The first `download.progress` after a grab states the cached set plus a placeholder `ref: "pending:<season>:<episode>"` (producer rule, S8). `[ts:src/modules/plugins/host/fliks-host.service.ts:937]–[ts:src/modules/plugins/host/fliks-host.service.ts:975]`

### Connection drops (security)

28. `dropConnectionsForUser(userId)`: complete the observable of every SSE connection of the user (teardown of rule 15 runs, announcing `remote.targets_changed` per connection that had a target), delete every polled target of the user; if any polled target was dropped, emit `remote.targets_changed` to the user. Log line `Dropped N SSE connection(s) and M polled target(s) for user U` when either count > 0. Evicted connections are already closed (rule 22). `[ts:src/modules/scheduler/events.service.ts:651]–[ts:src/modules/scheduler/events.service.ts:676]`
29. Callers: user update when `roleChanging || enabledChanging` (`roleChanging` = `roleId` differs, `enabledChanging` = `enabled` differs, [ts:src/modules/users/users.service.ts:250]–[ts:src/modules/users/users.service.ts:251]; so re-enabling also drops) `[ts:src/modules/users/users.service.ts:328]`. Not called on `isAdmin` change, library-access change ([ts:src/modules/users/users.service.ts:351]–[ts:src/modules/users/users.service.ts:352]) or user deletion ([ts:src/modules/users/users.service.ts:396]), which only call `engine.revokeOwner`, nor on password change (neither). (S1 bridge `POST /internal/bridge/drop-connections` serves this call and rule 30's logout; deleted in S2.)
30. `dropConnectionsForTarget(userId, targetId)`: same but scoped to the caller's own device; completes SSE connections matching both, deletes `polled:<targetId>` if owned by the user; nothing found: warning `Logout target scope: no connection for user U target T` and return; polled drop emits `remote.targets_changed`. Called from logout with `payload.sub` of the verified access token (cookie, else Bearer) and the body field `targetId`; no `targetId` in the body: warning, nothing dropped; an invalid/expired access token: nothing dropped. `[ts:src/modules/scheduler/events.service.ts:678]–[ts:src/modules/scheduler/events.service.ts:703]` `[ts:src/modules/auth/auth.controller.ts:96]` `[ts:src/modules/auth/auth.controller.ts:111]–[ts:src/modules/auth/auth.controller.ts:129]`

### Target registry (hub half of remote control)

31. `listForUser(userId)` / `listAll()`: every SSE connection with a non-null `targetId` plus every non-expired polled target, each as `{connectionId, ...identity}`, sorted by `since` descending (newest first). The scan itself expires polled targets whose last poll is older than 30 000 ms (`POLLED_TARGET_TTL_MS`): deleted, log `Polled target T stopped polling`, and `remote.targets_changed` emitted to the target's owner. Expiry is lazy (only when a list runs). `[ts:src/modules/scheduler/events.service.ts:540]–[ts:src/modules/scheduler/events.service.ts:568]` `[ts:src/modules/scheduler/events.service.ts:368]`
32. `registerPolledTarget(userId, identity)`: refuses a missing `targetId` (warning, no-op). Key `polled:<targetId>`. Re-registration keeps `since` and `queue`, refreshes `lastPoll` and identity; first registration emits `remote.targets_changed` to the user. The key doubles as the connection id. `[ts:src/modules/scheduler/events.service.ts:583]–[ts:src/modules/scheduler/events.service.ts:607]` The route derives `targetId = <deviceId>#native` server-side. `[ts:src/modules/remote/remote.service.ts:267]–[ts:src/modules/remote/remote.service.ts:277]`
33. `drainCommands(userId, targetId)`: unknown target or other owner: `null` (route answers 404 `remote.error_device_offline`); else refresh `lastPoll` (no TTL check), return and clear the queue (each command at most once). `[ts:src/modules/scheduler/events.service.ts:611]–[ts:src/modules/scheduler/events.service.ts:618]` `[ts:src/modules/remote/remote.service.ts:281]–[ts:src/modules/remote/remote.service.ts:290]`
34. `resolveTarget(userId, targetId)`: among `listForUser(userId)`, the newest matching row's `connectionId`, or `null`; more than one match logs a warning. Scoping to the user is the authorization. `[ts:src/modules/scheduler/events.service.ts:623]–[ts:src/modules/scheduler/events.service.ts:633]`
35. `targetIdFor(connectionId)`: SSE connection's `targetId`, else polled target's, else `null` (also `null` for null/undefined input). `[ts:src/modules/scheduler/events.service.ts:637]–[ts:src/modules/scheduler/events.service.ts:644]` `hasConnection(id)` is `true` only for SSE connections (not polled). `[ts:src/modules/scheduler/events.service.ts:505]–[ts:src/modules/scheduler/events.service.ts:507]`
36. Attribution: `claimAttribution(targetId, userId, mediaFileId)` stores one claim per target (overwrites). `takeAttribution(targetId, mediaFileId)`: null target or no claim: `null`; the claim is deleted on any read; older than 60 000 ms (`ATTRIBUTION_TTL_MS`): `null`; file mismatch: `null`; else the claimant's user id. Claimed by `remote.command` `load` with a `mediaFileId` (after delivery); taken by playback-info, which re-claims it (fresh timestamp) when the engine open fails [ts:src/modules/streaming/services/engine-playback.service.ts:187]–[ts:src/modules/streaming/services/engine-playback.service.ts:193]. `[ts:src/modules/scheduler/events.service.ts:512]–[ts:src/modules/scheduler/events.service.ts:538]` `[ts:src/modules/scheduler/events.service.ts:371]` `[ts:src/modules/remote/remote.service.ts:213]–[ts:src/modules/remote/remote.service.ts:216]` `[ts:src/modules/streaming/services/engine-playback.service.ts:132]–[ts:src/modules/streaming/services/engine-playback.service.ts:135]`

### Domain bus (backend to backend)

37. `emitDomain(event)` publishes to `domainSubject`; `onDomain(handler)` subscribes. In-process, at-most-once, no persistence, no replay, no retry; a handler that throws or rejects is caught and logged `Domain event handler threw on "<type>": <message>` (+stack), never reaching the emitter; handlers run synchronously up to their first await. `[ts:src/modules/scheduler/events.service.ts:782]–[ts:src/modules/scheduler/events.service.ts:805]`
38. `DomainEvent` payloads (11 types) are in the Events section. The plugin contract keeps a compile-time assertion that its webhook event list equals `DomainEvent['type']`; adding a domain event requires adding it to `PLUGIN_WEBHOOK_EVENT_NAMES` too. `[ts:src/modules/plugins/plugin-registry.service.ts:64]` `[ts:src/common/plugin-contract/manifest.ts:11]–[ts:src/common/plugin-contract/manifest.ts:23]`
39. `settings.changed` exists only as a `DomainEvent` (emitted after the in-process listeners ran); there is no `settings.changed` SSE event despite plan §3.2. `[ts:src/modules/settings/settings.service.ts:42]–[ts:src/modules/settings/settings.service.ts:53]`

### `GET /api/system/activity` and the registry

40. Query: `page` default 1, `limit` default 25; each is `Number.parseInt(x, 10)` and accepted only when finite and `> 0`, else the default (so `page=0`, `page=-3`, `page=abc`, `limit=0` fall back; `limit=1e3` parses as 1; no upper bound on `limit`). `[ts:src/modules/scheduler/system.controller.ts:303]–[ts:src/modules/scheduler/system.controller.ts:309]`
41. Response `{ data, total, dropped }`: `total` = number of top-level rows (a parent and its children count as one), `dropped` = lifetime count of registrations rejected at capacity. `[ts:src/modules/scheduler/activity-registry.service.ts:115]–[ts:src/modules/scheduler/activity-registry.service.ts:138]`
42. Entry shape (`ActivityEntry`, JSON order as serialized by `toPublic`): `id: string`, `type: string`, `subject?: MediaProgressSubject`, `status: 'running'|'pending'`, `current?: number`, `total?: number`, `parentId?: string`; `undefined` fields are omitted from JSON. A top-level row additionally has `children?: ActivityEntry[]` (omitted when empty), children never nest further (a row whose parent is itself a child is in neither list nor `total`). `subject` = `{title: string, mediaId?, mediaType?: string, seasonNumber?, episodeNumber?, episodeTitle?, episodeId?}`. `[ts:src/modules/scheduler/activity-registry.service.ts:7]–[ts:src/modules/scheduler/activity-registry.service.ts:23]` `[ts:src/modules/scheduler/activity-registry.service.ts:180]–[ts:src/modules/scheduler/activity-registry.service.ts:190]` `[ts:src/common/utils/media-progress-subject.util.ts:12]–[ts:src/common/utils/media-progress-subject.util.ts:20]`
43. Order: running before pending; inside a status group, ascending insertion sequence `seq`; applied to top-level rows and, separately, to each parent's children. `seq` is assigned on first insert and kept across upserts of the same id (pending to running does not reorder). `[ts:src/modules/scheduler/activity-registry.service.ts:173]–[ts:src/modules/scheduler/activity-registry.service.ts:178]` `[ts:src/modules/scheduler/activity-registry.service.ts:156]–[ts:src/modules/scheduler/activity-registry.service.ts:160]`
44. A child whose `parentId` is absent from the registry is listed as a top-level row. Pagination slices the ordered top-level list `[(page-1)*limit, +limit)`; a page past the end returns `data: []` with the real `total`. `[ts:src/modules/scheduler/activity-registry.service.ts:118]–[ts:src/modules/scheduler/activity-registry.service.ts:137]`
45. `upsertPending(id, type, subject?, parentId?)` stores `{id, type, subject, status:'pending'}` (a re-upsert of a running id returns it to pending and drops `current/total`); `upsertRunning(id, type, subject?, current?, total?, parentId?)` stores status running. `parentId` is sticky: `parentId ?? existing?.parentId`. `[ts:src/modules/scheduler/activity-registry.service.ts:70]–[ts:src/modules/scheduler/activity-registry.service.ts:92]` `[ts:src/modules/scheduler/activity-registry.service.ts:156]–[ts:src/modules/scheduler/activity-registry.service.ts:160]`

The hub and registry are in-memory: no SQL. Audience resolution for media-scoped events lives in `SseAudienceService` (today's only caller is the plugin host, S8; the S2 forwarder receives resolved user ids, Bridges item 1). Equivalent SQL, for the port when the producers move:
