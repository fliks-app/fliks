## Rules

### A. Secret, claims, signing

1. Secret resolution: `JWT_SECRET` env if non-empty (verbatim, no trim); else `<conf>/.jwt-secret` if the file exists (content `.trim()`); else generate `randomBytes(32).toString('hex')`, `mkdir -p <conf>` mode 0700, write file mode 0600; if persisting fails, an in-memory fresh hex secret for this process. Cached for the process lifetime. `[ts:src/common/utils/jwt-secret.ts:55]`–`[ts:src/common/utils/jwt-secret.ts:87]`
2. `<conf>` = first writable of `[FLIKS_CONF_DIR.trim() || '/app/conf', <os.tmpdir()>/fliks-conf]`, probed by creating then unlinking `<dir>/.probe` (dir created recursive, mode 0700); none writable: last candidate with a warning. `[ts:src/common/utils/jwt-secret.ts:39]`–`[ts:src/common/utils/jwt-secret.ts:51]`, `[ts:src/common/constants/writable-dir.ts:14]`–`[ts:src/common/constants/writable-dir.ts:34]`
3. HMAC key bytes = the secret string's UTF-8 bytes (the 64-char hex is NOT hex-decoded). Header `{"alg":"HS256","typ":"JWT"}`. `[ts:src/modules/auth/auth.module.ts:35]`
4. Access token claims `{sub: number (user id), username: string, iat, exp}`; no `scope` key (absent, not null). `exp - iat` = `JWT_EXPIRATION` (default `'1h'`, parsed by `ms()`, see `config.md`). `[ts:src/modules/auth/auth.service.ts:180]`, `[ts:src/modules/auth/auth.module.ts:41]`
5. Stream/Cast tokens: same claims plus `scope: 'stream'`. Cast: fixed `expiresIn: '4h'`. Stream: `STREAM_TOKEN_TTL` (default `'12h'`, `ms()` grammar). No other claim (no `jti`, no media or session binding). `[ts:src/modules/auth/auth.service.ts:227]`–`[ts:src/modules/auth/auth.service.ts:234]`, `[ts:src/modules/auth/auth.service.ts:267]`–`[ts:src/modules/auth/auth.service.ts:281]`
6. Tokens issued by either process must verify in the other during the strangler: same secret file, same claim names, same HS256. Same resolver in both processes `[ts:src/modules/auth/strategies/jwt.strategy.ts:55]` (plan §7.1). Two first-boot writers can leave the processes with different secrets because `writeFileSync` has no exclusive flag `[ts:src/common/utils/jwt-secret.ts:74]`, see O9.

### B. Request authentication (extractor `Authed`)

7. Token source order, first non-empty wins, no fall-through on a bad token: (1) cookie `fliks_access` parsed from the raw `Cookie` header (split on `;`, trim, `startsWith('fliks_access=')`, first match, `decodeURIComponent` with raw fallback; an array header is joined with `'; '`); (2) `Authorization: Bearer <t>` (passport-jwt: scheme matched case-insensitively, first two whitespace-separated tokens); (3) query `?token=`. An empty value counts as absent. A stale cookie therefore shadows a valid Bearer. `[ts:src/modules/auth/strategies/jwt.strategy.ts:44]`–`[ts:src/modules/auth/strategies/jwt.strategy.ts:48]`, `[ts:src/modules/auth/request-cookie.util.ts:4]`–`[ts:src/modules/auth/request-cookie.util.ts:31]`
8. Verification: signature with the secret; `exp` enforced with zero leeway (`ignoreExpiration: false`); `nbf` honoured if present. Nest passes no `algorithms` option, so jsonwebtoken 9.0.3 accepts HS256, HS384 and HS512 for a string key. `[ts:src/modules/auth/strategies/jwt.strategy.ts:49]`–`[ts:src/modules/auth/strategies/jwt.strategy.ts:55]` Rust accepts HS256 only (Nest only ever signs HS256): `[new]` hardening, no F-number, unobservable for tokens Fliks issues; list it in README Deviations (plan §0.5).
9. After verification: load the user with its role where `id = sub AND enabled = true` on every request (no caching); none found: 401. `username` and every other claim are ignored (a renamed user's old token stays valid). `sub` missing or not an integer must be 401 in Rust (Nest would run `findOne` with an undefined id). Invalidation is only this lookup: a deleted or disabled user is 401 on the next request and a role change applies on the next request, but a password change revokes nothing (no access-token check, no refresh-token revoke: `[ts:src/modules/users/users.service.ts:238]`–`[ts:src/modules/users/users.service.ts:245]`); deleting a user cascades its `refresh_tokens` rows (`onDelete: 'CASCADE'`, `[ts:src/modules/auth/entities/refresh-token.entity.ts:18]`). `[ts:src/modules/auth/strategies/jwt.strategy.ts:59]`–`[ts:src/modules/auth/strategies/jwt.strategy.ts:69]`; sub guard `[assumed]` (unverifiable: only the server signs tokens).
10. Token scope: `scope = payload.scope ?? null`. Any non-null value is "scoped" (only `'stream'` is ever issued). `[ts:src/modules/auth/strategies/jwt.strategy.ts:67]`
11. `SessionTokenGuard` (Rust `SessionAuthed`): a scoped token gets 403 `{"message":"session_token_required","error":"Forbidden","statusCode":403}`; unscoped passes. No S1 route uses it today. Nest users of it (their own specs declare it): `[ts:src/modules/livetv/controllers/livetv.controller.ts:141]`, `:162`, `:171`, `:191`, `[ts:src/modules/scheduler/system.controller.ts:235]`, `[ts:src/modules/playback/playback.controller.ts:206]`, `[ts:src/modules/playback/playback.controller.ts:410]`, `[ts:src/modules/remote/remote.controller.ts:27]` (class-level, guard order JWT, Policies, SessionToken): 15 routes in the manifest. `[ts:src/modules/auth/guards/session-token.guard.ts:22]`–`[ts:src/modules/auth/guards/session-token.guard.ts:31]`
12. A `stream`-scope token is accepted on every route that does not declare `SessionTokenGuard`, including all 13 auth routes: it can mint new stream tokens, call `cast-info`, `me`, pairing `approve`/`deny`, and pass policy checks of `users`/`roles`. Contract today; the plan does not decide whether S1 routes become `SessionAuthed`, see O1. `[ts:src/modules/auth/auth.controller.ts:138]`–`[ts:src/modules/auth/auth.controller.ts:184]`
13. `OptionalAuthed` (plan §7.1): no S1 route needs it; unguarded auth routes ignore credentials entirely, except `logout` (rule 50). `[ts:src/modules/auth/auth.controller.ts:40]`
14. Every authentication failure (no token, bad signature, expired, unknown or disabled user) returns 401 `{"message":"Unauthorized","statusCode":401}` (no `error` key: bare `UnauthorizedException`). `[ts:src/modules/auth/strategies/jwt.strategy.ts:64]`–`[ts:src/modules/auth/strategies/jwt.strategy.ts:66]`

### C. Error bodies

15. Nest `HttpException` bodies: with a string message `{"message": <string>, "error": <reason phrase>, "statusCode": n}` (`error` = `Unauthorized`, `Forbidden`, `Bad Request`, `Not Found`, `Conflict`, `Payload Too Large`); bare exception (no message) `{"message": <reason phrase>, "statusCode": n}` with no `error` key. Key order irrelevant. Rust `AppError{status, message: Value, error}` must omit `error` for the bare form (plan §7.5 sketch always has it). Verified in `@nestjs/common` `HttpException.createBody`; examples `[ts:src/modules/auth/auth.service.ts:154]` (with message), `[ts:src/modules/auth/strategies/jwt.strategy.ts:65]` (bare).
16. Validation failure: 400 `{"message": [<class-validator messages>], "error": "Bad Request", "statusCode": 400}`; pipe is global `whitelist`, `forbidNonWhitelisted`, `transform`, no implicit conversion (JSON types are strict: `IsBoolean` rejects `"true"`, `IsNumber` accepts non-integers and rejects `NaN`/`Infinity`, `IsOptional` lets `null` through as "absent-ish" but the value stays `null`). Message text is free-form for the parity runner unless it matches `^[a-z0-9_.]+$`. Unknown body keys: 400 `property <k> should not exist`. `[ts:src/main.ts:77]`–`[ts:src/main.ts:82]`
17. Guards run before pipes: an unauthenticated or forbidden request with an invalid body is 401/403, never 400. `[ts:src/modules/users/users.controller.ts:30]`
18. `ParseIntPipe` path params: non-integer string → 400 `Validation failed (numeric string is expected)`. Pairing `:pairingId` is a plain string. `[ts:src/modules/users/users.controller.ts:75]`, `[ts:src/modules/auth/pairing/pairing.controller.ts:92]`

### E. Login, logout, refresh

29. Login lookup: user by exact (case-sensitive) `username` with `passwordHash` selected and role joined. Steps and order: (a) `serverType` defaults `local`; any other value → 401 `Media server login for <serverType> not yet implemented` before any DB access; (b) no user or `passwordHash` null (Emby-imported users) → 401 `Invalid credentials` without running bcrypt; (c) bcrypt mismatch → 401 `Invalid credentials`; (d) `enabled = false` → 401 `Account disabled` (revealed only with the right password); (e) set `lastLogin = now`; (f) issue pair (rule 31); (g) body `user = SafeUser`. `[ts:src/modules/auth/auth.service.ts:61]`–`[ts:src/modules/auth/auth.service.ts:73]`, `[ts:src/modules/auth/auth.service.ts:141]`–`[ts:src/modules/auth/auth.service.ts:171]`
30. bcrypt: cost 12 for every hash (login seed, register, create user, change password); verify accepts the stored hash as is (`$2a$/$2b$/$2y$`), no rehash on login. bcrypt ignores bytes past 72. `[ts:src/modules/auth/auth.service.ts:113]`, `[ts:src/modules/users/users.service.ts:61]`
31. `issueTokenPair`: access token (rule 4), `accessTokenExpiresAt` = decoded `exp` (fallback `now/1000 + 3600`), refresh token (rule 33), `refreshTokenExpiresAt = floor(expiresAt_ms / 1000)`. Login and pairing claims store `userAgent = null` (the controller never passes it); refresh stores the request `User-Agent`. `[ts:src/modules/auth/auth.service.ts:179]`–`[ts:src/modules/auth/auth.service.ts:194]`, `[ts:src/modules/auth/auth.controller.ts:47]`
32. The refresh token plaintext is JSON-only (login, refresh, pairing status body), never in a cookie. `[ts:src/modules/auth/auth.controller.ts:54]`–`[ts:src/modules/auth/auth.controller.ts:58]`
33. Refresh token = `randomBytes(48)` base64url (64 chars); stored as `sha256(raw)` lower-case hex (hash input = the token's UTF-8 bytes); `expiresAt = now + REFRESH_TOKEN_TTL_DAYS` days (default 60; `parseInt`, must be finite and > 0 else 60); `userAgent` truncated to 255 chars; `lastUsedAt` null. `[ts:src/modules/auth/refresh-token.service.ts:46]`–`[ts:src/modules/auth/refresh-token.service.ts:75]`
34. Rotation (`POST /auth/refresh`), strictly in this order: empty/missing `refreshToken` → 401 `Missing refresh token`; row by hash not found → 401 `Invalid refresh token`; row already `revokedAt`: if `now - revokedAt <= 30 000 ms` → 401 `Refresh token already rotated` (family untouched), else revoke every un-revoked refresh token of that user and 401 `Refresh token reuse detected`; `expiresAt < now` → 401 `Refresh token expired` (row not revoked); else set `revokedAt = lastUsedAt = now`. Then user must be `enabled` else 401 `Account disabled` (token already consumed); else issue a new pair (rule 31) and set the cookie. "Family" = all of the user's tokens, not per login chain. `[ts:src/modules/auth/refresh-token.service.ts:26]`, `[ts:src/modules/auth/refresh-token.service.ts:88]`–`[ts:src/modules/auth/refresh-token.service.ts:120]`, `[ts:src/modules/auth/auth.service.ts:201]`–`[ts:src/modules/auth/auth.service.ts:207]`
35. The Nest rotation is read-then-update, not atomic: two concurrent requests with the same live token can both succeed. Rotate + new-token insert are not in one transaction. Whether Rust keeps this or uses a conditional update is O3. `[ts:src/modules/auth/refresh-token.service.ts:90]`–`[ts:src/modules/auth/refresh-token.service.ts:118]`
36. Logout revokes by the same `revokedAt` column as rotation, so presenting a logged-out refresh token more than 30 s later triggers the family revoke of rule 34. `[ts:src/modules/auth/refresh-token.service.ts:123]`–`[ts:src/modules/auth/refresh-token.service.ts:129]`
37. Register (Nest behaviour, kept for an authorised caller): username taken (exact match) → 409 `Username already taken`; role = `Admin` if the users table is empty, else the role with `isDefault = true`; if neither exists, seed `DEFAULT_ROLES` then pick `Admin`/`User`; user row: `passwordHash = bcrypt12`, `isAdmin = (table was empty)`, `mediaServerType = 'local'`, `roleId`. Response is `safeUser(savedEntity)`: the saved entity has no loaded role, so `role` is `null` (or `'Admin'` if `isAdmin`) and `permissions` is `[]` for a non-admin; keys TypeORM did not fill on insert (`email` when omitted, `avatar`, `lastLogin`, `mediaServerId`) are likely absent rather than `null`. `[ts:src/modules/auth/auth.service.ts:75]`–`[ts:src/modules/auth/auth.service.ts:121]`; absent-key claim `[assumed]`: TypeORM insert result merge not verifiable without running, record a parity scenario against Nest and match it.
38. **F1** `[new]`: `POST /api/auth/register` requires authentication and `users.manage` (`manage:all` qualifies); otherwise 403. Unauthenticated callers get 401 from the extractor (`[assumed]`: plan F1 says "else 403" without separating anonymous, see O2). With F1 the table is never empty for an authorised caller, so the `isFirstUser` branch and the role-seeding fallback of rule 37 are unreachable and are not ported. The `admin`/`password` seed on an empty `users` table stays (users.md rule on seeding). Client: hide the register screen for non-admins. (plan §7.6 F1; user decision 2026-10-15)
39. No login rate limiting or lockout, in Nest or Rust (user decision 2026-10-15; recorded so reviewers do not add it). `[ts:src/modules/auth/auth.controller.ts:40]`

### F. Response shapes

40. `SafeUser` (login `user`, `GET /auth/me`, register): every `users` column except `passwordHash`, plus `role`, `permissions`, `libraryIds`, `features`. Column keys: `id, createdAt, updatedAt, username, email, roleId, mediaServerType, mediaServerId, avatar, lastLogin, isAdmin, enabled, requirePasswordChange, movieQuotaLimit, seriesQuotaLimit, quotaPeriodDays, libraryOrder, hiddenLibraryIds, profileVisibility, shareTastes, shareRecommendations, shareWatchHistory, shareLikes, shareStats, shareDisabled, hideSpoilers, edlEnabled, edlAutoSkipCommercials, spoilerHideStills, spoilerHideOverviews, spoilerHideTitles` (types: users.md rule 2). Computed: `role` = role name, else `'Admin'` if `isAdmin`, else `null` (differs from the users module, which gives `null`); `permissions` = rule 19; `libraryIds` always `[]` here (never hydrated); `features` = rule 41. Dates are ISO-8601 with ms (`...000Z`). `passwordHash` never serialised (`select: false` and `@Exclude`); the object is a plain object so class-transformer does nothing. `[ts:src/modules/auth/auth.service.ts:124]`–`[ts:src/modules/auth/auth.service.ts:139]`, `[ts:src/modules/users/entities/user.entity.ts:21]`–`[ts:src/modules/users/entities/user.entity.ts:23]`

### H. Pairing state machine

54. `status`: missing `pairingId` → 400 `Missing pairingId`; missing header → 400 `Missing X-Device-Id header`; unknown `publicId` → 404 `Pairing request not found`; a `pending` row past `expiresAt` is flipped to `expired` (persisted) and returned as such; claim condition = `status = 'approved' AND row.deviceId = header AND accessToken = '__approved__' AND approvedByUserId is set`: then load the approver user (by id, **no `enabled` check**; not found → `{status:'approved'}` without tokens), issue a pair (rule 31, `userAgent` null), set row `accessToken = NULL`, return `{status, ...TokenPair}` and set the cookie.
