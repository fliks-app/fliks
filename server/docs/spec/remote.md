# Spec: remote control (+ grants)

Sources: `src/modules/remote/{remote.controller,remote.service,remote-grant.service,remote.module}.ts`, `remote/dto/*.ts`, `remote/entities/remote-control-grant.entity.ts`, `src/migrations/1784500000000-add-remote-control-grants.ts`; hub-side target state in `src/modules/scheduler/events.service.ts` (owned by `events-hub.md`, referenced by name only). Milestone: S2 (plan §10 step 3, after the SSE hub). Tag paths are relative to `backend/`.

Scope of the domain: which devices ("targets") an account may see and command, the per-device grant codes, the household fan-out of `remote.*` events. The live connection map, polled-target queues, attribution claims, superseded-connection eviction and the SSE transport are hub state: see `events-hub.md` (D-hub below).

## Rules

Targets and listing
1. A target id is `deviceId#tabNonce` (SSE client) or `deviceId#native` (polled client); `deviceIdOf(targetId)` = text before the first `#` (whole string when none). Grants are keyed by device id, so every tab/reconnect of a device shares one permission `[ts:src/modules/remote/remote.service.ts:41]`. A `deviceId` that itself contains `#` collapses to its prefix (consequence of the same function).
2. `GET /targets` rows, in this order: (a) the caller's own live targets from the hub (`listForUser`), skipping the one whose `targetId === self` (UX filter, not security); (b) then, for an admin, every other account's targets (`listAll` minus caller's own, minus `self`) with `ownerUsername` set from `users`, and the result is returned at once; (c) for a non-admin, the targets of accounts that granted a device to the caller, kept only when `deviceIdOf(targetId)` is in the caller's granted device set (a second device of the same owner stays invisible), each with `ownerUsername` = owner's username `[ts:src/modules/remote/remote.service.ts:119]`. Own rows have `ownerUsername: null`.
3. Within one source, rows are ordered by connection `since` descending (hub `collect` sorts SSE and polled entries together) `[ts:src/modules/scheduler/events.service.ts:567]`. Across owners in (c) the order follows the unordered `users` query (DB order) `[ts:src/modules/remote/remote.service.ts:152]`: [assumed] clients do not rely on it, parity must sort or ignore order.
4. (c) only lists owners with `enabled = true`; (b) admin listing does not filter disabled owners (it lists whatever the hub holds) `[ts:src/modules/remote/remote.service.ts:152]`, `[ts:src/modules/remote/remote.service.ts:133]`.
5. `nowPlaying`: the live session (presence registry, see `presence.md`) whose `sseConnectionId === connection.connectionId`; omitted (null) when none, or when `now - lastBeat > liveSessionTtlMs` (30 000 ms default, env `STREAM_LIVE_SESSION_TTL_MS`, positive int else default) `[ts:src/modules/remote/remote.service.ts:357]`, `[ts:src/modules/streaming/lifetime-constants.ts:28]`. `systemName` comes from the same live session (`null` when none, even if stale); `positionSeconds` = session `position`, `state` = session `state`. A polled target's connection id is `polled:<targetId>`; its heartbeat carries `targetId` and the server stores `sseConnectionId = polled:<targetId>` on the session, so it matches too `[ts:src/modules/playback/playback.controller.ts:241]`.
6. `userAgent`, `deviceName`, `formFactor`, `tvPlatform` come from the connection identity captured at SSE connect (`/api/system/events` query `device, ff, tvPlatform, name`) or at `register` (`formFactor` default `'tv'`, `tvPlatform` null, `userAgent` null, `deviceName` = `name ?? null`) `[ts:src/modules/remote/remote.service.ts:265]`.

Authorization (`canControl`)
7. `canControl(me, targetUserId, deviceId)` returns `{ allowed, reason }`, evaluated in this order: `targetUserId == null` -> admin ? `admin` : deny `ownerless_target_requires_admin`; `targetUserId === me.id` -> allow `self`; admin -> allow `admin`; target user row missing -> deny `target_user_missing`; empty/absent `deviceId` -> deny `no_device_id`; no grant row `(deviceId, granteeUserId = me.id)` -> deny `device_not_granted`; target user `enabled = false` (re-read now) -> deny `target_disabled`; else allow `granted` `[ts:src/modules/remote/remote.service.ts:228]`. The `ownerless` branch is unreachable today (owners always resolve to a user id) but is kept in the predicate.
8. "Admin" = `casl.createForUser(user).can(Manage, 'Settings')`: `users.isAdmin` or role permission `settings.access` or `manage:all` `[ts:src/modules/remote/remote.service.ts:258]`, `[ts:src/modules/auth/casl/casl-ability.factory.ts:132]`.
9. The same predicate runs at listing visibility and at `command`/`commands` (`authorizeTarget`): `findTargetOwner` resolves visibility, then `canControl` consents `[ts:src/modules/remote/remote.service.ts:296]`.
10. `findTargetOwner(me, targetId)` order: (i) own connection via hub `resolveTarget(me.id, targetId)` (newest wins when several map, warning logged) -> owner = me; (ii) for each device grant of the caller (`grantedDevices`) whose `deviceId === deviceIdOf(targetId)`: hub `resolveTarget(grant.ownerUserId, targetId)`; first hit wins, owner username looked up; (iii) admin only: scan `listAll()` for `connection.targetId === targetId`, first hit; else null `[ts:src/modules/remote/remote.service.ts:321]`.
11. `authorizeTarget`: not found -> `404 NotFoundException('remote.error_device_offline')`; `canControl` denied -> `403 ForbiddenException('remote.error_' + reason)` (e.g. `remote.error_device_not_granted`); both logged at warn `[ts:src/modules/remote/remote.service.ts:296]`. 404 never reveals whether a target exists outside the caller's scope.

Commands
12. `POST /:targetId/command` order: authorize (404/403) -> self-target check -> action check -> deliver. `targetId === dto.byTargetId` -> `400 BadRequestException('remote.error_self_target')` `[ts:src/modules/remote/remote.service.ts:177]`. The `remote.error_unknown_action` branch is unreachable (the DTO `@IsIn` rejects first with a validation 400) `[ts:src/modules/remote/remote.service.ts:184]`.
13. Delivery: `emitToConnection(connectionId, event)` of exactly the resolved connection, never `emitToUser` (a fallback broadcast would let one phone pause every device of the account) `[ts:src/modules/remote/remote.service.ts:195]`. The event is `{ ...dto, type: 'remote.command', cmdId: randomUUID(), expiresAt: Date.now() + 10000, byTargetId: dto.byTargetId ?? null }`: every validated DTO field is forwarded (including `qualityId`, which the TS union omits), absent optional fields are omitted from the JSON, `subtitleId: null` is kept `[ts:src/modules/remote/remote.service.ts:28]`.
14. Delivery returns false (dead SSE socket, or polled queue already at 20) -> `404 NotFoundException('remote.error_device_offline')`; success is never reported for a dropped command `[ts:src/modules/remote/remote.service.ts:204]`, `[ts:src/modules/scheduler/events.service.ts:461]`. Response `202 { cmdId }`.
15. `expiresAt` is an absolute epoch-ms deadline (10 s TTL): the target drops a late command itself; the server does not expire queued/pushed commands `[ts:src/modules/remote/remote.service.ts:29]`.
16. Attribution: when `action === 'load'` and `mediaFileId` is truthy, `claimAttribution(targetId, me.id, mediaFileId)` (hub state, 60 s TTL, consumed by the next playback-info on that target for the same file) after a successful delivery; no claim for any other action, nor `browse` `[ts:src/modules/remote/remote.service.ts:214]`, `[ts:src/modules/scheduler/events.service.ts:512]`.

Polled targets
17. `POST /register` derives `targetId = deviceId + '#native'` server-side (a caller-supplied id is never accepted) and calls the hub `registerPolledTarget(me.id, { targetId, formFactor: body.formFactor ?? 'tv', tvPlatform: null, deviceName: body.name ?? null, userAgent: null })`; response `{ targetId }`, status 201 `[ts:src/modules/remote/remote.service.ts:265]`.
18. Hub semantics the port must reproduce (D-hub): polled map keyed `polled:<targetId>` (also its connection id); re-register keeps `since` and the queue and refreshes `lastPoll`; first registration emits `remote.targets_changed` to the owner; entry expires `POLLED_TARGET_TTL_MS = 30000` after the last poll, evicted lazily during any listing/resolve (emitting `remote.targets_changed`); queue bounded `POLLED_QUEUE_MAX = 20` `[ts:src/modules/scheduler/events.service.ts:583]`, `[ts:src/modules/scheduler/events.service.ts:550]`, `[ts:src/modules/scheduler/events.service.ts:368]`, `[ts:src/modules/scheduler/events.service.ts:373]`.
19. `GET /commands?targetId=`: `authorizeTarget` first (so a grantee passes visibility/consent), then hub `drainCommands(me.id, targetId)`: returns and clears the queue, refreshes `lastPoll`; `null` (unknown target or `polled.userId !== me.id`, i.e. an SSE target or someone else's) -> `404 remote.error_device_offline`. Draining is at-most-once per command `[ts:src/modules/remote/remote.service.ts:282]`, `[ts:src/modules/scheduler/events.service.ts:611]`.
20. An expired polled target reads as offline (404): the client must re-`register`. The 404 (not `[]`) is deliberate: a mis-registered device must not poll forever in silence `[ts:src/modules/remote/remote.service.ts:280]`.
21. A polled target is keyed only by `polled:<targetId>` with no owner in the key: a second account registering the same `deviceId` overwrites the entry (`userId` replaced, `since` and queue kept) and then drains its queued commands `[ts:src/modules/scheduler/events.service.ts:591]`. Not covered by F1-F7: open question O1 in the report. Parity must not assert either behavior.
22. `GET /commands` without `targetId`: `deviceIdOf(undefined)` throws a TypeError inside `findTargetOwner` after the own-connection lookup misses -> unhandled -> `500 { statusCode: 500, message: "Internal server error" }` `[ts:src/modules/remote/remote.service.ts:327]`. Frozen contract says keep it unless a deviation is decided (open question O2).

Grants
23. Constants: code TTL 600 000 ms (response `expiresIn: 600`, seconds, `floor`), max 3 unclaimed codes per `deviceId`, alphabet `ABCDEFGHJKLMNPQRSTUVWXYZ23456789` (no I, O, 0, 1), length 6, mint retries 10 `[ts:src/modules/remote/remote-grant.service.ts:16]`.
24. `POST /grants/code`: (1) delete every unclaimed code (grantee null) with `codeExpiresAt < now`, for all devices; (2) count unclaimed rows of this `deviceId` (any owner): `>= 3` -> `400 remote.error_too_many_codes`; (3) mint: draw 6 chars with `crypto.randomInt`, accept when no row has that code, up to 10 draws else `400 remote.error_code_unavailable`; (4) insert `{ code, deviceId, ownerUserId = caller, granteeUserId = null, deviceName.slice(0,80), codeExpiresAt = now + 10 min }`; response `{ id, code, expiresIn: 600 }` status 201. No `remote.targets_changed` is emitted `[ts:src/modules/remote/remote-grant.service.ts:62]`, `[ts:src/modules/remote/remote-grant.service.ts:205]`, `[ts:src/modules/remote/remote-grant.service.ts:215]`.
25. `POST /grants/claim`: `code` = `trim().toUpperCase()` of the body value (the DTO length check 4..12 runs on the raw value first). Row lookup `code = $1 AND granteeUserId IS NULL`. Order of failures: no row -> `404 remote.error_unknown_code`; `codeExpiresAt < now` -> delete the row, `404 remote.error_expired_code`; `ownerUserId === caller` -> `400 remote.error_own_device` (row kept); caller already holds a grant on that device (any owner) -> delete the new row, return the EXISTING grant as `GrantDto` (no announce, status 201); else set `code = null`, `granteeUserId = caller`, save, announce `remote.targets_changed` to grantee and owner, return `GrantDto` `[ts:src/modules/remote/remote-grant.service.ts:97]`.
26. A code is single-use: cleared (NULL) on claim so a displayed string never reaches an established grant. Only the code expires; a claimed grant stands until revoked. There is no account-level or follow-based gating (the two `users` flag columns were dropped by the migration) `[ts:src/migrations/1784500000000-add-remote-control-grants.ts:38]`.
27. `GET /grants`: `held` = rows where `granteeUserId = caller`; `issued` = rows where `ownerUserId = caller AND granteeUserId IS NOT NULL` (+ `AND deviceId = $q` when `deviceId` query is truthy). Unclaimed codes never appear. No ORDER BY (DB order). `ownerUsername`/`granteeUsername` resolved via `users` (null when the user is gone) `[ts:src/modules/remote/remote.controller.ts:87]`, `[ts:src/modules/remote/remote-grant.service.ts:139]`, `[ts:src/modules/remote/remote-grant.service.ts:148]`.
28. `DELETE /grants/:id`: unknown id -> `404 remote.error_unknown_grant`; caller neither owner nor grantee -> the same 404 (existence not revealed); else delete (also works on an unclaimed code row by its owner, which is how a device withdraws a code), announce `remote.targets_changed` to grantee (if any) and owner; 204 `[ts:src/modules/remote/remote-grant.service.ts:161]`.
29. `announce(...ids)`: `emitToUser(id, { type: 'remote.targets_changed' })` for each distinct non-null id. Because it uses `emitToUser`, the household fan-out of rule 31 also applies to it `[ts:src/modules/remote/remote-grant.service.ts:55]`.
30. No cleanup of grants on user delete, user disable or device sign-out: no FK, no cascade in the schema; `canControl` re-reads `enabled`, and a deleted owner makes `target_user_missing` / dangling rows `[ts:src/migrations/1784500000000-add-remote-control-grants.ts:8]` (grep of the codebase shows no other reference to the entity).

Household fan-out
31. `EventsService.emitToUser` calls the registered fan-out hook (one registration, by `RemoteService`'s constructor) after dispatching to the owner, only for `remote.state`, `remote.targets_changed`, `remote.stopped`. `emitToUsers` never triggers it, which prevents loops `[ts:src/modules/scheduler/events.service.ts:428]`, `[ts:src/modules/scheduler/events.service.ts:442]`, `[ts:src/modules/remote/remote.service.ts:63]`.
32. `fanOutToGrantees(ownerId, event)`: cache key `device:<ownerId>:<deviceIdOf(event.targetId)>` for `remote.state`/`remote.stopped` (frames scoped to the one device), else `owner:<ownerId>` for `remote.targets_changed`; viewers = `granteesForDevice(ownerId, deviceId)` (grant rows of that device whose `ownerUserId` is the event's owner, grantee non-null; [new] F31: Nest took every owner, so a code minted by anyone for that device id leaked its playback state) or `granteesForOwner(ownerId)`; audience = viewers + all enabled admins, de-duplicated, minus the owner; if non-empty `emitToUsers(audience, event)` `[ts:src/modules/remote/remote.service.ts:77]`.
33. Two in-memory caches of 30 000 ms (`GRANT_CACHE_MS`): `viewerCache: Map<key, { ids, at }>` and `adminCache: { ids, at }`. They are never invalidated on grant/revoke/claim: a new/revoked grant affects the audience of state frames up to 30 s late, while the command path re-checks the DB on every command. The viewer map has no eviction (one key per device/owner seen) `[ts:src/modules/remote/remote.service.ts:39]`, `[ts:src/modules/remote/remote.service.ts:72]`, `[ts:src/modules/remote/remote.service.ts:102]`.
34. `adminIds()` = all `enabled = true` users filtered by rule 8, cached 30 s `[ts:src/modules/remote/remote.service.ts:106]`.
