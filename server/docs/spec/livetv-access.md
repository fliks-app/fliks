# Spec: live TV access (user routes, channel visibility, restricted groups, grants)

Scope: who may see and play which channel, the user routes of `/api/livetv/*`, the admin access routes, the admin channel-catalog routes (their only SQL is shared with the visibility rule), the `livetv_*` access settings. Not here: sessions, capacity, failover, resolver, engine coupling (`livetv-sessions.md`); sources, sync, XMLTV, guide match, logos download, the three jobs (`livetv-sources.md` and `livetv-guide.md`): the user routes `GET /api/livetv/{channels/on-now,guide,programs/:id,search}` and the admin `guide-sources` and `guide/match-report` routes are in `livetv-guide.md`, the admin `sources` routes in `livetv-sources.md`; both only consume rules 10 and 14-17 of this file.

## Routes

Extractors follow `auth.md`: `Authed` (rejects `scope:'stream'`, 401), `SessionAuthed` (rejects it with 403 `session_token_required`), `StreamAuthed` (accepts it). Policy `Read LiveTvChannel` = permission `livetv.read` (admin: `manage:all`), policy `Manage Settings` = `settings.access` or admin.

The session routes (`POST channels/:id/play`, `DELETE sessions/:sessionId`, `PUT sessions/:sessionId/state`) are in `livetv-sessions.md`. Route order: `PATCH channels/bulk` is matched before `PATCH channels/:id` (the static segment matches first). The module has 33 routes: 11 user (4 here, 3 in `livetv-sessions.md`, 4 in `livetv-guide.md`), 5 access and 4 admin channel routes here, 13 admin source and guide routes (7 in `livetv-sources.md`, 6 in `livetv-guide.md`).

## Rules

### Vocabulary and storage

1. A group is a free-text `channel.groupName`; a channel with no provider group stores the sentinel `__livetv_ungrouped__` (never null after ingestion; null only on rows older than migration `1785600000000`), so it can be listed, counted and restricted. Group-name normalisation (`normalize_group_name`) = trim, then the sentinel when empty (the one function of `livetv-sources.md` rule 27).
2. Fold key of a group = trimmed then lower-cased (accents kept on purpose). Every comparison of restrictions, grants and exemptions uses it, never exact text. The trim is `fliks_domain::js` JS `trim` (the set of `livetv-sources.md` rule 27, one helper for both rules; never `str::trim`, which strips U+0085 and keeps U+FEFF) then `str::to_lowercase`; rule 14 pins where the fold runs.
3. The only live TV route a stream-scope token may call is `GET channels/:id/logo` (native clients append `?token=` to `<img>` loads); every other route here and in `livetv-sessions.md` rejects it, the list, admin `GET`s and all admin writes included.
4. Settings keys written by this module (through the settings store with the own-module origin, the only way past the protected-key guard of the generic settings API): `livetv_restricted_groups`, `livetv_restricted_groups_exempt` (JSON array of strings), `livetv_restricted_groups_vanished` (JSON object group name to ISO date). The generic settings PUT refuses them (`settings.md` rule 9); the access service calls the settings store directly. Each write emits `settings.changed` like any write (settings.md).
5. Reading a group-set key: absent, empty, unparsable JSON, or not an array yields `[]`; non-string members are dropped. The vanished map: not an object or an array yields `{}`; non-string values dropped. A corrupt value never fails a read.
6. Writing a group set: trim each, drop empties, deduplicate by fold key keeping the first spelling met, sort by `str` byte order of the UTF-8 (equal to the JS default string sort for BMP text; vectors avoid astral characters).
7. One `tokio::sync::Mutex` in the access service serialises every read-modify-write of the three keys and the grants table (the sync pass `restrict_adult_groups`, `expire_vanished_groups`, admin `set_restricted_groups`, `set_grants`); the server is a single process.

### Visibility (who sees which channel)

8. `denied_groups(user)`: restricted set empty returns `[]` with one settings read; a user whose permissions include `manage:all` or `settings.access` returns `[]` (never filtered; an `isAdmin` user's permissions are `['manage:all']`); else every restricted group whose fold key is not among the fold keys of the user's `livetv_group_access` rows.
9. A restricted group is absent for a denied user, not hidden: no row in the list, the count, the guide, the programme lookup or the search, 404 on play, prefs and logo. Hiding (`pref.hidden`) is the viewer's own undoable preference and is never a control.
10. Channel visible to a user (the list, `status`, guide pages) = `channel.enabled = true` and (no pref row or `pref.hidden = false`) and (`groupName IS NULL` or its fold key is not denied). Order: `COALESCE(pref.favorite,false) DESC, number ASC NULLS LAST, sortIndex ASC, name ASC` (then `id ASC`). `group` is an exact match on `groupName` (not folded), `favoritesOnly` adds `pref.favorite = true`, `query` is `name ILIKE '%' || q || '%'` with `%` and `_` in `q` escaped (`ESCAPE '\'`, as the guide search `q` of `livetv-guide.md` rule 45); an empty `group` or `query` is no filter (truthiness test).
11. `status.available` = count of rule 10 with no filter > 0.
12. Playable (`find_playable(id, user)`): `enabled = true`, plus the streams with their source, and not in a denied group; absent, disabled and denied are the same 404 `Live TV channel #<id> not found` (never distinguishable). A channel's `hidden` pref and an expired account do not block it. Only streams whose `source.enabled = true` are loaded, so a disabled source's channels are not playable: no stream left is 503 `livetv_channel_unavailable` at open and a denial at the resolver (`livetv-sessions.md` rules 5, 30); an open viewer of a disabled source ends at its next playlist request. They stay listed: the vanished-group sweep counts them.
13. Logo visibility: the channel row exists (enabled or not) and is not in a denied group, else the same 404. Prefs (`hidden`) and `enabled` are not checked.
14. Where the fold runs: one predicate only. The raw denied names are passed as a `text[]` and both sides are folded in SQL (`lower(btrim(x))` on the column and on `unnest($denied)`); play, prefs, logo and the resolver use the same SQL (no application-side fold). `btrim` only strips spaces and `lower` follows the database's `lc_ctype`.
15. Guide-channel visibility for a user and a `guideChannelId`: rule 10 with no filters and `"guideChannelId" = $2`, count > 0. Used by `GET programs/:id`.
16. Guide-channel scoping: appends a correlated `EXISTS (SELECT 1 FROM livetv_channels c LEFT JOIN livetv_user_channel_prefs pref ON pref."channelId" = c.id AND pref."userId" = $u WHERE c."guideChannelId" = <column> AND c.enabled = true AND (pref.hidden IS NULL OR pref.hidden = false) [AND (c."groupName" IS NULL OR lower(btrim(c."groupName")) NOT IN (denied))])`; never an `IN` list (a 15k-channel lineup would exceed the 65535 bind cap). Used by `search`.
17. Paging for a user: rule 10 counted then `OFFSET (page-1)*pageSize LIMIT pageSize`, used by `guide` and `on-now`; `search` takes page 1.
18. Logo route: logo visibility (rule 13), then `size` in `thumb|medium|full` else `full`; file `<images base>/livetv/<id>[-thumb|-medium].png` (`images::paths::Target::livetv(id).file(root, size)`, the paths module shared with the store, `image-store.md` rule 18); a missing sized file falls back to `full` and adds `X-Image-Size-Served: full`; no file 404 (bare body `{statusCode:404,message:"Not Found"}`). `/api/images/livetv/*` is deliberately not served by the image routes (a logo may belong to a restricted group). Every channel payload (this list and the `on-now`, `guide`, `search` items of `livetv-guide.md`) answers `logoPath` only when it is the local path `/api/livetv/channels/<id>/logo` (`?v=<hash>` once cached), else `null`; never the provider URL. The field stays `string | null`; an uncached logo (a channel enabled between two syncs, a dead logo url retried at each sync) shows the client's initials placeholder (`live-tv.html`).
19. Prefs: channel must be enabled and not denied (404 otherwise, same body as play); no existing row creates one (`favorite false`, `hidden false`, `lastPlayedAt null`), then each given field overwrites. Both fields absent is a no-op 200. `lastPlayedAt` (channel and pref) is never written by any code (dead columns; Rust leaves them untouched).
20. `GET /users/:userId` and `PUT /users/:userId` take the path id as a canonical integer (400 otherwise).

### Restricted groups

21. Restricted-groups view: for each stored restricted name, `automatic` = it matches `ADULT_GROUP_PATTERN` (rule 26), `vanishedSince` = the vanished map entry (exact name key) or null, `cleanupAt` = `vanishedSince + livetv_stale_stream_days * 86 400 000 ms` as ISO or null. `livetv_stale_stream_days`: `parseInt(raw,10)` if finite else 7 (negative and 0 accepted).
22. `set_restricted_groups(groups)` (under the mutex): `previous` = stored set; `unique` = rule 6; `dropped` = previous groups whose fold key is not in `unique`. Order matters and is part of the contract: (a) delete the grants of `dropped` (every stored spelling matching by fold key; a grant stored as `XXX` goes when `xxx` is dropped), (b) write `livetv_restricted_groups`, (c) exemption bookkeeping (rule 23), (d) clear vanished timers of `unique` (rule 25). A failure in (a) leaves the group restricted (safe) rather than open with dangling grants; (a) and (b) may share one transaction as long as the visible order holds.
23. Exemptions (`livetv_restricted_groups_exempt`): of the `dropped` groups, those matching the adult pattern are added (an explicit unrestriction that the next sync must not undo); of `unique`, those matching the pattern are removed from it (re-restricting retires the exemption). Keyed by fold key, stored spelling replaced, not duplicated. Written only when either list is non-empty.
24. `PUT restricted-groups` answers `unique`. Dropping a group never touches other groups' grants; resubmitting the same group under another casing is not a drop (no grant churn).
25. `clear_vanished(names)`: deletes the vanished entries whose fold key matches; writes the map only if something changed. Called by `set_restricted_groups` (for `unique`) and `set_grants` (for the matched groups): an admin confirmation cancels a pending expiry.
26. `ADULT_GROUP_PATTERN` (JS regexp source, case-insensitive, no `u` flag so `\b`/`\w` are ASCII): `/\b(?:xxx|sex[eo]?|porn\w*|erot(?:ic|iqu|ik)\w*|x[- ]?rated|adult(?!\s*swim\b)\w*)\b|(?<![a-z0-9])(?:\+18|18\+)(?![a-z0-9])/i`. The Rust `regex` crate has neither look-around nor ASCII-only `\b` by default: the matcher uses `fancy-regex` (a `fliks_domain` dependency) with ASCII word semantics (`(?-u:\b)`, `[a-zA-Z0-9_]` for `\w`); vectors below are the contract.
27. `restrict_adult_groups(groupNames)` (called by the source sync after each source, owner of that call: `livetv-sources.md`): under the mutex, `known` = fold keys of restricted plus exempt; additions = names matching the pattern and not known; none returns the current set; else `set_restricted_groups_locked([...current,...additions])` (each addition normalised, nothing dropped; rule 22 (d) also clears the vanished timer of every restricted group, not only the additions). Returns the resulting set. A newly seen adult group is therefore restricted before any non-admin can list it.
28. `expire_vanished_groups(liveGroupNames)` (called after a full successful sweep, whose caller guarantees `liveGroupNames` is every group any source still carries a channel for, enabled or not): candidates = restricted plus exempt names; a candidate absent (by fold key) from the live set gets `vanished[name] = now` if it had none; a candidate present loses its entry; entries for names that are not candidates are deleted. Expired = vanished entries that were already vanished before this pass (a group first marked in this pass can never expire in it, even with 0 grace days), are restricted (an exemption never expires), and `since <= now - graceDays`. Expired groups: grants deleted, removed from `livetv_restricted_groups` (re-read, then filtered), vanished entries dropped, one warn log. Map written only if changed; returns the expired names.
29. `set_grants(userId, groups)` (under the mutex): `requested` = trimmed, non-empty, exact-deduplicated; matched against the restricted set by fold key; a match is stored under the restricted list's own spelling, a non-match goes to `ignored`; delete all of the user's grants, insert the matched ones, `clear_vanished(matched)`. Answer `{groups, ignored}`. Grants for a non-restricted group are never stored (no dormant grant resurrecting later). After the write, each live viewer of that user (`livetv-sessions.md` rule 1) whose channel `find_playable` now refuses is ended (engine `DELETE /v1/sessions/{sid}?reason=revoked`, then the viewer is dropped); the user's VOD sessions are untouched, and a grant that only grows ends nothing. The resolver alone does not suffice: a `direct.ts` viewer is one long response, resolved only when it connects.
30. Unknown `userId` on `PUT users/:userId`: 404 before any write.

### Admin channel catalog (shares rule 10's table, not its predicate)

31. Bulk update: select `id, name` of channels matching the AND of the given selectors (`channelIds` IN, `group` exact, `sourceId` via `EXISTS (SELECT 1 FROM livetv_channel_streams s2 WHERE s2."channelId" = channel.id AND s2."sourceId" = $1)`, `namePattern` ILIKE `%x%`); a selector that is an empty string is skipped, so `{group: ""}` selects every channel, and `{}` selects every channel (the admin UI's "all channels" scope sends `{}`); no match returns `{affected: 0}`. Then in this order, in one transaction: `enabled` update; `groupName` update with the group-name normalisation then `UPDATE livetv_channels SET "groupNameSource" = 'manual' WHERE id = ANY($1)` (stops a later sync realigning it); `startNumber` renumbers `orderedIds` (the request's `channelIds` order filtered to matches, else matches sorted by name with JS `localeCompare`) with `UPDATE livetv_channels AS c SET number = v.n FROM (VALUES ($1,$2),...) AS v(id, n) WHERE c.id = v.id` (`startNumber + index`).
32. `merge(target, sources)`: sources minus the target; none left returns (200, no work). One transaction: target must exist (404) with its streams; the sources' streams ordered `priority ASC` get `channelId = target`, `priority = target.streams.length + i`; the source channels are deleted (their prefs cascade; unknown source ids are silently ignored; the target keeps its own group, so merging a restricted-group channel into an open one exposes its streams: admin-only, kept).
33. Channel update: each given field overwrites (`groupName` through the group-name normalisation; `guideChannelId` also sets `guideMatchKind = 'manual'`; `name`/`number` unvalidated beyond type); if `groupName` was given, `groupNameSource` becomes `'manual'` and the response row carries the value after the update.
34. Admin list: `total` = filtered count; page ids by `ORDER BY name ASC, id ASC OFFSET LIMIT` (two-step: a to-many join must not paginate), then channels with `streams` and `streams.source` for those ids, re-ordered by the id page; `groups` = `GROUP BY "groupName"` counts scoped only by `sourceId`, sorted case-insensitive name then name. `pageSize` has no maximum.
35. `GET /api/livetv/admin/access/users`: every user ordered `username ASC` with the role loaded; `groups` from one `SELECT "userId", "groupName" FROM livetv_group_access WHERE "userId" IN (...)` (row order per user is storage order); `hasFullAccess` = permissions include `manage:all` or `settings.access` (`deniedGroups` short-circuit).
36. Session views for admins: there is no `/api/livetv` admin session route. Admins see live viewers in `GET /api/system/streams` (rows of `livetv-sessions.md` rule 40) and cannot stop one through `POST /api/system/streams/:sid/command` (presence has no entry: 400 `Session not found`).

### Decisions settled in review

37. Restricted-group bypass review (checked, no bypass found in this scope): the list, guide pages, programme lookup, search, play, prefs, logo and the resolver all apply rule 9; merge across groups (rule 32) and `hidden` (rule 9) are admin or self-inflicted. Rule 14's single predicate closes the fold mismatch between SQL and application checks.
38. Decided in `livetv-sessions.md`: ownership of `DELETE sessions/:sessionId` (rule 18) and the resolver owner check (rule 31). Not implemented: a live-only token and a per-user viewer cap (fliks-app/fliks#1728). The `updatedAt` trigger covers the raw group stamps of rules 31 and 33.

## SQL

All identifiers quoted as in the schema. Tables: `livetv_channels`, `livetv_channel_streams`, `livetv_user_channel_prefs` (unique `(userId, channelId)`, FK cascade on both), `livetv_group_access` (unique `(userId, groupName)`, FK cascade on `userId`), `app_settings`.

- User list / count / page / guide-channel check: rule 10, one statement: `SELECT channel.*, pref.favorite AS pref_favorite FROM livetv_channels channel LEFT JOIN livetv_user_channel_prefs pref ON pref."channelId" = channel.id AND pref."userId" = $1 WHERE channel.enabled = true AND (pref.hidden IS NULL OR pref.hidden = false) [AND (channel."groupName" IS NULL OR lower(btrim(channel."groupName")) <> ALL($denied))] [AND channel."groupName" = $g] [AND pref.favorite = true] [AND channel.name ILIKE $q] ORDER BY COALESCE(pref.favorite,false) DESC, channel.number ASC NULLS LAST, channel."sortIndex" ASC, channel.name ASC, channel.id ASC [OFFSET LIMIT]`; count = same without ordering. (`denied` folded in SQL, rule 14.)
- Playable: `SELECT * FROM livetv_channels WHERE id = $1 AND enabled = true`, then `SELECT s.*, src.* FROM livetv_channel_streams s JOIN livetv_sources src ON src.id = s."sourceId" WHERE s."channelId" = $1 AND src.enabled = true` (rule 12; order irrelevant, sorted in code, `livetv-sessions.md` rule 3; `src."password"` is never selected here), denied-group check per rule 14.
- Visible logo: `SELECT id, "groupName" FROM livetv_channels WHERE id = $1`.
- Prefs upsert: `INSERT INTO livetv_user_channel_prefs ("userId","channelId",favorite,hidden) VALUES ($1,$2,COALESCE($3,false),COALESCE($4,false)) ON CONFLICT ("userId","channelId") DO UPDATE SET favorite = COALESCE($3, livetv_user_channel_prefs.favorite), hidden = COALESCE($4, livetv_user_channel_prefs.hidden)` (the `updatedAt` trigger covers the timestamp).
- Grants: `SELECT * FROM livetv_group_access WHERE "userId" = $1`; `DELETE FROM livetv_group_access WHERE "userId" = $1`; `INSERT INTO livetv_group_access ("userId","groupName") VALUES...`; group-wide delete: load all rows, keep those whose fold key matches, `DELETE... WHERE "groupName" = ANY($stored)`.
- Settings: `SELECT value FROM app_settings WHERE key = $1` / the settings store upsert (`settings.md`); keys in rule 4.
- Admin: the statements quoted in rules 31-34; admin list second step `WHERE channel.id = ANY($ids)` with streams and sources joined.

## Events

None emitted by this module except the `settings.changed` domain events caused by the three own-module writes (rule 4); none consumed. No SSE event announces a changed restriction: clients refetch on navigation. Live viewers lose access through the resolver (`livetv-sessions.md` rule 30) and, on a grant change, rule 29; never an event.

## Jobs/timers

None here. The vanished-group sweep runs inside the source sync (`livetv-sources.md`, hourly job); this module only provides `restrictAdultGroups` and `expireVanishedGroups`. The mutex of rule 7 is the only coordination.

## Vectors/parity

Fixture set `server/fixtures/livetv-groups`, replayed by a Rust test: `{ restricted[], exempt[], vanished{}, grants[], user:{permissions[]} } -> denied_groups`, `{ names[] } -> restrict_adult_groups additions`, `{ live[], restricted[], exempt[], vanished{}, graceDays, now } -> expire_vanished_groups`, plus the adult-pattern table: positive `ADULTES, Adulte, Adultes FR, FOR ADULTS, PORNO, Eroticos, Erotik, SEX, X-RATED, +18, 18+`; negative `HOT, HOT TV Israel, Hot Hits, Adult Swim, News, FR | SPORT`; `éxxx` (ASCII `\b`: positive), `Sussex`, `Essex`, `xxxl` (negative), `18+Movies` and `+18Movies` (`(?![a-z0-9])` after `18+` fails on `M`: negative).

HTTP parity scenarios: the `livetv-access-*`, `livetv-admin-channels-*`, `livetv-channels-*`, `livetv-logo-*`, `livetv-prefs-*` and `livetv-status*` files in `server/parity/scenarios/livetv/`.
