# Spec: Kobo sync (experimental)

Scope: the emulated Kobo store API a Kobo e-reader talks to once its `api_endpoint` points at Fliks: routes, the credential (a `kobo` device token in the path), the library sync with its token and deletions, covers, reading state, shelves, and the optional proxy to the real store. Credentials are `device-tokens.md`; the progression is `item-delivery.md` rules 18-24 and `kosync.md` rule 13; the ACL is `libraries.md` and `books.md` rule 22. Plan: `plans/books-audiobooks.plan.md` section 3.9 point 5, item 6.1. The wire is reimplemented from the public behaviour of Calibre-Web (`cps/kobo.py`), Komga and Kavita, modelled on the Kobo store API of firmware 4.x (Libra and Clara families); it has not been run against a real device.

Books are delivered as KEPUB (item 6.2, `kepub.md`), converted from the EPUB on its first download (rules 27-30); `kobo/books.rs::downloads` chooses the format and URL of a book's file.

## Setup

The user creates a device token of kind `kobo` in the profile and puts, in `.kobo/Kobo/Kobo eReader.conf` under `[OneStoreServices]`, the line `api_endpoint=https://<host>/kobo/<token>`. The device then appends `/v1/...` to it. The token is in the path, so it ends up in proxy logs: renewing it (`device-tokens.md` `POST .../renew`) is one click in the profile, and the old one stops at once.

## Credential

1. Every route is `/kobo/<token>/...`. The token must be well formed (`device-tokens.md` rule 12) and hash to a `kobo` row (`opds` and `kosync` rows never match). Nothing else is read: no cookie, no Bearer (the device's own `Authorization` is ignored, except by the proxy, rule 25). The same token opens the engine's data plane through `/cred/<token>/` for book downloads of `text` editions only, never video, audio, sprites or subtitles (`device-tokens.md` rule 9).
2. An unknown, renewed or revoked token, a malformed one, or one of a disabled user is `401` with an empty body. A role without `media.read` is `403`. A hit stamps `lastUsedAt`, at most once a minute. Renewing or revoking stops the routes at once; the engine may keep answering a download link it already resolved for up to the 30 s `ttlS` (`device-tokens.md` rule 8).
3. Failure throttle, in-process, per client network, on the limiter of the login (`auth.md` rules 39 and 63) under a key no username can take: a failing token counts before the lookup, the 6th failure within 15 minutes is `429` with `Retry-After: 900`, a valid token is never throttled and clears nothing (a device syncs in parallel).
4. Every answer is `application/json` (images aside) with `Cache-Control: no-store`. The caller is the token's owner with their library ACL: `accessible_library_ids` bounds every list and every lookup (rule 9).

## Routes

Paths are relative to `/kobo/<token>`. The device sends the headers of its firmware (`x-kobo-*`, `User-Agent`); none is required.

| Method path | Answer |
|---|---|
| `GET /v1/initialization` | `{"Resources": {...}}` (rule 5), header `x-kobo-apitoken: e30=` |
| `GET /v1/library/sync` | JSON array of changes (rules 10-17), headers `x-kobo-synctoken` and, when more remain, `x-kobo-sync: continue` |
| `GET /v1/library/{uuid}/metadata` | `[BookMetadata]`, 404 for a book the owner cannot read |
| `GET /v1/library/{uuid}/state` | `[ReadingState]`, 404 likewise |
| `PUT /v1/library/{uuid}/state` | body `{"ReadingStates": [...]}`, answer in rule 20, 404 likewise |
| `DELETE /v1/library/{uuid}` | 204, archives the book for this device (rule 15), 404 for an unknown uuid |
| `GET /{uuid}/{w}/{h}/{greyscale}/image.jpg`, `GET /{uuid}/{w}/{h}/{quality}/{greyscale}/image.jpg` | the cover (rule 8) |
| `GET /v1/library/tags` | `[Tag]` of the owner's shelves (rule 22) |
| `POST /v1/library/tags` | create (rule 23), 201 and the tag id as a JSON string |
| `PUT /v1/library/tags/{id}` | rename, 200 |
| `DELETE /v1/library/tags/{id}` | delete, 200 |
| `POST /v1/library/tags/{id}/items`, `POST /v1/library/tags/{id}/items/delete` | add or remove books, 201 and 200 |
| `GET /v1/user/profile`, `GET /v1/user/loyalty/benefits`, `GET /v1/analytics/gettests`, `POST /v1/auth/device`, `GET /v1/user/wishlist`, `GET /v1/deals`, `GET /v1/products/**` | the stubs of rule 6 |
| any other path under `/v1/`, and the stubs above | the proxy (rule 25) when it is on, else the stub of rule 6 |
| any other path or method under `/kobo/`, and `/kobo/<token>` itself | `404 {"message": "Not found"}`, never the app's index page |

5. Initialization: `Resources` points everything the server handles back at the request's own base URL (`X-Forwarded-Proto` and `X-Forwarded-Host`, else `Host`; scheme `http` when none says `https`): `image_host`, `image_url_template` and `image_url_quality_template` (rule 8), `library_sync`, `library_metadata`, `tags`, `user_profile`, `user_loyalty_benefits`, and the `kobo_*_enabled` switches set to `False` (audiobooks, native borrow, subscriptions, superpoints). The rest of the map is the static list of the real store (`kobo/resources.json`, 147 keys, the data of `NATIVE_KOBO_RESOURCES` in Calibre-Web `cps/kobo.py` at commit 6e840acb; values may be JSON objects), so the device still finds every key it reads; the proxy (rule 25) puts the store's own answer under ours when on. The `kobo_*_enabled` switches for features this server has none of (audiobooks, subscriptions, superpoints, native borrow, one-store library, shelfie, credit redemption) are `False` in ours, so the store's `True` never wins.
6. Stubs, so a device does not stall: `profile` `{"UserId": <token owner id as text>, "Email": ""}`-like empty profile, `loyalty/benefits` `{"Benefits": {}}`, `analytics/gettests` `{"Result": "Success", "TestKey": "", "Tests": {}}`, `auth/device` a fixed bearer pair (`AccessToken`, `RefreshToken`, `TokenType: "Bearer"`, `TrackingId`, `UserKey`; none is a secret or is checked), `wishlist` and `deals` `[]`... an unknown path `{}`. A stub never reads the database.

## Books

7. A Kobo book is a text item: the lowest-id item of a `text` edition of a `book` work (`books.md`), whose file is the one the OPDS catalogue links (`item_parts` of the highest `version`, `libraries::HIDDEN_FILES_FROM` applied) and has the extension `.epub`. A work or edition outside the owner's libraries, an item with no readable EPUB (a PDF, a CBZ, a wanted shell) is not a Kobo book: it is in no sync, and its uuid is a 404 everywhere. An edition links its own library (`COALESCE(editions."libraryId", media."libraryId")`) as in the OPDS entries.
8. Identifiers are stateless UUIDs: the book of item `n` is `f11c5b00-0000-4000-8000-` + `n` as 12 hexadecimal digits (`EntitlementId`, `RevisionId`, `CrossRevisionId`, `WorkId`, `CoverImageId`, the uuid of every path); a shelf of playlist `n` is the same with `f11c5a60`. A uuid of another shape names nothing. The cover is the media's local poster (`images.md`), the `thumb` size when `w` is at most 300, else `medium`, else `full`; `h`, quality and greyscale are ignored (the device scales). A book with no poster, or one the owner cannot read, is 404. Covers answer `image/jpeg`, `Cache-Control: private, max-age=86400`.
9. `BookMetadata` carries `Title`, `Contributors` (authors), `Description` (overview), `Language`, `Publisher` `{ "Imprint": "", "Name" }`, `PublicationDate` (Jan 1 of `year`), `CoverImageId`, ids, free prices (`0`), `ContributorRoles` (`{Name, Role: "Author"}`), and `DownloadUrls`: one `{ "Format": "KEPUB", "Size", "Url", "Platform": "Generic" }` entry from `kobo/books.rs::downloads`, the size being the EPUB's (the KEPUB does not exist yet) and the URL `<base>/kobo/<token>/download/<uuid>/kepub` (rule 27). A work with no description or publisher omits the key.

## KEPUB download

27. `GET /kobo/<token>/download/<uuid>/kepub` is the download of a Kobo book (rule 7) under the credential of rule 1: an unknown uuid or a book the owner cannot read is `404` with an empty body, a file that is gone or leaves its folder root through a symlink likewise. The answer is the KEPUB of the book's file, `application/epub+zip`, with `Range` support, `Content-Disposition: attachment; filename="<uuid>.kepub.epub"` and `Cache-Control: private, no-cache`. The token opens nothing else of the data plane: this route reads only files of rule 7, and the engine's `/cred/<token>/` links stay limited to text editions (`device-tokens.md` rule 9).
28. The conversion (`kepub.md`) runs on the first download of a version of the file, not at sync time. A version is the file row id with the length and modification time of the file on disk, so a replaced file is converted again. The result is `<cache dir>/kepub/<file>-<length>-<mtime ns>.kepub.epub`, written under a unique temporary name and renamed. One conversion runs at a time, process-wide: the lock moves into the blocking job, so a download dropped mid-conversion neither starts a second one nor leaves a half-written file, and the retry finds the finished file. A download that waited on the lock finds the first one's file.
29. The cache is bounded by the lifecycle of the file and by size. A hit sets the file's modification time to now. After a conversion, still under the lock, the other versions of the same file are deleted, temporaries older than an hour too, and the least recently modified converted files go until the directory holds at most 1 GiB. A file evicted between the lookup and the open is converted again once. Nothing else removes them, so a deleted book's file leaves at the next conversion that needs the room.
30. A conversion that fails (a file that is no valid EPUB, over the limits of `kepub.md`, a full disk) is logged at `warn` with the file id and the download is `307` to the plain EPUB through the data plane, `<base>/cred/<token>/api/stream/<file>?download=1`, so the device still gets its book. Nothing is remembered: the next download tries again.
31. `application/epub+zip` is never compressed by the HTTP layer, so the answer keeps its `Content-Length` and `Accept-Ranges`.

## Library sync

10. The device keeps nothing of what it was sent; the server does, per token, in `kobo_sync_items` (rule 26). The sync token (`x-kobo-synctoken`, request and response) is the base64 of a JSON object `{"v":1,"t":<microseconds>,"b":[item ids],"g":[item ids],"s":[playlist ids],"sg":[playlist ids],"c":<item id>}`: what the previous answer sent as books, as removals, as shelves and as shelf removals, when the server read the library for it, and, only when that answer was cut at 100 entries (`c` absent or 0 otherwise), the item id of its last book entry. `c` is optional: a token without it starts at 0, and a negative one is no token. An unreadable token, or a version other than 1, is no token.
11. With no token, the device starts from nothing: every row of this token is deleted (archived books included, so a reset device gets its library back) and every book is new.
12. With a token, the server first acknowledges the batch it names: `b` and `s` become rows with `syncedAt = stateAt = t`, `g` and `sg` delete theirs. Nothing is written when an answer is built, so an answer the device never received is rebuilt identically on its retry with the same token.
13. Then it scans the library as the owner (rule 7) in windows of 500 text items in id order, starting after the token's `c` (0 when absent): per window, the ids and dates of the readable books, the token's rows and the owner's playback states of those ids only, and the metadata of only the books it sends. It answers at most 100 entries, in this order: books, reading states and removals by item id, then shelf changes. When more remain, `x-kobo-sync: continue`, the token carries `c`, and the next call resumes after it; a change to an item at or before `c` is sent by the next sync that starts without a `c`. Shelves read only the readable books among the items of the owner's playlists. Each entry is one object:
    - a book without a row: `{"NewEntitlement": {"BookEntitlement", "BookMetadata", "ReadingState"}}`;
    - a book whose row has `syncedAt` older than the book's last change (`greatest` of the update times of the item, the work, its edition, its file and its author credits): `{"ChangedEntitlement": {...same}}`;
    - a book whose only change is the owner's playback state (`updatedAt` after the row's `stateAt`): `{"ChangedReadingState": {"ReadingState"}}`;
    - a row whose book is no longer readable, or no longer an EPUB, or deleted: `{"ChangedEntitlement": {"BookEntitlement": {..., "IsRemoved": true}}}`, then the row goes at the next acknowledgement.
    `BookEntitlement` is `Accessibility "Full"`, `Status "Active"`, `IsRemoved`, `Created` and `LastModified` (the work's), the ids, `OriginCategory "Imported"`.
14. A change the device itself made to the reading state (rule 19) sets the row's `stateAt` to the state's `updatedAt`, so it is not echoed back. Another reader's change (web, KOReader) is a `ChangedReadingState` carrying a bookmark with the percentage only (rule 21).
15. `DELETE /v1/library/{uuid}` is the user removing the book from the device: the row is kept with `archived = true` and the book is sent no more to this token, whatever changes, until a sync without a token. The library is not touched.
16. A token no sync has acknowledged is cheap: the server holds no cursor, so there is no state to expire or leak between devices; the price is that a sync that starts at 0 reads the whole library in windows (ids and dates, not the files), bounded by the ACL; the pages of one sync together read it once.
17. A removed token (`DELETE /api/device-tokens/:id`) takes its rows with it (`ON DELETE CASCADE`).

## Reading state

18. The mapping of the playback state (`playback_states`, `(userId, itemId)`) to a Kobo `ReadingState`: `EntitlementId` the uuid; `StatusInfo.Status` `Finished` when the state is completed, `Reading` when its progression is above 0, else `ReadyToRead`; `CurrentBookmark.ProgressPercent` the progression times 100 (the book-wide percentage, not the chapter's); `LastModified`, `PriorityTimestamp` and each part's `LastModified` the state's `updatedAt` (the item's creation when there is none); `Statistics` zeros.
19. `PUT /v1/library/{uuid}/state` takes the first element of `ReadingStates` whose `EntitlementId` is the path's uuid. Written to the playback state like a web beat (`kosync.md` rule 13: `watched::record_watch`, progression clamped to 0..1, `mediaFileId` the book's file, no position, no duration, the finished rule of the text family, the locator set to NULL because a KoboSpan is no Readium locator): from `CurrentBookmark.ProgressPercent` when it is a finite number; `StatusInfo.Status = "Finished"` writes progression 1; `ReadyToRead` with no bookmark writes progression 0 (unread). The whole `CurrentBookmark`, `StatusInfo` and `Statistics` objects as received are kept in the row's `state` (at most 16 KiB, else `state` is NULL), and `stateAt` is set to the state's new `updatedAt` in either case (rule 14). The beat, the read-back of `updatedAt` and the row are written under one in-process lock per `(user, book)` that holds no database connection while it waits.
20. The answer is `{"RequestResult": "Success", "UpdateResults": [{"EntitlementId", "CurrentBookmarkResult": {"Result": "Success"}, "StatisticsResult": {"Result": "Success"}, "StatusInfoResult": {"Result": "Success"}}]}`. A body that is not that shape is `400 {"message": "Invalid request"}`; an unreadable book is 404 and writes nothing.
21. Reading a state back: when the row holds a `state` whose `stateAt` is not older than the playback state's `updatedAt`, the device's own `CurrentBookmark` (its `Location` included), `StatusInfo` and `Statistics` are returned as it sent them, so it resumes exactly; otherwise (the owner read elsewhere since) only the percentage is returned, and the device decides whether to move. A Kobo location is never converted to a Readium locator, nor the other way.

## Shelves

22. A Kobo shelf (tag) is a playlist the token's owner owns (`playlists.md`, `ownerId`); shared or saved playlists are not shelves. Only a playlist that holds at least one Kobo book the owner can read, or that this token already knows (it made it, or was sent it), is a shelf: a playlist of films or of other items is never listed, whatever its name. Its items are its readable Kobo books only. `Tag` is `{ "Id": uuid, "Name", "Created", "LastModified" (the playlist's `updatedAt`), "Type": "UserTag", "Items": [{ "RevisionId": book uuid, "Type": "ProductRevisionTagItem" }] }`, its items the playlist's Kobo books (rule 7) in position order. The sync sends `NewTag` for a playlist without a `shelf` row, `ChangedTag` when `updatedAt` is after the row's `syncedAt`, and `{"DeletedTag": {"Tag": {"Id", "LastModified"}}}` for a row whose playlist is gone.
23. `POST /v1/library/tags` `{"Name", "Items": [{"RevisionId"}]}` creates a private playlist named `Name` (trimmed, 1..255 characters, else 400) for the owner, or reuses the owner's playlist of exactly that name, and adds the readable books named by `Items` (an unreadable or unknown uuid is skipped). `PUT` renames, `DELETE` deletes, `.../items` adds and `.../items/delete` removes: each only on a playlist the owner owns, else 404. A reused playlist must hold readable Kobo books only. A playlist that holds anything else (films, items outside the owner's libraries) is never wiped from a device: `PUT` on it is `409` and `DELETE` removes only its Kobo books and keeps the playlist. The mixed check, the delete and the rename run in the transaction after the `FOR UPDATE` of the playlist, and only on a playlist the device can see (it holds a readable book or this token knows it): any other id, an empty playlist included, is `404` and untouched. A `create` that reuses a playlist marks it known to the token only when the token was up to date on it, so a playlist the device never saw is sent whole. Each write runs in one transaction on the locked playlist, and one `create` per user at a time (advisory lock), so two requests for one name make one shelf. Every write sets the playlist's `updatedAt`. A write by the device does not bring its own change back as a `ChangedTag`: the row's `syncedAt` is set to the new `updatedAt` only when the device was up to date before (its previous `syncedAt` not older than the previous `updatedAt`), so a web edit it had not yet seen is still sent.
24. A deleted or renamed playlist is seen by the device at its next sync; a book added to a shelf in Fliks appears in the shelf at the next sync even when the book is already on the device.

## Store proxy

25. `app_settings.kobo_store_proxy` = `true` (default off, any other value is off; admin, `settings.md`) lets the server forward to `https://storeapi.kobo.com` what it does not handle: a `/v1/...` path outside the routes above, and the `auth/device`, `initialization` resources merge of rule 5. The request goes with its method, path after the token, query, body and the headers `Authorization`, `Content-Type`, `Accept`, `User-Agent` and every `x-kobo-*`; the answer comes back with its status, `Content-Type` and body. The host is fixed; no redirect is followed; an upstream failure is `502` with an empty body. With the proxy off nothing leaves the server, and the stubs of rule 6 answer. A book the server serves is never proxied; with the proxy on, a book uuid that is not ours (a store book) is forwarded for `metadata`, `state` and `DELETE`, and its cover is a `307` to the store CDN (`cdn.kobo.com/book-images`); with it off those are `404`. A store answer that is a redirect (3xx) is no answer: `502`. A proxied answer is capped at 8 MiB and a proxied request body at 1 MiB; the `initialization` call to the store must be a success, is capped like the others, times out after 5 s and falls back to the static map. The store base URL is a field of the app state (`kobo_store`), set to the real store at startup and changed only by the test harness: nothing in a request, a setting or the environment can.

## Known limits

- A sync token replayed after a later one (a device restored from a backup) can resurrect a book removed in between: the removal is rebuilt from `kobo_sync_items`, and an old token acknowledges the older batch. Low impact, not guarded.
- A sync that starts at 0 reads the ids and dates of the whole readable library, in windows.

## Data

26. `kobo_sync_items("tokenId" -> device_tokens ON DELETE CASCADE, "kind" text ('item' | 'shelf'), "refId" integer (item or playlist id, no foreign key: its disappearance is how a removal is detected), "syncedAt" timestamptz, "stateAt" timestamptz, "archived" boolean, "state" jsonb NULL)`, primary key `("tokenId", "kind", "refId")`. `device_token_kind` gains `kobo`.

## Tests

`tests/it/kobo.rs` replays the requests a device sends against a fresh database: initialization and its resources, a full sync with a token round trip, a second sync that is empty, a change, a removal (a book that becomes unreadable), the retry of a lost answer, paging past 100, an archived book, a reset (no token), progress `PUT` then `GET` and its effect on the shared progression, a state written elsewhere coming back, covers by size, shelves in both directions, the ACL on every route, a `kosync`/`opds` token and a revoked or disabled owner, the throttle, the proxy off by default, and the KEPUB download (conversion, cache hit, replaced file, ACL, fallback to the EPUB). `device_tokens` tests cover the kind and the sources.
