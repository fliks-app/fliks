# Spec: social (likes, follows, recommendations, profiles, stats)

Sources: `[ts:src/modules/social/likes.controller.ts]`, `[ts:src/modules/social/likes.service.ts]`, `[ts:src/modules/social/social.controller.ts]`, `[ts:src/modules/social/social.service.ts]`, `[ts:src/modules/social/dto/*.ts]`, `[ts:src/modules/social/entities/*.ts]`, stats `[ts:src/modules/users/users-stats.service.ts]`, teardown `[ts:src/modules/users/users.service.ts]`. Milestone: S4 (requests moved to S5, plan §15.3). Authentication, error-body shapes and validation are in `auth.md` (cited "auth rule N"); user columns are in `users.md`; playlists (`PlaylistView`, `listVisibleForOwner`) are in `playlists.md`; history / recommendations / top-genres are in `playback-state.md`.

Scope: `LikesController` (4 routes) + `SocialController` (16 routes) = 20 routes (manifest filter: `.[]|select(.path|test("^/api/(likes|social)"))`). Both controllers are guarded by `JwtOrApiKeyGuard` only, no `PoliciesGuard`, no CASL subject: every rule lives in the services `[ts:src/modules/social/likes.controller.ts:20]`, `[ts:src/modules/social/social.controller.ts:23]`. The "caller row" `me` is the user loaded by the auth extractor on every request (auth rule 14), so `me.shareDisabled`, `me.isAdmin`, `me.permissions` are always current.

Conventions used below: "void" = handler returns nothing, Nest answers with the route's default status (POST 201, others 200) and an empty body; there is no `@HttpCode` on any route of this file `[ts:src/modules/social/social.controller.ts:23]`. "404 U" = `{"message":"User #<id> not found","error":"Not Found","statusCode":404}` (auth rule 15). "400V" = validation body (auth rule 16). Every route: 401 for missing/invalid credentials (auth rule 14), guards before pipes (auth rule 17), non-integer `:id`-style path params 400 `Validation failed (numeric string is expected)` (auth rule 18). F8: Rust rejects `scope:'stream'` tokens on all of these (401).

## Rules

### A. Likes

1. Likes are per-user bookmarks of a movie/series (`seasonId` and `episodeId` both absent), a season (`seasonId`) or an episode (`episodeId`); `mediaId` is always the parent title. Three partial unique indexes make a like idempotent per granularity: `UQ_likes_movie (userId, mediaId) WHERE seasonId IS NULL AND episodeId IS NULL`, `UQ_likes_season (userId, seasonId) WHERE seasonId IS NOT NULL`, `UQ_likes_episode (userId, episodeId) WHERE episodeId IS NOT NULL`; all FKs `ON DELETE CASCADE` (DDL is S0's). `[ts:src/modules/social/entities/like.entity.ts:19]`–`[ts:src/modules/social/entities/like.entity.ts:33]`
2. `POST /likes`: `INSERT INTO likes ("userId","mediaId","seasonId","episodeId") VALUES ($me,$mediaId, $seasonId|NULL, $episodeId|NULL) ON CONFLICT DO NOTHING` (no conflict target: any of the three indexes). A falsy `seasonId`/`episodeId` (absent, `null`, `0`) is stored as NULL. Both `seasonId` and `episodeId` may be sent and are stored as given. No check that the media/season/episode exists, belongs together, or is in a library the caller can access: an unknown id violates an FK: Nest answers `[assumed]` 500 (FK violation 23503 is not caught; unverifiable without running); Rust answers 400 or 404 (C1, rule 48; Q1). Response 201 empty. `[ts:src/modules/social/likes.service.ts:49]`–`[ts:src/modules/social/likes.service.ts:61]`
3. `DELETE /likes`: `DELETE FROM likes WHERE "userId"=$me AND "mediaId"=$m AND ("seasonId"=$s | "seasonId" IS NULL) AND ("episodeId"=$e | "episodeId" IS NULL)`: the `IS NULL` branch is taken when the DTO value is falsy, so the body must repeat the exact granularity used to like. Always 200 empty (nothing matched is not an error). `[ts:src/modules/social/likes.service.ts:63]`–`[ts:src/modules/social/likes.service.ts:73]`
4. `GET /likes` query `libraryId`: `libraryId ? +libraryId : undefined`; a non-numeric or `0` value therefore means "no filter" (NaN/0 are falsy in the service). Scope = the caller's accessible library ids (`libraries.md`: all ids when `isAdmin` or `manage:all`, else `library_user_access` rows `[ts:src/modules/libraries/libraries.service.ts:63]`–`[ts:src/modules/libraries/libraries.service.ts:74]`). `[ts:src/modules/social/likes.controller.ts:25]`–`[ts:src/modules/social/likes.controller.ts:28]`, `[ts:src/modules/social/likes.service.ts:44]`–`[ts:src/modules/social/likes.service.ts:47]`
5. `listLikes(userId, accessibleIds, {libraryId?, limit?})`: accessible list empty -> `[]`. Load the user's likes newest first (`createdAt DESC`) with `LIMIT limit ?? 60` **applied before** the ACL and `libraryId` filters, so a caller with many likes in inaccessible libraries gets fewer than 60 (frozen). Drop a like whose media is missing or whose `media.libraryId` is not in `accessibleIds`; drop when `libraryId` is truthy and differs. Item: `{mediaId: number, mediaType: 'movie'|'series', title: string, posterUrl: string|null, fanartUrl: string|null, seasonId: number|null, episodeId: number|null, label: string|null, stillUrl: string|null}`. `label`: episode like -> `` `S${season.seasonNumber ?? '?'}E${episodeNumber}` `` plus ` · <episode title>` when the title is non-empty, where `season = like.season ?? episode.season ?? null`; else season like -> `<media title> · S<seasonNumber>`; else `null`. `stillUrl` = episode `stillUrl` or `null`. Tie-break for equal `createdAt`: `l.id DESC` `[assumed]` (Nest has none; physical order). `[ts:src/modules/social/likes.service.ts:115]`–`[ts:src/modules/social/likes.service.ts:152]`
6. `GET /likes/state/:mediaId`: `{media, seasonIds, episodeIds}` from the caller's like rows of that media: `media` = some row has both `seasonId` and `episodeId` NULL; `seasonIds` = non-null `seasonId` of rows (row order, no sort); `episodeIds` likewise. No ACL and no existence check (unknown media -> `{media:false,seasonIds:[],episodeIds:[]}`). Row order: `ORDER BY l.id` (C12; Nest unordered). `[ts:src/modules/social/likes.service.ts:95]`–`[ts:src/modules/social/likes.service.ts:108]`
7. `likedKeys(userId, mediaIds)` (internal, used by rule 42): the set of `mediaId:seasonId|'':episodeId|''` strings of the user's likes among `mediaIds`; empty input -> empty set. `[ts:src/modules/social/likes.service.ts:76]`–`[ts:src/modules/social/likes.service.ts:92]`

### B. Follow graph

8. `user_follows(followerId, followingId, status 'pending'|'accepted' default 'accepted')`, unique pair `UQ_user_follows_pair`, FKs cascade. A follow of a **public** profile is stored `accepted` at once, with no consent from the target; a follow of a **private** profile is `pending` until accepted. Hence one-way accepted edges are normal. `[ts:src/modules/social/entities/user-follow.entity.ts:14]`–`[ts:src/modules/social/entities/user-follow.entity.ts:23]`
9. `POST /follow/:userId` order: (1) `me.id == userId` -> 400 `Cannot follow yourself`; (2) `me.shareDisabled` -> 400 `Sharing features are disabled`; (3) target must exist AND `enabled = true` else 404 U; (4) `target.shareDisabled` -> 404 U (undiscoverable, no probing); (5) an edge `me -> target` already exists (any status) -> 201 `{status: <existing status>}` and **no event, no write**; (6) insert with status `accepted` when `target.profileVisibility = 'public'` else `pending`; (7) emit SSE to the target (rule 47); (8) 201 `{status}`. `[ts:src/modules/social/social.service.ts:174]`–`[ts:src/modules/social/social.service.ts:211]`
10. Steps 5-6 are read-then-insert without a transaction: two concurrent follows hit `UQ_user_follows_pair` and the loser fails with `[assumed]` 500 (23505 not caught). Rust: `INSERT ... ON CONFLICT DO NOTHING` then re-read and answer as step 5 (C1: no 500). `[new]` C1. `[ts:src/modules/social/social.service.ts:185]`–`[ts:src/modules/social/social.service.ts:200]`
11. A pending request stays pending if the target later turns public; changing `profileVisibility` (either way) never touches existing edges (an accepted follower of a profile that becomes private keeps access). `[ts:src/modules/social/social.service.ts:190]`–`[ts:src/modules/social/social.service.ts:193]` (no code path elsewhere updates `user_follows` status except rule 13)
12. `DELETE /follow/:userId`: `DELETE FROM user_follows WHERE "followerId"=$me AND "followingId"=$userId` (pending or accepted, also cancels a pending request); target need not exist; no event; 200 void. `[ts:src/modules/social/social.service.ts:213]`–`[ts:src/modules/social/social.service.ts:218]`
13. `POST /requests/:userId/accept`: find edge `userId -> me` with status `pending`, none -> 404 `Follow request not found`; set `accepted`; emit `social.follow_accepted` to the requester; 201 void. Does not check that the requester is still enabled or not `shareDisabled`. `[ts:src/modules/social/social.service.ts:221]`–`[ts:src/modules/social/social.service.ts:238]`
14. `POST /requests/:userId/reject`: `DELETE FROM user_follows WHERE "followerId"=$userId AND "followingId"=$me AND status='pending'`; no 404, no event; 201 void. An accepted follower cannot be removed by the followed user through this API (only the follower unfollows). `[ts:src/modules/social/social.service.ts:240]`–`[ts:src/modules/social/social.service.ts:246]`
15. `GET /requests`: edges `* -> me` with status `pending`, joined to the follower row, mapped through `decorate` (rule 20); no `enabled`/`shareDisabled` filter; order unspecified in Nest, Rust `ORDER BY uf.id ASC` (C12). `[ts:src/modules/social/social.service.ts:249]`–`[ts:src/modules/social/social.service.ts:255]`
16. `areMutualFollowers(a,b)` (both directions accepted) has no remaining caller in `backend/src` (`rg areMutualFollowers`: definition only; remote grants dropped the follow gating, `remote.md` rule 26). Not ported. `[ts:src/modules/social/social.service.ts:136]`–`[ts:src/modules/social/social.service.ts:142]`
17. `requireUser(id)`: `SELECT ... FROM users WHERE id=$1 AND enabled = true`, none -> 404 `User #<id> not found`. A disabled account is indistinguishable from a missing one. `[ts:src/modules/social/social.service.ts:118]`–`[ts:src/modules/social/social.service.ts:122]`
18. `connectionsVisible(me, target)` = `me.id == target.id || target.profileVisibility = 'public' || me -> target is accepted`. `[ts:src/modules/social/social.service.ts:299]`–`[ts:src/modules/social/social.service.ts:305]`
19. `GET /users/:userId/followers` and `/following`: `requireUser(userId)` (404 U), then `[]` (200) when `!connectionsVisible`, else the accepted edges (`* -> userId`, resp. `userId -> *`) joined to the other user, through `decorate`. Nest: no `shareDisabled` check on viewer or target and no `enabled` filter on the listed users (a disabled follower still appears). Rust applies the profile/stats gate and the `enabled` check (F23, rule 49). Order unspecified in Nest, Rust `ORDER BY uf.id ASC` (C12). `[ts:src/modules/social/social.service.ts:307]`–`[ts:src/modules/social/social.service.ts:325]`
20. `decorate(me, users)` -> `SocialUser = {id: number, username: string, avatar: string|null, isFollowing: boolean, requested: boolean, followsYou: boolean}`: `isFollowing` = edge `me -> u` is `accepted`; `requested` = edge `me -> u` is `pending`; `followsYou` = edge `u -> me` is `accepted`. Empty input -> `[]`; output keeps the input order. `[ts:src/modules/social/social.service.ts:145]`–`[ts:src/modules/social/social.service.ts:170]`

### C. Discovery

21. `GET /search?q=`: `me.shareDisabled` -> `[]`. Else users with `enabled = true AND shareDisabled = false AND id <> me.id`, plus `username ILIKE '%'||trim(q)||'%'` when the trimmed `q` is non-empty (no `q` = default roster), `ORDER BY username ASC LIMIT 30` in Nest (Rust: `ORDER BY lower(username), id`, C15, rule 52), decorated. `%` and `_` in `q` are NOT escaped (they act as wildcards; keep). Private-profile users are included (that is how a follow request is made). Nest ordering is the database collation; Rust is collation-independent (C15). `[ts:src/modules/social/social.service.ts:259]`–`[ts:src/modules/social/social.service.ts:272]`
22. `GET /connectable?q=`: `me.shareDisabled` -> `[]`. As rule 21 plus `(profileVisibility = 'public' OR id IN (<ids the caller follows with status accepted>))` (`IN (-1)` when none). Same reach as the playlist-collaborator rule (`playlists.md` rule 25) and `recommend` (rule 40). `[ts:src/modules/social/social.service.ts:277]`–`[ts:src/modules/social/social.service.ts:297]`

### D. Visibility matrix (authz surface)

Facts used: `V` = viewer (`me`), `T` = target user, `follows` = edge `V -> T` is **accepted** (a pending edge never grants anything), `public` = `T.profileVisibility = 'public'` (enum `public|private`, default `private`, users.md rule 2), `optOut(X)` = `X.shareDisabled`. `[ts:src/modules/social/social.service.ts:299]`, `[ts:src/modules/social/social.service.ts:372]`

| Question | Rule (exact) | Else |
|---|---|---|
| Does `T` exist for `V`? | `T.enabled` | 404 U |
| `profile`, `stats`: may `V` look at `T` at all? | `V = T`, or (`!optOut(T)` and `!optOut(V)`) | 404 U (never 403) |
| `follow`, `recommend`: may `V` act on `T`? | `V <> T`, `!optOut(V)` (400), `!optOut(T)` (404 U); `recommend` also needs `public` or `follows` (404 U) | see rules 9, 40 |
| `search`, `connectable`: who is listed? | `V` not opted out; listed = enabled and not opted out and not `V`; `connectable` further needs `public` or `follows` | `[]` |
| `followers`, `following` lists | `V = T` or `public` or `follows` | `[]` (200) |
| Profile content (playlists, tastes, ...) | `canSeeContent` = `V = T` or `public` or `follows` | header only, counts 0 (rule 31) |
| Profile `followerCount`/`followingCount` | shown when `canSeeContent`, else `0` | `0` |
| Playlists section | `public` playlists of `T`; plus `followers` ones when `V = T` or `follows` (`includeFollowers`); `private` ones never | `playlists.md` rule 18 |
| Stats | `V = T`, or (`T.shareStats` and (`public` or `follows`)) | 404 U |
| Per-section flags (`tastes`, `recommendations`, `recentlyWatched`, `likes`, `stats`) | `V = T` or `T.shareTastes` / `shareRecommendations` / `shareWatchHistory` / `shareLikes` / `shareStats` (all default `false`) | section empty, `shown.<x> = false` |
| Library scoping of shown content | every list is filtered by the **viewer's** accessible library ids, never the target's | item dropped |

23. A private profile's non-follower (and a pending requester) sees only `{id, username, avatar, isFollowing, requested, followsYou, isSelf, visibility}`; username and avatar of every enabled, non-opted-out member are therefore public to every member by design. `[ts:src/modules/social/social.service.ts:385]`–`[ts:src/modules/social/social.service.ts:398]`
24. "No probe": `shareDisabled` members answer exactly like missing ones on `follow`, `recommend`, `profile`, `stats`; they are NOT hidden on `followers`/`following` in Nest (Rust hides them, F23, rule 49). `[ts:src/modules/social/social.service.ts:182]`–`[ts:src/modules/social/social.service.ts:184]`, `[ts:src/modules/social/social.service.ts:332]`–`[ts:src/modules/social/social.service.ts:336]`

### E. Profile (`GET /users/:userId/profile`)

25. Used by clients for every member page (F2 removed `GET /api/users/:id` for others, so this route is the only cross-user read; users.md rule 5). The Rust route must return the `PublicProfile` JSON below with the same nulls and empties.
26. Order: `requireUser(userId)` (404 U), `isSelf = me.id == userId`; `!isSelf && (T.shareDisabled || me.shareDisabled)` -> 404 U. `[ts:src/modules/social/social.service.ts:329]`–`[ts:src/modules/social/social.service.ts:336]`
27. Header (always present): `{id, username, avatar: string|null, isFollowing, requested, followsYou, isSelf, visibility: 'public'|'private', followerCount, followingCount}`. `followerCount` = count of accepted edges `* -> T`, `followingCount` = accepted `T -> *` (disabled users counted). For `isSelf`: `isFollowing = false`, `requested = false`, `followsYou = false`. `[ts:src/modules/social/social.service.ts:337]`–`[ts:src/modules/social/social.service.ts:370]`
28. `canSeeContent = isSelf || public || isFollowing` (accepted). When false: header with `followerCount = 0`, `followingCount = 0`, `shown` all `false`, and `playlists`, `topGenres`, `recommendations`, `recentlyWatched`, `likes` all `[]`. `[ts:src/modules/social/social.service.ts:372]`–`[ts:src/modules/social/social.service.ts:398]`
29. When true: `includeFollowers = isSelf || isFollowing`; `viewerAccessible` = accessible library ids of the viewer; `shown = {playlists: true, tastes: isSelf || T.shareTastes, recommendations: isSelf || T.shareRecommendations, recentlyWatched: isSelf || T.shareWatchHistory, likes: isSelf || T.shareLikes, stats: isSelf || T.shareStats}`. `shown.stats` is only a UI hint: the stats themselves come from the stats route (rule 35). `[ts:src/modules/social/social.service.ts:401]`–`[ts:src/modules/social/social.service.ts:410]`
30. Sections, fetched concurrently, each skipped (empty) unless its flag is true: `playlists` = `listVisibleForOwner(T, V, includeFollowers)` (`playlists.md` rule 18; note a viewer who is `T` sees only public and followers playlists here, role `viewer`); `topGenres` = `getTopGenres(T)` default limit 8 -> `{genre: string, weight: number}[]` (`playback-state.md` rule 29; NOT scoped to the viewer's libraries, so genre names derive from the target's whole history in Nest; Rust scopes to the viewer's libraries, F25, rule 50); `recommendations` = `getRecommendations(T, viewerAccessible, 15)` (`playback-state.md` rules 21-28) with `becauseTitle` forced to `''` on every item (it names a title from the target's unscoped history); `recentlyWatched` = `getHistory(T, page 1, limit 12, viewerAccessible).data` (`WatchHistoryItem[]`, `playback-state.md` rule 13); `likes` = `listLikes(T, viewerAccessible, {limit: 24})` (rule 5). `[ts:src/modules/social/social.service.ts:411]`–`[ts:src/modules/social/social.service.ts:436]`
31. All sections are computed with the **target's** data and the **viewer's** library ACL; an empty `viewerAccessible` yields empty `recommendations`, `recentlyWatched`, `likes`. `[ts:src/modules/social/social.service.ts:402]`
32. The profile is built from plain objects (no entity serialisation): no `@Exclude` effects.
33. `PublicProfile` JSON = header (rule 27) + `shown: {playlists, tastes, recommendations, recentlyWatched, likes, stats: boolean}` + `playlists: PlaylistView[]` + `topGenres` + `recommendations: RecommendationItem[]` + `recentlyWatched: WatchHistoryItem[]` + `likes: LikedItem[]`. `[ts:src/modules/social/social.service.ts:45]`–`[ts:src/modules/social/social.service.ts:64]`

### F. Stats (`GET /users/:userId/stats`)

34. This is the second consumer of the stats aggregation that `users.md` rule 28 specifies for the admin route. From S4 Rust has ONE implementation (`user_stats(user_id)`, SQL below); the Nest `UsersStatsService` and its duplication of the two queries (allowed in `bridge.md` between S1 and S4) are deleted. The response shape is exactly `users.md` rule 28.
35. Gate (before aggregating): `requireUser` (404 U); `!isSelf && (T.shareDisabled || me.shareDisabled)` -> 404 U; for non-self: `iFollow` = accepted edge `me -> T`, `canSee = public || iFollow`; `!T.shareStats || !canSee` -> 404 U.
