## Rules

### A. Model and access control

1. Tables: `playlists(name varchar(255), ownerId, autoRemoveWatched bool=false, autoPlay bool=false, autoDownload bool=false, visibility enum 'private'|'followers'|'public' default 'private', coverImageUrl varchar(512) null)`; `playlist_items(playlistId, mediaId, episodeId null, position int, addedById null ON DELETE SET NULL)` with partial unique indexes `UQ_playlist_items_movie (playlistId, mediaId) WHERE episodeId IS NULL` and `UQ_playlist_items_episode (playlistId, episodeId) WHERE episodeId IS NOT NULL` (no unique on `position`); `playlist_shares(playlistId, userId, role enum 'viewer'|'editor'|'administrator' default 'viewer')` unique `(playlistId, userId)`; `playlist_saves(userId, playlistId)` unique pair. Every FK cascades on delete except `addedById`. The owner is the column `ownerId`, never a share row, so the owner cannot be removed or demoted structurally. `coverImageUrl` is never written by the API (always `null`). DDL is S0's. `[ts:src/modules/playlists/entities/playlist.entity.ts:20]`–`[ts:src/modules/playlists/entities/playlist.entity.ts:63]`, `[ts:src/modules/playlists/entities/playlist-item.entity.ts:22]`–`[ts:src/modules/playlists/entities/playlist-item.entity.ts:37]`, `[ts:src/modules/playlists/entities/playlist-share.entity.ts:20]`–`[ts:src/modules/playlists/entities/playlist-share.entity.ts:23]`, `[ts:src/modules/playlists/entities/playlist-save.entity.ts:18]`–`[ts:src/modules/playlists/entities/playlist-save.entity.ts:20]`
2. Roles rank `viewer 1 < editor 2 < administrator 3`; `owner` is implicit full access and is reported as the string `'owner'` in `role` fields. `[ts:src/modules/playlists/playlists.service.ts:33]`–`[ts:src/modules/playlists/playlists.service.ts:39]`
3. The class-level policies (`Read|Create|Update|Delete` on `Playlist`) are unconditional grants for every authenticated user, `manage:all` included (auth rules 20, 24, 26), so the policy check never rejects after authentication: Rust needs only the authenticated extractor (a `readonly` role can create and edit its own playlists). `[ts:src/modules/auth/casl/casl-ability.factory.ts:78]`–`[ts:src/modules/auth/casl/casl-ability.factory.ts:81]`, `[ts:src/modules/playlists/playlists.controller.ts:28]`–`[ts:src/modules/playlists/playlists.controller.ts:34]`
4. `assertRole(user, id, min)` returns `{playlist, role}` and decides every authorisation: (1) no playlist row -> 404 P; (2) `playlist.ownerId == user.id` -> role `'owner'`; (3) **only when `min = viewer`**: `visibility = 'public'` -> role `viewer` (a share row is not consulted); `visibility = 'followers'` and an accepted `user -> owner` edge exists -> role `viewer`; (4) share row for `(playlist, user)`: none -> 404 P (non-members never learn the playlist exists); `rank(share.role) < rank(min)` -> 403 role; else the share's role. Visibility therefore never grants write access, and a caller with no share who fails step 3 gets 404, not 403, on write routes. `[ts:src/modules/playlists/playlists.service.ts:114]`–`[ts:src/modules/playlists/playlists.service.ts:151]`
5. Nest quirk (Rust fixes `GET /:id`, C13, rule 41; PATCH/POST: Q1): because step 3 returns before the share lookup, a caller holding an `editor` or `administrator` share on a `public` playlist (or a `followers` playlist they follow) receives `role: 'viewer'` in `GET /playlists/:id` and in every `PlaylistView` built through `findOneForUser` (create, patch); the list route (rule 9) reports the real share role. Authorisation of write routes is unaffected (they pass `min >= editor`, which skips step 3). `[ts:src/modules/playlists/playlists.service.ts:127]`–`[ts:src/modules/playlists/playlists.service.ts:130]`, `[ts:src/modules/playlists/playlists.service.ts:232]`–`[ts:src/modules/playlists/playlists.service.ts:247]`
6. Resulting matrix (O owner, A/E/V share role, pub = `public` visibility, fol = `followers` visibility with an accepted follow of the owner, none = no share):

| Route | Min role | O | A | E | V | none + pub / fol | none otherwise |
|---|---|---|---|---|---|---|---|
| `GET :id`, `GET :id/items`, `GET :id/members`, `POST|DELETE :id/save` | viewer | ok | ok | ok | ok | ok (role `viewer`) | 404 P |
| `DELETE :id` | viewer, then owner check | ok | 403 `Only the owner can delete a playlist` | 403 same | 403 same | 403 same (readable, not owner) | 404 P |
| `PATCH :id`, `POST|DELETE :id/members[/:userId]` | administrator | ok | ok | 403 role | 403 role | 404 P | 404 P |
| `POST :id/items`, `DELETE :id/items/...`, `PUT :id/items/order` | editor | ok | ok | ok | 403 role | 404 P | 404 P |

7. `shareDisabled` (users.md): an opted-out caller cannot `save` (400, before the role lookup, so also on a playlist they cannot read), cannot `addMember` (400, after the role check), cannot set a non-private `visibility` (400); reading/writing playlists they already own or are a member of is unaffected. The teardown that makes everything private is `social.md` rule 46 (rule 40 below). `[ts:src/modules/playlists/playlists.service.ts:252]`–`[ts:src/modules/playlists/playlists.service.ts:254]`, `[ts:src/modules/playlists/playlists.service.ts:404]`–`[ts:src/modules/playlists/playlists.service.ts:410]`, `[ts:src/modules/playlists/playlists.service.ts:481]`–`[ts:src/modules/playlists/playlists.service.ts:483]`
8. Library ACL: every read that shows media (`items`, posters, counts, `addItem`) is scoped to the **caller's** accessible library ids (all ids when `isAdmin` or `manage:all`, else `library_user_access`, `[ts:src/modules/libraries/libraries.service.ts:63]`–`[ts:src/modules/libraries/libraries.service.ts:74]`); items in libraries the caller cannot access are omitted for shared members too. Rows are never removed by this filter.

### B. Reads

9. `GET /playlists`: the union of owned playlists (`role 'owner'`, `saved false`), playlists shared with the caller (their share role, `saved false`) and playlists the caller saved (`role 'viewer'`, `saved true`); a playlist in several sets appears once with precedence owner > share > save. Empty union -> `[]`. Each entry is a `PlaylistView` (rule 10) with `itemCount`/`posters` computed under the caller's ACL (rule 12), sorted by `name` with JS `localeCompare` (ICU, default locale; Rust sorts by `name` in byte order then `id`, README convention for collation-ordered lists `[assumed]`, Q2; C12). In Nest saved playlists are listed whatever their current visibility: after the owner makes a saved playlist private the saver still sees its name, owner id, counts and posters in the list although `GET /playlists/:id` is 404; Rust drops such entries (F26, rule 42). `[ts:src/modules/playlists/playlists.service.ts:159]`–`[ts:src/modules/playlists/playlists.service.ts:203]`
10. `PlaylistView` = `{id: number, name: string, ownerId: number, role: 'owner'|'viewer'|'editor'|'administrator', autoRemoveWatched: boolean, autoDownload: boolean, autoPlay: boolean, visibility: 'private'|'followers'|'public', saved: boolean, coverImageUrl: string|null, itemCount: number, posters: string[], createdAt: ISO, updatedAt: ISO}`. `[ts:src/modules/playlists/playlists.service.ts:41]`–`[ts:src/modules/playlists/playlists.service.ts:57]`, `[ts:src/modules/playlists/playlists.service.ts:834]`–`[ts:src/modules/playlists/playlists.service.ts:856]`
11. `GET /playlists/:id`: `assertRole(viewer)`; `saved = role != 'owner' && a playlist_saves row exists for the caller` (so a share holder who also saved reports `saved: true` here and `false` in the list, rule 9); view built with the caller's ACL stats. `[ts:src/modules/playlists/playlists.service.ts:232]`–`[ts:src/modules/playlists/playlists.service.ts:248]`
12. `itemCount` / `posters` (per playlist, viewer ACL): `itemCount` = number of `playlist_items` rows whose media is in an accessible library (a series counts once per episode row); `posters` = up to 4 distinct `media.posterUrl` values (distinct by URL, so two titles with the same URL collapse), `posterUrl IS NOT NULL`, ordered by the minimum `position` of each URL. Empty playlist-id list or empty accessible list -> no stats -> `itemCount 0`, `posters []`. SQL verbatim below. `[ts:src/modules/playlists/playlists.service.ts:863]`–`[ts:src/modules/playlists/playlists.service.ts:907]`
13. `GET /playlists/:id/items`: `assertRole(viewer)`; items `ORDER BY position ASC` (tie-break `id ASC` `[assumed]`, positions are not unique, rule 25); empty -> `[]`; media loaded with `library` relation filtered to accessible ids (empty accessible -> `-1`, nothing matches); an item whose media is not loaded (inaccessible) is omitted; episodes loaded with their `season` relation for the items having `episodeId`. `[ts:src/modules/playlists/playlists.service.ts:287]`–`[ts:src/modules/playlists/playlists.service.ts:316]`, `[ts:src/modules/playlists/playlists.service.ts:355]`–`[ts:src/modules/playlists/playlists.service.ts:371]`
14. `PlaylistItemView` = `{itemId: number, position: number, addedById: number|null, media: Media, episode: Episode|null, progressPercent: number, watched: boolean}`. `media` is the serialised `Media` entity (`media.md`, S3): all columns except `searchVector` (`select:false`), the eager `metadata` relation, the loaded `library` relation (a full Library row, including `path`: omitted for callers who cannot manage libraries, F22, rule 44) next to `libraryId`, the virtual `path` getter (`@Expose`, library path + folder; omitted likewise, F22), `qualityProfileId`, `languageProfileId`, `addedById`; no `seasons`/`cast`/`crew`/`files`. `episode` is the `Episode` entity (all columns except `searchVector`, plus `seasonId` and the loaded `season` object without its `episodes`), `null` for a movie item; for an episode item `media` is the parent series. Entities are serialised by the global class-serializer (no `@Exclude` on these classes; the contract is the S3 media JSON). `[ts:src/modules/playlists/playlists.service.ts:59]`–`[ts:src/modules/playlists/playlists.service.ts:71]`, `[ts:src/modules/media/entities/media.entity.ts:104]`–`[ts:src/modules/media/entities/media.entity.ts:114]`, `[ts:src/modules/media/entities/media.entity.ts:166]`–`[ts:src/modules/media/entities/media.entity.ts:172]`, `[ts:src/modules/media/entities/episode.entity.ts:70]`–`[ts:src/modules/media/entities/episode.entity.ts:74]`

No row -> `{progressPercent: 0, watched: false}`; `completed` -> `{100, true}`; else `watched false` and `progressPercent = durationSeconds > 0 ? min(100, Math.round(positionSeconds / durationSeconds * 100)) : 0` (`Math.round` rounds .5 up). `[ts:src/modules/playlists/playlists.service.ts:318]`–`[ts:src/modules/playlists/playlists.service.ts:353]`

### C. Playlist writes

19. `POST /playlists`: `INSERT INTO playlists (name, "ownerId", "autoRemoveWatched", "autoDownload", "autoPlay") VALUES (trim(name), $me, flag ?? false, ...)`; `visibility` takes the column default `'private'`; the body cannot set it (400 `property visibility should not exist`). `name` is validated (string, <= 255 chars) before the trim, an empty or blank name is accepted and stored as `''`. `[ts:src/modules/playlists/playlists.service.ts:378]`–`[ts:src/modules/playlists/playlists.service.ts:389]`, `[ts:src/modules/playlists/dto/create-playlist.dto.ts:3]`–`[ts:src/modules/playlists/dto/create-playlist.dto.ts:18]`
20. The create response is `findOneForUser` of the new row: `role 'owner'`, `saved false`, `itemCount 0`, `posters []`, `coverImageUrl null`. `[ts:src/modules/playlists/playlists.service.ts:388]`
21. `PATCH /playlists/:id`: `assertRole(administrator)` first (404 P / 403 role); then the patch is built from the defined fields (`name` trimmed, the three booleans, `visibility`); `visibility !== 'private'` while `user.shareDisabled` -> 400 `Sharing features are disabled` (no write); a non-empty patch is applied with `UPDATE playlists SET <fields>, "updatedAt" = now() WHERE id = $1` (even when values are unchanged), an empty body writes nothing and leaves `updatedAt`; the response is `findOneForUser` (rule 5 applies to `role`). An administrator-share member (not only the owner) may change `visibility`, rename and set the flags. `[ts:src/modules/playlists/playlists.service.ts:391]`–`[ts:src/modules/playlists/playlists.service.ts:413]`, `[ts:src/modules/playlists/dto/update-playlist.dto.ts:10]`–`[ts:src/modules/playlists/dto/update-playlist.dto.ts:31]`
22. `DELETE /playlists/:id`: `assertRole(viewer)` (404 P when unreadable), then not owner -> 403 `Only the owner can delete a playlist`; `DELETE FROM playlists WHERE id = $1` (cascade to items, shares, saves); 200 empty. `[ts:src/modules/playlists/playlists.service.ts:415]`–`[ts:src/modules/playlists/playlists.service.ts:425]`

### D. Members (shares)

24. `POST /members` order: (1) `assertRole(administrator)`; (2) `user.shareDisabled` -> 400 `Sharing features are disabled`; (3) `dto.userId == user.id` -> 400 `Cannot change your own role`; (4) `dto.userId == playlist.ownerId` -> 400 `The owner is already a member`; (5) target user with `enabled = true` else 404 `User #<id> not found`; (6) connectable gate (rule 25) else 403 `You can only add public members or members you follow`; (7) upsert: a share exists -> `UPDATE role` (any of the three roles, including a promotion or demotion of another administrator), else `INSERT`; (8) respond `Member[]` (201). `[ts:src/modules/playlists/playlists.service.ts:471]`–`[ts:src/modules/playlists/playlists.service.ts:527]`, `[ts:src/modules/playlists/dto/add-playlist-member.dto.ts:5]`–`[ts:src/modules/playlists/dto/add-playlist-member.dto.ts:11]`
25. Connectable gate = `!target.shareDisabled && (target.profileVisibility = 'public' || accepted edge caller -> target)`: same reach as `social.md` rules 22 and 40. A `shareDisabled` target answers 403 in Nest but 404 on follow/recommend, so Nest distinguishes opted-out members from missing ones; Rust answers 404 `User #<id> not found` for both (F27, rule 43). `[ts:src/modules/playlists/playlists.service.ts:494]`–`[ts:src/modules/playlists/playlists.service.ts:510]`
26. Delegation: an administrator share can add, promote (to administrator), demote and remove other members including other administrators; only the owner is protected (rules 24 steps 3-4, 27). The added member is not notified (no event). `[ts:src/modules/playlists/playlists.service.ts:511]`–`[ts:src/modules/playlists/playlists.service.ts:525]`
27. `DELETE /members/:userId`: `assertRole(administrator)`; `userId == caller` -> 400 `Cannot change your own membership`; `userId == ownerId` -> 400 `Cannot remove the owner`; `DELETE FROM playlist_shares WHERE "playlistId" = $1 AND "userId" = $2` (removing a non-member is not an error); respond `Member[]` (200). A non-owner member has no way to leave a playlist (the route needs administrator and forbids self): kept as is, a feature outside the port's scope (plan §15.3). The removed user's saves, `addedById` attributions and items stay. `[ts:src/modules/playlists/playlists.service.ts:530]`–`[ts:src/modules/playlists/playlists.service.ts:551]`

### E. Items

28. `POST /items` (`addItem`): `assertRole(editor)`, then `accessible` ids (empty -> `[-1]`), then target resolution (rule 29); no targets -> 201 `{added: 0}`; else one transaction: load the playlist's existing rows, drop targets already present (movie target: its `mediaId` already has a row with `episodeId IS NULL`; episode target: its `episodeId` already present); nothing fresh -> single (non-bulk) add 400 `errors.media_already_in_playlist`, bulk add `{added: 0}`; else `position` starts at `MAX(position) + 1` (`0` for an empty playlist) and increases by 1 per inserted row in target order, rows inserted with `addedById = caller`, then `UPDATE playlists SET "updatedAt" = now()`; 201 `{added: n}`. `[ts:src/modules/playlists/playlists.service.ts:564]`–`[ts:src/modules/playlists/playlists.service.ts:620]`
29. Targets (precedence `episodeId`, then `seasonId`, then `mediaId`; the others are ignored): `episodeId` -> the episode with its season, none (or no season) -> 404 `Episode #<id> not found`; the series (`season.mediaId`) must be `type = 'series'` in an accessible library else 404 `Series #<id> not found`; one target `{mediaId: series, episodeId}`, non-bulk. `seasonId` -> all episodes of the season `ORDER BY episodeNumber`; none (unknown season, empty season) -> `[]` targets (no 404) -> `{added: 0}`; series accessibility as above; bulk. `mediaId` -> media in an accessible library else 404 `Media #<id> not found`; `type = 'series'` -> every episode of every season (specials included) ordered by `(seasonNumber, episodeNumber)`, bulk (a series without episodes -> `{added:0}`); otherwise (movie) one target `{mediaId, episodeId: null}`, non-bulk. ### F. Reorder (exact semantics)

33. `PUT /items/order` body `{itemIds: number[]}` (IsArray + every element an integer). `assertRole(editor)`; load all item ids of the playlist; the request is valid iff `itemIds` contains no duplicate, has the same length as the playlist's item list, and every id belongs to the playlist; otherwise 400 `itemIds must list every item in the playlist exactly once` and nothing is written (a partial or filtered list is rejected, an empty list is valid only for an empty playlist). `[ts:src/modules/playlists/playlists.service.ts:801]`–`[ts:src/modules/playlists/playlists.service.ts:820]`
34. Write: one transaction in which, for `idx = 0 .. n-1` in request order, `UPDATE playlist_items SET position = idx WHERE id = itemIds[idx]`, then `UPDATE playlists SET "updatedAt" = now() WHERE id = $1` (also bumped for an empty playlist). Result: positions become exactly `0..n-1` in the requested order (gaps closed, the old values irrelevant); 200 empty. `[ts:src/modules/playlists/playlists.service.ts:821]`–`[ts:src/modules/playlists/playlists.service.ts:827]`

The validation read happens before and outside the transaction, with no lock: an item added or removed between validation and write makes the persisted order inconsistent (a new item keeps its old position, possibly equal to one assigned here).
