# Spec: scheduler

Sources: `[ts:src/modules/scheduler/scheduler.service.ts]`, `[ts:src/modules/scheduler/commands.controller.ts]`, `[ts:src/modules/scheduler/command-audit.util.ts]`, `[ts:src/modules/scheduler/entities/command.entity.ts]`, `[ts:src/modules/scheduler/scheduled-job-registry.service.ts]`, `[ts:src/common/constants/core-scheduler-jobs.ts]`, `[ts:src/modules/plugins/plugin-jobs.service.ts]`. Scope: the `commands` table and its audit wrapper (`runAuditedCommand`), the cron runner, the boot sweep, the core jobs (Backup, RefreshMetadata, RefreshMissingMetadata, prune commands, the trigger-only list) and `/api/commands*`. Not here: `SubtitleSchedulerService` and its 6-hourly tick (S6), the live TV jobs (S7), plugin manifest crons and the plugin staging sweep (S8), pairing / refresh-token prunes (S1), QoE purge and scan backfill (S2), the SSE hub and activity registry (S2, `events-hub.md`). Those still run in Nest; Rust lists and triggers them through the `jobs` bridge (Bridges).

## Rules

### A. The `commands` table

1. Table `commands` (baseline + `1783000000000_align-timestamp-columns-to-timestamptz.sql` + `1786500000000_updated_at_trigger.sql`, so C8 applies): `id serial`, `createdAt`/`updatedAt timestamptz NOT NULL DEFAULT now()`, `name varchar NOT NULL`, `status varchar NOT NULL DEFAULT 'queued'`, `startedOn`/`endedOn timestamptz NULL`, `trigger varchar NOT NULL DEFAULT 'manual'`, `body jsonb NULL`. No index beyond the PK, no enum. `[ts:src/modules/scheduler/entities/command.entity.ts:4]`–`[ts:src/modules/scheduler/entities/command.entity.ts:23]`, `[ts:src/common/entities/base.entity.ts:7]`–`[ts:src/common/entities/base.entity.ts:16]`
2. Vocabulary: `status` in `queued|running|completed|failed`; `trigger` in `manual|scheduled|auto` (`auto` only from marker detection). `body` is written only by `IntroDetection` (`{seasonId, mediaId, seasonNumber}`, markers spec) `[ts:src/modules/markers/markers.service.ts:152]`–`[ts:src/modules/markers/markers.service.ts:162]`; every other producer leaves it `null`, and lists return it as stored. The status page shows `body.mediaTitle` when present `[ts:client/src/app/features/system/status/status.html:218]`, a key no producer writes. Row JSON in lists: `{id, createdAt, updatedAt, name, status, startedOn, endedOn, trigger, body}`, dates ISO-8601 with ms and `Z`, nullable columns as `null` (never absent). `[ts:src/modules/scheduler/entities/command.entity.ts:6]`–`[ts:src/modules/scheduler/entities/command.entity.ts:22]`
3. Names written today: the core names of rules 10 and 15, `IntroDetection` `[ts:src/modules/markers/markers.service.ts:152]`, `ImportWatchHistory` `[ts:src/modules/media-servers/media-servers.controller.ts:107]`, `ImportSeerrRequests` `[ts:src/modules/imports/imports.controller.ts:159]`, the three `LiveTv*` crons `[ts:src/modules/livetv/services/livetv-scheduler.service.ts:34]`–`[ts:src/modules/livetv/services/livetv-scheduler.service.ts:61]`, plus nothing for plugin jobs (rule 13). The last three families are ported by their own S5 specs (markers, imports, media-servers) through rule 5 and by S7 (live TV); until S7 Nest still inserts the `LiveTv*` rows itself into the same table.

### B. Audit wrapper

4. `run_audited(name, trigger, fn)` (scheduled and in-process callers): INSERT a row `{name, status:'running', trigger, startedOn: now}`; emit `command.started {name}`; run `fn`; on `Err` log `Command <name> error: <message>` at error level (the message is not stored; `body` stays null) and set `status='failed'`, else `'completed'`; always set `endedOn = now`, UPDATE the row, emit `command.completed {name, status}`; the error is swallowed (never propagates to the cron tick). `[ts:src/modules/scheduler/command-audit.util.ts:12]`–`[ts:src/modules/scheduler/command-audit.util.ts:40]`
5. API for other Rust domains (`fliks_server::jobs::run_audited`): every domain port that audits work (`IntroDetection`, `ImportWatchHistory`, `ImportSeerrRequests`, later live TV) calls this one function; no second copy of the lifecycle. `IntroDetection` is the one producer that creates a `queued` row first and updates it by id (markers spec); it uses the update helpers of rule 6, not `run_audited`. `[ts:src/modules/markers/markers.service.ts:335]`–`[ts:src/modules/markers/markers.service.ts:385]`
6. Manual path (`POST /commands`): INSERT `{name, status:'queued', trigger:'manual'}` and answer; then, detached from the request: UPDATE `status='running', startedOn=now`; emit `command.started {name}`; run the job body; UPDATE `status='completed'|'failed', endedOn=now`; emit `command.completed {name, status}`; on failure log `Command <name> failed: <message>` (the message is not stored). The only differences from rule 4 are the `queued` stage and `trigger='manual'`. `[ts:src/modules/scheduler/scheduler.service.ts:273]`–`[ts:src/modules/scheduler/scheduler.service.ts:281]`, `[ts:src/modules/scheduler/scheduler.service.ts:333]`–`[ts:src/modules/scheduler/scheduler.service.ts:378]`

### C. Boot sweep and cron runner

7. Boot: `UPDATE commands SET status='failed', "endedOn"=now() WHERE status IN ('running','queued')`; when rows were touched, warn `Marked <n> stale command(s) as failed on startup`. Rust runs it after migrations and before spawning Nest and before the cron runner starts, so no row of this boot is swept. Nest's own sweep is deleted with `SchedulerService`. `[ts:src/modules/scheduler/scheduler.service.ts:119]`–`[ts:src/modules/scheduler/scheduler.service.ts:129]`
8. Cron runner: one in-process task per Rust-owned job (Jobs/timers), expressions in 5-field form exactly as in rule 10 (`croner`, plan §10; seconds field accepted for plugin crons later), evaluated in the server time zone (rule 9). A tick fires the job through rule 4 (`trigger='scheduled'`). No catch-up: a job whose time passed while the server was down is not run (`@nestjs/schedule` has none). A tick whose job is still queued or running in this process is skipped with a warn (C22); Nest let ticks overlap. Shutdown stops the timers and does not wait for a running job; its row is swept at the next boot (rule 7). `[ts:src/modules/scheduler/scheduler.service.ts:137]`–`[ts:src/modules/scheduler/scheduler.service.ts:174]` `[assumed]` for the skip and the shutdown (Nest has neither).
9. Server time zone: `@nestjs/schedule` builds each `CronJob` with no `timeZone`, and `cron-parser` is called with no `tz`, so both use the process zone (`TZ`, else `/etc/localtime`; Node ships its own tz database, so `TZ=Europe/Paris` works in an image without `tzdata`). Rust resolves `TZ` as an IANA name with `chrono-tz`, falls back to `/etc/localtime`, then UTC; `nextRun` and the cron runner use the same zone object `[assumed]`, Q2. `[ts:src/modules/scheduler/scheduler.service.ts:214]`

### D. `GET /commands/schedulers`

10. Core entries, in this order, `triggerable: true`, `pluginId: null`. Rust owns the first two schedules; the next three are listed by Rust but fired by Nest (rules 30, 31). `[ts:src/modules/scheduler/scheduler.service.ts:81]`–`[ts:src/modules/scheduler/scheduler.service.ts:117]`

    | name | cron (verbatim string) | labelKey |
    |---|---|---|
    | `Backup` | `0 02 * * *` | `system.cmd_backup` |
    | `RefreshMetadata` | `0 04 * * *` | `system.cmd_refresh_metadata` |
    | `RefreshPluginSources` | `0 3 * * *` | `system.cmd_refresh_plugin_sources` |
    | `SubtitleSearch` | `0 0-23/6 * * *` | `system.cmd_subtitle_search` |
    | `SubtitleUpgrade` | `0 0-23/6 * * *` | `system.cmd_subtitle_upgrade` |

    Strings from `CronExpression.EVERY_DAY_AT_2AM`, `EVERY_DAY_AT_4AM`, `PLUGIN_SOURCE_REFRESH_CRON` `[ts:src/common/constants/core-scheduler-jobs.ts:13]`, `EVERY_6_HOURS` (`@nestjs/schedule` 6.1.1 enum); they are part of the contract and the client shows them.
11. After the core five come the Nest-held jobs (rule 18): the registry jobs in registration order (today `LiveTvSourceRefresh`, `LiveTvGuideRefresh`, `LiveTvGuidePrune`, `pluginId: null`, `lastRun`/`lastStatus` from `commands` like core), then the plugin-declared jobs `{name, cron, triggerable, labelKey, lastRun: null, lastStatus: null, pluginId}` (a plugin's runs have no `commands` row, rule 13). When the bridge is unreachable the Nest-held entries are omitted and the response is still 200 (the listing "shrinks" the same way when nothing registered). `[ts:src/modules/scheduler/scheduler.service.ts:195]`–`[ts:src/modules/scheduler/scheduler.service.ts:239]`, `[ts:src/modules/scheduler/scheduled-job-registry.service.ts:45]`–`[ts:src/modules/scheduler/scheduled-job-registry.service.ts:51]`
12. `lastRun` / `lastStatus` = `startedOn` / `status` of the newest row of that name by `createdAt` (a `queued` row gives `lastRun: null, lastStatus: 'queued'`), else both `null`; one query for all non-plugin names (SQL). `nextRun` = next fire time strictly after now, computed in the zone of rule 9 and serialized as UTC ISO-8601 with ms and `Z` (a JS `Date`). `[ts:src/modules/scheduler/scheduler.service.ts:202]`–`[ts:src/modules/scheduler/scheduler.service.ts:225]`
13. A plugin job never gets a `commands` row: core owns that trail, the plugin's run does not. `[ts:src/modules/scheduler/scheduler.service.ts:227]`

### E. `POST /commands`

14. DTO `{name: string}` (`@IsString`; empty string passes); global pipe: missing or non-string `name` → 400 with the class-validator array, unknown extra key → 400 (whitelist + forbid, bootstrap rule 2). `[ts:src/modules/scheduler/commands.controller.ts:17]`–`[ts:src/modules/scheduler/commands.controller.ts:20]`
15. Known names, in this order: triggerable core schedulers (rule 10), triggerable registry jobs, then the trigger-only list `RescanAll, RefreshMissingMetadata, RescanMissingFiles, GenerateSprites, GenerateMissingSprites, DetectMarkers, DetectMissingMarkers`. Not in it: a declared plugin job (→ plugin branch, rule 18), else 400 `Unknown command: <name>. Valid: <names joined by ", ">`. Names are case-sensitive; `IntroDetection`, `ImportWatchHistory` etc. are not triggerable here. `[ts:src/modules/scheduler/scheduler.service.ts:243]`–`[ts:src/modules/scheduler/scheduler.service.ts:270]`, `[ts:src/common/constants/core-scheduler-jobs.ts:29]`–`[ts:src/common/constants/core-scheduler-jobs.ts:37]`
16. Response 201 is the whole queued row, as `GET /commands` lists it: `{id, createdAt, updatedAt, name, status:'queued', startedOn:null, endedOn:null, trigger:'manual', body:null}` (recorded from Nest, which returns the nulls). A plugin job answers 201 `{ok: true}` and no row. `[ts:src/modules/scheduler/scheduler.service.ts:273]`–`[ts:src/modules/scheduler/scheduler.service.ts:283]`
17. Dispatch (rule 6 around it): `Backup` → rule 22; `RefreshMetadata` → 23; `RefreshMissingMetadata` → 25; `RescanAll`, `RescanMissingFiles` → 27; `GenerateSprites`, `GenerateMissingSprites` → 28; `DetectMarkers`, `DetectMissingMarkers` → 29; `SubtitleSearch`, `SubtitleUpgrade`, `RefreshPluginSources` and registry jobs → bridge (rule 18). Nest has no branch for `RefreshPluginSources`: the row goes `running` then `completed` having done nothing, although the job is listed as triggerable (C21: Rust runs it). `[ts:src/modules/scheduler/scheduler.service.ts:340]`–`[ts:src/modules/scheduler/scheduler.service.ts:357]`
18. Nest-held names (registry jobs, plugin-declared jobs, and the three bridged core names): Rust asks `GET /internal/jobs` to classify the name. Registry job or bridged core name: rules 15-17 as for any job, body = `POST /internal/jobs/run {name}` held open until the job ends (204 → completed, any other status or transport error → failed). Plugin-declared job: no row; `POST /internal/jobs/run` answers immediately `202` → `{ok:true}`, `409` → 409 `Job "<name>" is already running`, `400 {message}` → 400 `Job "<name>" is <reason with '-' replaced by ' '>` (reasons `unknown job`, `not triggerable`). Bridge unreachable: a registry or plugin name is then simply unknown (400 as rule 15); a bridged core name still gets its row, which ends `failed`. `[ts:src/modules/scheduler/scheduler.service.ts:253]`–`[ts:src/modules/scheduler/scheduler.service.ts:265]`, `[ts:src/modules/plugins/plugin-jobs.service.ts:79]`–`[ts:src/modules/plugins/plugin-jobs.service.ts:83]`
19. Two jobs with one name may run at once today (no guard on the core path; only plugin jobs answer 409). Rust answers 409 `Command "<name>" is already running` when a row of that name is `queued`/`running` in this process (C22). The same `jobs::Running` claims cover the S6 subtitle tick (`subtitles.md` rule 55) and the S8 plugin jobs and scheduled calls (`plugins.md` rules 50, 55). `[ts:src/modules/scheduler/scheduler.service.ts:253]`–`[ts:src/modules/scheduler/scheduler.service.ts:283]` `[new]`

### F. List and clear

20. `GET /commands`: `p = max(1, Number(page) || 1)`, `l = min(100, max(1, Number(limit) || 25))`; `ORDER BY "createdAt" DESC` (+ `id DESC` as final tie-break, C12) `OFFSET (p-1)*l LIMIT l`; `total` = count of all rows. Absent, empty, `0` and `NaN` page/limit take the defaults; negative is clamped up; above 100 clamped down. Nest accepts `1.5` or `1e1` (fractional offset, DB-dependent) and hex; Rust: any non-canonical integer string → 400 (C1), integers keep Nest's clamping. `[ts:src/modules/scheduler/commands.controller.ts:35]`–`[ts:src/modules/scheduler/commands.controller.ts:39]`, `[ts:src/modules/scheduler/scheduler.service.ts:286]`–`[ts:src/modules/scheduler/scheduler.service.ts:296]`
21. `DELETE /commands/history`: `DELETE FROM commands WHERE status NOT IN ('running','queued')`, log `Command history cleared — <n> row(s) deleted`, answer `{deleted: n}`. `[ts:src/modules/scheduler/scheduler.service.ts:302]`–`[ts:src/modules/scheduler/scheduler.service.ts:312]`

### G. Jobs

22. **Backup** (`Backup`, cron or manual): create a dump through the system spec's `create_backup` (`system.md` rules 17-19), then delete every backup past the newest 7, log `Backup: wrote <filename> (<size> bytes)` plus `, pruned <n> older backup(s)` when any. The direct `POST /api/system/backup` does not prune. `[ts:src/modules/scheduler/scheduler.service.ts:381]`–`[ts:src/modules/scheduler/scheduler.service.ts:388]`, `[ts:src/modules/scheduler/backup.service.ts:85]`–`[ts:src/modules/scheduler/backup.service.ts:93]`
23. **RefreshMetadata** (`RefreshMetadata`, 04:00 or manual): if env `TMDB_API_KEY` is blank after trim, warn `RefreshMetadata: TMDB_API_KEY not configured` and return (row `completed`). Else load every media (Rust: `ORDER BY id`, scalar columns only), keep those with a provider id (`tmdbId` or `tvdbId` non-null, or non-empty `imdbId`), then those due (rule 24); log the start counts. For each due media `i`: emit `task.progress {command:'RefreshMetadata', current:i, total, message:title, subject}` (subject = `buildMediaProgressSubject(media)`), activity `upsertRunning('RefreshMetadata','RefreshMetadata',subject,i,total)`, call the media metadata refresh with the id only (`refreshMetadata(id)` reloads the media itself `[ts:src/modules/media/media-service/media-metadata.service.ts:219]`–`[ts:src/modules/media/media-service/media-metadata.service.ts:224]`, S5 media spec); a failure warns `RefreshMetadata: failed for "<title>": <message>` and continues. After the loop, when `total > 0`, emit a final `task.progress {current:total, total, message:'RefreshMetadata'}`; the activity row `RefreshMetadata` is removed in a `finally`. Nest sleeps 50 ms between media to yield its event loop; Rust does not. `[ts:src/modules/scheduler/scheduler.service.ts:390]`–`[ts:src/modules/scheduler/scheduler.service.ts:457]`, `[ts:src/modules/media/media-identity.util.ts:4]`–`[ts:src/modules/media/media-identity.util.ts:8]`, `[ts:src/modules/scheduler/scheduler.service.ts:42]`
24. Due test: a media is *settled* when it is a movie released more than 365 days ago (`releaseDate`, a `date` column read as `YYYY-MM-DD`, is UTC midnight of that day; when it is null, `year` (non-zero) as 1 January 00:00 local time; else not settled; a non-null unparsable `releaseDate` is not settled and does not fall back to `year`) or a series with `status='ended'`. Not settled → due. Settled → due when `metadataRefreshedAt` is null or at least 7 days old. `[ts:src/modules/scheduler/scheduler.service.ts:461]`–`[ts:src/modules/scheduler/scheduler.service.ts:480]`
25. **RefreshMissingMetadata** (trigger-only): same `TMDB_API_KEY` guard (`RefreshMissingMetadata: TMDB_API_KEY not configured`). `staleMonths = max(1, parseInt(METADATA_STALE_AFTER_MONTHS || '3', 10) || 3)`; `staleBefore = now - staleMonths` calendar months (`setMonth`, local time). Candidates = identified media (rule 23) that are incomplete (`posterUrl` empty/null, or `overview` empty/null, or a series with no `seasons` row) or never refreshed or `metadataRefreshedAt < staleBefore`. Per candidate the same progress, activity (`RefreshMissingMetadata`) and refresh as rule 23, no sleep, warn `RefreshMissingMetadata: failed for "<title>": <message>`; final progress when `candidates > 0`; summary log. `[ts:src/modules/scheduler/scheduler.service.ts:759]`–`[ts:src/modules/scheduler/scheduler.service.ts:838]`
26. **Prune commands** (`0 03 * * *`, not listed, not triggerable, no row, no event): `DELETE FROM commands WHERE "createdAt" < now() - interval '720 hours'` (Nest: `Date.now() - 30×24 h`, so not calendar days across DST), log `PruneOldCommands: deleted <n> command(s) older than 30 days`. It also removes an old `running` row (none can exist after rule 7). `[ts:src/modules/scheduler/scheduler.service.ts:151]`–`[ts:src/modules/scheduler/scheduler.service.ts:162]`
27. **RescanAll** / **RescanMissingFiles** (trigger-only): `RescanAll` = every media `(id, title, type)`; `RescanMissingFiles` = media whose library has a path and that either have no file (and a non-empty `folderName`: a root-level movie with no file is skipped) or, for a series, any file with `episodeId` null. Shared loop: log `<name>: started — <n> media to scan`; pre-register an activity `<name>:<mediaId>` (type `<name>`, parent `<name>`) as pending for every media; per media emit `task.progress {command:name, current:i, total, message:title, subject}`, `upsertRunning(name, name, undefined, i, total)` and `upsertRunning('<name>:<id>', name, subject)`, call the rescan (`media-rescan.service.ts:378`, returns `{added, removed, updated}`), remove the child row in `finally`; a failure counts as skipped and warns `<name>: skipped "<title>": <message>`; final progress when `total > 0`; the parent row is removed in a `finally`; summary `<name>: scanned <ok>/<n> media, <changes> change(s), <skipped> skipped` and, when skipped, a warn. Rust adds `ORDER BY id`. `[ts:src/modules/scheduler/scheduler.service.ts:676]`–`[ts:src/modules/scheduler/scheduler.service.ts:753]`, `[ts:src/modules/scheduler/scheduler.service.ts:844]`–`[ts:src/modules/scheduler/scheduler.service.ts:871]`, `[ts:src/modules/media/media-service/media-rescan.service.ts:378]`
28. **GenerateSprites** (force) / **GenerateMissingSprites** (trigger-only): file ids = all `media_files`; the missing variant drops files whose legacy sprite metadata path exists, a filter the S2 engine cache makes meaningless (`playback-info.md` rule 52): Rust passes every id with `force=false` and lets the engine report a cached sprite (Q4). Subjects are resolved in chunks of 1 000 ids (scalar columns of media, episode, season only). Every file is registered as pending `GenerateSprite:<fileId>` (type `GenerateSprite`, parent = command name) up front. Files are processed in batches of 2, concurrently inside a batch: per batch emit `task.progress {command, current:i, total, message: formatted subject of the first file or the command name, subject}`, `upsertRunning(command, command, undefined, i, total)`; each file calls the S2 sprite job (`stream::sprite::generate`, priority `normal` when forced else `low`); a failure warns `Sprite failed for file #<id>: <message>` (`PostImportService.generateSprite` catches and returns `null`, so the scheduler's own `<command>: failed for file <id>` warn never fires) and, like any `null` result, counts as not generated and always removes its `GenerateSprite:<id>` row. Summary `<command>: generated <g>/<n> sprites`. No final 100 % progress event and no 50 ms sleep. `[ts:src/modules/scheduler/scheduler.service.ts:482]`–`[ts:src/modules/scheduler/scheduler.service.ts:600]`, `[ts:src/modules/scheduler/post-import.service.ts:248]`–`[ts:src/modules/scheduler/post-import.service.ts:263]`
29. **DetectMarkers** / **DetectMissingMarkers** (trigger-only): seasons = `markers.listSeasonsForScan(onlyMissing)` (`s."seasonNumber" > 0`, series only, and for the missing variant at least one `hasFile` episode with `markersScannedAt` null; `ORDER BY m.title, s."seasonNumber"`; markers spec). Pre-register `IntroDetection:<seasonId>` pending (type `IntroDetection`, parent = command name), then per season: progress `{command, current:i, total, message: formatted season subject, subject}`, `upsertRunning(command, command, undefined, i, total)`, `markers.runDetectionInline(seasonId, subject)` (no `commands` row of its own; a season already in detection elsewhere returns `{0, 0}` and counts as scanned, not skipped); counts `introsDetected + outrosDetected`; a failure warns `<command>: skipped "<title>" S<n>: <message>`; final progress when `total > 0`; log `<command>: done — <d> marker(s) saved across <ok>/<n> season(s)`. `[ts:src/modules/scheduler/scheduler.service.ts:607]`–`[ts:src/modules/scheduler/scheduler.service.ts:673]`, `[ts:src/modules/markers/markers.service.ts:194]`–`[ts:src/modules/markers/markers.service.ts:258]`
30. **RefreshPluginSources** (`0 3 * * *` or manual): Rust owns the schedule and the audit row (rule 4) and runs the body through `jobs/run` (Nest: catalog `refreshAll()` then plugin auto-update `run()`, a no-op unless an admin opted in); S8 ports the body and drops the call. `[ts:src/modules/scheduler/scheduler.service.ts:167]`–`[ts:src/modules/scheduler/scheduler.service.ts:174]`
31. **SubtitleSearch** / **SubtitleUpgrade**: listed by Rust, manual trigger through `jobs/run` (`searchMissingSubtitles()` / `upgradeSubtitles()`). The scheduled firing stays Nest's `tick()` every 6 h gated by the `subtitle_*_interval` settings, and it writes no `commands` row (only the manual path does). Rust must not schedule them (double run); S6 moves both. `[ts:src/modules/scheduler/subtitle-scheduler.service.ts:69]`–`[ts:src/modules/scheduler/subtitle-scheduler.service.ts:87]`, `[ts:src/modules/scheduler/scheduler.service.ts:344]`–`[ts:src/modules/scheduler/scheduler.service.ts:347]`
32. ## SQL

- Boot sweep: `UPDATE commands SET status = 'failed', "endedOn" = now() WHERE status IN ('running','queued')`.
- Insert (scheduled / manual): `INSERT INTO commands (name, status, trigger, "startedOn") VALUES ($1,'running',$2,now()) RETURNING *` / `INSERT INTO commands (name, status, trigger) VALUES ($1,'queued','manual') RETURNING id, "createdAt", "updatedAt", name, status, trigger`.
- Transitions: `UPDATE commands SET status='running', "startedOn"=now() WHERE id=$1`; `UPDATE commands SET status=$2, "endedOn"=now() WHERE id=$1`.
- List: `SELECT * FROM commands ORDER BY "createdAt" DESC, id DESC OFFSET $1 LIMIT $2` + `SELECT count(*) FROM commands`.
- Last run per name: `SELECT DISTINCT ON (name) name, "startedOn", status FROM commands WHERE name = ANY($1) ORDER BY name, "createdAt" DESC, id DESC` (Nest: `c.id = (SELECT c2.id ... ORDER BY c2."createdAt" DESC LIMIT 1)`, ties arbitrary).
- Clear: `DELETE FROM commands WHERE status NOT IN ('running','queued')`. Prune: `DELETE FROM commands WHERE "createdAt" < now() - interval '720 hours'`.
- Job inputs (all read-only `SELECT`, `ORDER BY id`): media `(id, title, type, status, "releaseDate", year, "metadataRefreshedAt", "posterUrl", overview, "tmdbId", "tvdbId", "imdbId", "folderName", "libraryId")`; `EXISTS (SELECT 1 FROM seasons WHERE "mediaId" = m.id)`; `media_files (id, "episodeId", "mediaId")`; libraries `path`; seasons for scan (markers spec).

## Deviations

Row numbers are the S5 block of plan §15.3; each row goes into `README.md` Deviations when S5 ships. Security: none specific to this domain (the triggers are admin-level, `settings.access`, and take no path or command argument; the shell-outs of Backup are in `system.md`, F36 to F38).

- C1 and C20 (extended): `GET /api/commands` `page`/`limit` that are not canonical integers (`1.5`, `1e1`, `0x10`, ` 7 `) answer 400; integers keep the clamps of rule 20. The same extension covers `GET /api/system/logs?limit` (`system.md` rule 27). The client always sends integers.
- C12 (extended): final tie-break on every list and the last-run lookup (`id DESC`) and `ORDER BY id` on every job's input scan (Nest relies on heap order).
- C21: manual `RefreshPluginSources` runs the catalog refresh and auto-update (Nest: no dispatch branch, rule 17).
- C22: a command already `queued`/`running` under the same name is not started again: manual `POST` answers 409 `Command "<name>" is already running`, a cron tick is skipped with a warn (rules 8, 19). The web status page shows the 409 through its generic error toast.
- C97: on a DST-change day `cron-parser` skips or shifts some local fires (`0 04 * * *` Paris on 2026-03-29 is skipped) where `croner` fires each valid local time, so Rust fires them and `nextRun` shows them; the `cron-next` vector test allows a difference only in a window crossing a transition.
