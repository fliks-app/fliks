# Database migrations

Every schema change in production goes through a TypeORM migration committed
to this folder. Local dev keeps `synchronize: true` (auto-syncs from entity
metadata on each restart) so day-to-day entity tweaks don't need a migration
during exploration — but anything that lands on `main` MUST be backed by a
migration here, otherwise the prod deploy can't apply it.

## Workflow

### Generating a migration

After editing entities, with a DB whose schema matches the *previous*
migration state (typically a freshly-restored prod snapshot — NOT your
local `synchronize`-mutated DB):

```bash
npm run db:migration:generate -- src/migrations/<descriptive-name>
```

TypeORM diffs entity metadata against the live DB and emits a migration
file with the timestamp prefix. **Read the generated SQL** before
committing — TypeORM's diffing is imperfect (occasional spurious
DROP+CREATE on indexes, missed enum tweaks, etc.).

### Running migrations

```bash
npm run db:migration:run     # apply pending
npm run db:migration:revert  # undo the most recent
npm run db:migration:show    # list applied + pending
```

In production the app applies them automatically at boot
(`migrationsRun: true` when `NODE_ENV=production`).

## Baseline

The first migration captures the schema-as-of-v1.0.0. It is generated by
running `migration:generate` against an **empty** Postgres so TypeORM emits
the full set of `CREATE TABLE`/`CREATE INDEX` statements for every entity.

Existing dev / prod DBs that pre-date the migration system catch up by
inserting a row into `migrations` referencing the baseline timestamp,
without re-applying it (the schema is already there).

## Conventions

- **Names are descriptive**, not auto-generated junk: `add-user-avatar`,
  `rename-media-folder-to-foldername`, `index-media-tmdb-id`. Bad: `Migration`.
- **No `down()` methods** by default. Most teams don't roll forward by
  rolling back; a buggy `down()` that drops data is worse than no `down()`.
  Recover from a bad migration with a forward-fix migration instead.
- **One concern per migration**. Renaming a column AND backfilling its
  values AND adding an index = three migrations.
- **Long-running migrations** (table rewrites, big backfills) need a
  separate strategy than this folder — pause and pick something like
  pgroll or pt-online-schema-change before deploying them on prod.
